## Response A
# Speculative Decoding with an MTP Head: The Economics

## 1. The cost model

One speculative *round* for a batch of B sequences:

| Step | What happens | Cost |
|---|---|---|
| 1 | Target forward pass → 1 token + hidden state *h* | T_t(B) |
| 2 | MTP head on *h* → K proposed tokens | T_d(B) |
| 3 | Target forward pass over the K proposals → accepts *m*, emits 1 more token | T_v(B) |

Tokens produced per round: **B · (2 + m)** (one from step 1, *m* accepted drafts, one from step 3).
Baseline (no speculation) produces **B · 1** token per T_t(B).

$$\text{Speedup}(B) \;=\; \frac{(2+m)\,T_t(B)}{2\,T_t(B) + T_d(B)}$$

For an MTP head, T_v = T_t (same model, same batch), so the "verify cost" folds into the 2 T_t term. If you use a separate draft model, T_v can differ and the denominator becomes T_t + T_d + T_v.

Expected accepted tokens per sequence:

$$m \;=\; \sum_{i=1}^{K}\alpha^{i} \;=\; \frac{\alpha(1-\alpha^{K})}{1-\alpha}$$

For T_d ≈ 0 the speedup collapses to **(2 + m) / 2**, i.e. **1 + m/2**.

## 2. Acceptance rate is the whole game

| α | K | m = E[accepted] | Speedup (T_d→0) |
|---|---|---|---|
| 0.95 | 5 | 4.77 | 3.39× |
| 0.85 | 5 | 4.00 | 3.00× |
| 0.70 | 5 | 3.01 | 2.50× |
| 0.50 | 5 | 1.94 | 1.97× |
| 0.30 | 5 | 0.85 | 1.43× |
| 0.15 | 5 | 0.41 | 1.21× |
| 0.05 | 5 | 0.10 | 1.05× |

The 1.8× figure you see in benchmarks corresponds to roughly **α ≈ 0.6–0.7 with K = 5–8**, or **α ≈ 0.4 with K = 16**. It is not a property of the technique; it is a property of how predictable the target model's next-token distribution is on the workload you're running.

## 3. Where batch size actually enters

In the ideal model B cancels from numerator and denominator, so the speedup is **batch-size-independent**. Three practical effects break that:

- **Memory-bound → compute-bound transition.** At B = 1 the target pass is bandwidth-bound (T_t ≈ constant, dominated by weight loads). The MTP head loads a tiny fraction of the weights, so T_d/T_t is small and the speedup is near its ideal value. At large B both passes are compute-bound and T_d/T_t ≈ (FLOPs_mtp / FLOPs_target), which is the same ratio. The speedup is roughly flat across B, but the *absolute* latency per token degrades because you've doubled the GPU work per round.

- **Heterogeneous acceptance within a batch.** The verification pass costs T_t(B) regardless of how many tokens each sequence accepts. A batch mixing α = 0.9 sequences with α = 0.2 sequences gets an effective m that is the batch average, dragged down by the low-α sequences. At B = 1 there is no mixing; at B = 64 the variance in m across sequences means you pay full verification cost for sequences that accept almost nothing.

- **Kernel-launch and allocator overhead.** T_d(B) has a fixed component (CUDA kernel launches, paged-attention bookkeeping for K extra positions) that does not amortise at small B but is negligible at large B. This makes the speedup slightly *worse* at B = 1–4 for poorly fused MTP implementations.

Rule of thumb: **speculation helps latency at B = 1 and helps throughput at any B, but the throughput gain is diluted when acceptance rates are heterogeneous across the batch.**

## 4. When it cannot pay off

Set speedup > 1:

$$m \cdot T_t \;>\; T_d \qquad\Longleftrightarrow\qquad \frac{\alpha(1-\alpha^K)}{1-\alpha} \;>\; \frac{T_d}{T_t}$$

Concrete thresholds (K = 5):

| T_d / T_t | Break-even α | Interpretation |
|---|---|---|
| 0.02 (well-fused MTP head) | ≈ 0.04 | Almost any draft helps |
| 0.05 | ≈ 0.06 | Still very forgiving |
| 0.10 | ≈ 0.11 | Need ≥ 11 % per-token acceptance |
| 0.20 | ≈ 0.18 | Need ≥ 18 % acceptance |
| 0.50 (expensive draft) | ≈ 0.35 | Must be quite predictable |

It **cannot** pay off when:

1. **α < T_d / T_t / (K·(1-α))** — the draft head costs more than the tokens it saves. This is the single dominant failure mode.
2. **K is too large for the α regime.** If α = 0.5, m saturates near 2 regardless of K. Going from K = 5 to K = 32 buys almost nothing but doubles the verification pass length (and the MTP head's own latency).
3. **The target model is already fast and the MTP head is not.** If T_t = 2 ms and T_d = 1 ms, you need m > 0.5 just to break even, which requires α > ~0.12. The fixed overhead of the MTP head (kernel launches, extra memory traffic for K positions) eats the gain.
4. **The workload is high-entropy.** Code completion on novel APIs, creative writing, or multi-turn conversation with high temperature all push α down. If the target's own top-1 probability averages below the break-even α, no draft model can fix that.

## 5. The smallest predictive experiment

You cannot measure α without the draft head, but you **can** measure the ceiling on α, and that is enough to decide whether to build the head at all.

**Experiment: target-model self-predictability audit (~15 minutes, no draft model, no code changes)**

1. Pick 50–100 prompts representative of your actual workload (same domain, same temperature, same context lengths).
2. Run the target model autoregressively for 256 tokens per prompt. At every position *t*, record two numbers:
   - **p₁(t)** = the probability the target assigns to the token it actually emitted at position *t+1* (i.e. the argmax or sampled-token probability under the target's own distribution).
   - **H(t)** = the entropy of the target's next-token distribution at position *t*.
3. Compute the mean and distribution of p₁ across all positions.

**Why this works:** the acceptance rate for *any* draft model satisfies

$$\alpha \;\leq\; \mathbb{E}\!\bigl[\min(1,\; p_{\text{target}}(t)/p_{\text{draft}}(t))\bigr] \;\leq\; \mathbb{E}[p_1]$$

The second inequality holds because p_draft(t) ≥ 0 and the min caps at 1. So **mean p₁ is a hard upper bound on α for every possible draft model**, including a hypothetical perfect one. A real MTP head trained on the target's hidden states typically achieves **α ≈ 0.75–0.90 × mean p₁** (it captures most of the target's confidence but not all of it, because the target's distribution has a long tail the head doesn't model).

**Decision rule:**

- Compute the break-even α from your cost model: α\* = T_d / (K · T_t), roughly.
- If **0.8 × mean(p₁) < α\***, the MTP head cannot pay off. Skip it.
- If **0.8 × mean(p₁) > 2 × α\***, it will almost certainly pay off. Build the head.
- In between, build the head and measure.

The entropy H(t) is a useful diagnostic: positions with H > 3 nats (roughly, the target is uncertain among > 20 tokens) will have p₁ < 0.05 and will drag α down. If more than ~30 % of positions have H > 3, your workload is inherently low-acceptance and you should consider reducing K, raising the draft model's capacity, or restricting speculation to a subset of positions (e.g. only speculate on low-entropy positions).

This experiment costs one forward pass of the target model over your evaluation prompts — the same cost as running your eval suite — and requires no draft model, no speculative-decoding infrastructure, and no training. It converts the "will this help?" question into a single number you can compare against a threshold you already know from the cost model.

## Response B
# Speculative Decoding with an MTP Head: The Economics

## The speedup formula

One speculative cycle has three sequential phases:

| Phase | Cost | Why |
|---|---|---|
| Target pass at position *t* | $T_t$ | Produces token *t*+1 (always accepted) **and** the hidden state the MTP head needs |
| MTP-head pass | $T_d$ | Predicts *K* future tokens from that hidden state |
| Target verify pass | $T_v$ | Processes all *K* proposed tokens in one forward pass |

Under a geometric acceptance model (per-token acceptance probability $\alpha$), the expected tokens per cycle is

$$E[T] = \frac{1-\alpha^{K+1}}{1-\alpha}$$

The speedup over plain autoregressive decoding is therefore

$$\boxed{\;\text{Speedup} \;=\; \frac{E[T]}{1 + r + \gamma}\;}$$

where

- $r = T_d / T_t$ — draft-head cost as a fraction of one target pass (typically 0.02–0.15 for a single-block MTP head),
- $\gamma = T_v / T_t$ — **verification cost as a multiple of one target pass**.

The "+1" in the denominator is the non-negotiable cost of the initial target pass that feeds the MTP head. This is the structural tax that separates MTP-head speculation from a separate draft model.

## Why $\gamma$ is the whole story

$\gamma$ is where batch size, model size, and hardware enter. A transformer forward pass has two costs: loading weights from HBM (memory-bound) and FLOPs (compute-bound).

- **Memory-bound decode** (small model, large GPU, small batch): the weight load dominates. Processing *K* new tokens reuses the same weight load, so $\gamma \approx 1$. The verify pass costs about the same as a single-token pass.

- **Compute-bound decode** (large model, small GPU, large batch): the FLOPs dominate. Processing *K* tokens costs *K* times the FLOPs of one token, so $\gamma \approx K$.

The crossover batch size is set by arithmetic intensity:

$$B^* \;\approx\; \frac{\text{weight bytes}}{\text{HBM bandwidth} \;\times\; \text{FLOPs per token}}$$

Below $B^*$ you are memory-bound ($\gamma\to 1$); above it you are compute-bound ($\gamma\to K$). In practice $\gamma$ transitions smoothly between these limits as $B$ sweeps through $B^*$.

## The two regimes made concrete

**Memory-bound ($\gamma \approx 1$):**

$$\text{Speedup} \approx \frac{E[T]}{2 + r}$$

For $K=5$, $r=0.1$, $\alpha=0.9$: $E[T]=4.69$, speedup $\approx 2.2\times$. This is where you see the 1.8× headline numbers.

**Compute-bound ($\gamma \approx K$):**

$$\text{Speedup} \approx \frac{E[T]}{K + 1 + r}$$

Since $E[T] \le K+1$ always, the speedup is **strictly less than 1** for any $r > 0$. You pay *K* target-passes' worth of compute to get at most *K*+1 tokens, plus the draft-head overhead. **It is a slowdown, full stop, regardless of acceptance rate.**

This is the regime you hit when serving at batch sizes well above $B^*$, or when the model is large enough that even batch-1 decode is compute-bound (e.g., a 70B model on a single A100).

## When it cannot pay off

The necessary and sufficient condition for a net gain is:

$$E[T] > 1 + r + \gamma \quad\Longleftrightarrow\quad \frac{1-\alpha^{K+1}}{1-\alpha} > 1 + r + \gamma$$

It **cannot** pay off in three situations:

1. **Compute-bound verification** ($\gamma = K$): impossible for any $\alpha$, any $r > 0$. The algebra above shows the speedup ceiling is $(K+1)/(K+1+r) < 1$.

2. **Low acceptance rate in the memory-bound regime**: you need $E[T] > 2 + r$. For $K=5$, $r=0.1$ this requires $\alpha \gtrsim 0.55$. A draft head that is poorly aligned with the target (wrong architecture, undertrained, or the target model is highly stochastic) will sit below this and lose.

3. **The MTP head is not lightweight enough**: if $r$ is large (a multi-layer MTP head on a small target model), the $+r$ term in the denominator eats the gain even at high $\alpha$. The head must be a small fraction of the target.

A useful rule of thumb: **if $\gamma > E[T] - 1 - r$, you lose.** Measure $\gamma$ first; it is the dominant term.

## The smallest experiment that predicts the outcome

You have three unknowns: $\alpha$, $\gamma$, $r$. You want to predict the speedup before training the MTP head. Rank them by information content:

### 1. Measure $\gamma$ (the decisive number) — 10 minutes, no new code

At your **target serving batch size** $B$ and context length $L$, time the target model's forward pass with:

- 1 new token appended (normal decode step) → $T_t$
- $K$ new tokens appended in one pass (pad the input) → $T_v$

Set $\gamma = T_v / T_t$. Repeat at $B = 1, 4, 16, 64$ to see the transition.

**Decision rule:** if $\gamma \approx K$ at your operating batch size, **stop — speculation will not help this model on this hardware at this batch size.** No MTP head, no training. This single measurement rules out the compute-bound case entirely.

### 2. Estimate $\alpha$ from the target model's output entropy — 1 forward pass over your eval set

Run the target model on a representative prompt set. At each position, record the entropy $H_t$ of the output distribution. A well-trained MTP head approximates the target's distribution, so a good upper bound on per-token acceptance is

$$\alpha \;\lesssim\; 1 - \frac{\bar{H}}{\log V}$$

where $\bar{H}$ is the mean output entropy and $V$ is the vocabulary size. This is the fraction of probability mass the top-1 token carries, averaged over positions. A real MTP head will achieve somewhat less than this bound, so treat it as an optimistic ceiling.

If even this ceiling gives $E[T] \le 1 + r + \gamma$, the head won't help. If the ceiling gives a comfortable margin, the head probably will.

### 3. $r$ is known a priori

$r$ is the FLOPs (or parameter) ratio of the MTP head to the full target model. For a single transformer block head on a 60-layer model, $r \approx 1/60 \approx 0.02$. You know this from the architecture; no measurement needed.

### Putting it together

```
γ  ← timed benchmark (step 1)
α  ← entropy estimate (step 2), treat as upper bound
r  ← architecture (step 3)

predicted_speedup = (1 - α^(K+1)) / ((1-α) × (1 + r + γ))
```

If the predicted speedup with the **upper-bound** $\alpha$ is below 1.1, the head is not worth building. If it's above 1.3, build it and expect roughly that number. The entropy estimate is conservative enough that a 1.3× prediction usually lands at 1.1–1.5× in practice.

**Total cost of the experiment: one timed benchmark sweep and one forward pass over your eval set. No training, no new architecture, no GPU-hours beyond what you'd spend profiling the model anyway.** The entire prediction hinges on $\gamma$, which is a property of the *target model + hardware + batch size*, not of the MTP head. That is why it is the right thing to measure first.
