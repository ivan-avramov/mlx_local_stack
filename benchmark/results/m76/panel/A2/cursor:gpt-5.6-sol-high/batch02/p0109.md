## Response A
# Benchmark Results Pipeline & Storage Design

## Design Principles

The core tension is between **immutability** (a result must never silently change) and **regradability** (the *interpretation* of a result can change). The resolution is to separate the **run** (what the model did) from the **grading** (how we scored it), and make both content-addressed and append-only. A regrade is a new grading record that references the same run; it never touches the original.

---

## 1. Storage Layout

Three tiers, each with a distinct role and access pattern:

```
benchmarks/
├── artifacts/                  ← Tier 1: content-addressed, immutable blobs
│   └── sha256/
│       └── a3/f1/…            (two-level fan-out)
│
├── manifests/                  ← Tier 2: structured, append-only JSON docs
│   ├── runs/
│   │   └── 2025-07-14/
│   │       └── run_9f2c…manifest.json
│   └── gradings/
│       └── 2025-07-14/
│           └── grade_41ab…manifest.json
│
├── index/                      ← Tier 3: queryable, rebuildable
│   ├── runs.parquet
│   ├── gradings.parquet
│   └── metrics.parquet
│
└── schemas/                    ← versioned schema definitions
    ├── run_manifest.v3.json
    ├── grading_manifest.v2.json
    └── metric_row.v1.json
```

All three tiers live on the same filesystem or object store (S3, GCS, NFS). The artifact tier is the source of truth; the index tier is a **derived cache** that can be rebuilt from manifests at any time.

---

## 2. Tier 1 — Content-Addressed Artifact Store

Every raw input and output is stored as a blob keyed by its SHA-256.

```
artifacts/sha256/a3/f1/a3f1c8e2…blob
```

What goes here:

| Artifact type | Content | Example |
|---|---|---|
| `prompt` | The exact prompt sent to the model (system + user turns, rendered) | `{"system": "You are…", "user": "Solve…"}` |
| `model_output` | Raw model response: text, token IDs, logprobs, finish reason, latency | `{"text": "…", "tokens": [42,…], "logprobs": […], "finish": "stop", "latency_ms": 2340}` |
| `model_config` | Full generation config | `{"model": "gpt-4o-2024-11-20", "temperature": 0.0, "max_tokens": 4096, "seed": 42}` |
| `env_snapshot` | Runtime fingerprint | `{"os": "linux", "cuda": "12.4", "docker_image": "sha256:…", "python": "3.12.1", "libs": {"torch": "2.4.1"}}` |
| `grader_input` | What the grader received (may differ from raw output — e.g., truncated, reformatted) | same shape as `model_output` or a subset |
| `grader_output` | Grader's full response: score, rationale, rubric breakdown, LLM-grader raw text | `{"score": 0.85, "rationale": "…", "rubric": {"correctness": 1.0, "style": 0.5}}` |
| `grader_config` | Grader identity and params | `{"grader": "llm-judge", "model": "claude-sonnet-4-20250514", "rubric": "rubric_v7.yaml", "temp": 0.0}` |
| `benchmark_suite` | The versioned set of prompts/tasks for a benchmark | `{"name": "gsm8k", "version": "2025-07", "num_tasks": 1319}` |

**Key property:** if two runs use the same prompt, the blob is stored once. Deduplication is free.

## 3. Tier 2 — Run Manifest

One JSON document per run. This is the **provenance record** — it is the "recipe" that lets a reader reconstruct exactly what happened.

```json
{
  "manifest_id": "run_9f2c8a1e",
  "schema_version": 3,
  "created_at": "2025-07-14T09:32:11Z",

  "provenance": {
    "benchmark_suite": {
      "name": "gsm8k",
      "version": "2025-07",
      "artifact_sha256": "b7e3…c2"
    },
    "model": {
      "name": "gpt-4o-2024-11-20",
      "weights_ref": "api://gpt-4o-2024-11-20",
      "config_artifact_sha256": "d4a1…f0"
    },
    "run_code": {
      "repo": "github.com/org/eval-harness",
      "git_sha": "e4c9b21a",
      "branch": "main"
    },
    "env_snapshot_sha256": "1c8e…a9"
  },

  "sampling": {
    "temperature": 0.0,
    "top_p": 1.0,
    "max_tokens": 4096,
    "seed": 42
  },

  "tasks": [
    {
      "task_id": "gsm8k_0001",
      "prompt_sha256": "a3f1…c8",
      "output_sha256": "7b2d…e1",
      "status": "ok"
    },
    {
      "task_id": "gsm8k_0002",
      "prompt_sha256": "a3f1…c8",
      "output_sha256": "c940…37",
      "status": "ok"
    }
    // … one entry per task
  ],

  "run_metadata": {
    "total_tasks": 1319,
    "completed": 1319,
    "failed": 0,
    "wall_time_s": 412.7,
    "total_tokens": 2847301
  }
}
```

The manifest is **append-only**: once written, its bytes never change. If you need to annotate it, you write a new manifest that references the old one.

### Why this shape

- `tasks[]` is a flat array of (prompt_hash → output_hash) pairs. A reader iterates it, fetches each blob by hash, and has the complete I/O for every task. No ambiguity.
- `provenance` captures the full causal chain: which benchmark version, which model weights, which harness code, which machine.
- `sampling.seed` + `temperature` make the run reproducible (or document why it isn't, for stochastic samplers).

## 4. Tier 2b — Grading Manifest

Grading is a **separate, later** operation. A grading manifest references a run manifest and produces per-task scores.

```json
{
  "manifest_id": "grade_41ab77e0",
  "schema_version": 2,
  "created_at": "2025-07-15T14:01:00Z",

  "grader": {
    "name": "llm-judge",
    "model": "claude-sonnet-4-20250514",
    "config_artifact_sha256": "f8c2…14",
    "code_git_sha": "a1b2c3d4"
  },

  "references_run": "run_9f2c8a1e",

  "tasks": [
    {
      "task_id": "gsm8k_0001",
      "grader_input_sha256": "7b2d…e1",
      "grader_output_sha256": "e5a0…92",
      "score": 1.0
    },
    {
      "task_id": "gsm8k_0002",
      "grader_input_sha256": "c940…37",
      "grader_output_sha256": "1f3b…88",
      "score": 0.0
    }
  ],

  "aggregate": {
    "metric": "accuracy",
    "value": 0.743,
    "n": 1319
  }
}
```

**Regrading** = write a new grading manifest with a different `grader` block, same `references_run`. The old grading manifest is untouched. A reader can see the full grading history for a run by querying all grading manifests that reference it.

## 5. Tier 3 — Queryable Index

Derived from manifests. Rebuildable. This is what analysts and dashboards query.

**`runs.parquet`** — one row per run:

| Column | Type | Source |
|---|---|---|
| `run_id` | string | manifest_id |
| `benchmark` | string | provenance.benchmark_suite.name |
| `benchmark_version` | string | provenance.benchmark_suite.version |
| `model` | string | provenance.model.name |
| `config_hash` | string | provenance.model.config_artifact_sha256 |
| `git_sha` | string | provenance.run_code.git_sha |
| `created_at` | timestamp | created_at |
| `n_tasks` | int | run_metadata.total_tasks |
| `wall_time_s` | float | run_metadata.wall_time_s |

**`metrics.parquet`** — one row per (run, grading, task, metric):

| Column | Type |
|---|---|
| `run_id` | string |
| `grading_id` | string |
| `grader_name` | string |
| `grader_model` | string |
| `task_id` | string |
| `metric_name` | string (e.g., "accuracy", "pass@1", "bleu") |
| `value` | float |
| `graded_at` | timestamp |

**`gradings.parquet`** — one row per grading manifest, with the aggregate.

The index is rebuilt by a batch job that walks `manifests/` and extracts the flat columns. Because manifests are append-only, the rebuild is idempotent: `INSERT OR IGNORE` on `(run_id, grading_id, task_id, metric_name)`.

## 6. Provenance — How a Reader Reconstructs a Run

Given a row in `metrics.parquet`, the reconstruction chain is:

```
metrics row
  → run_id, grading_id
    → grading manifest (manifests/gradings/…/grade_41ab…manifest.json)
      → grader config artifact (fetch by sha256)
      → references_run → run manifest
        → provenance.model.config_artifact_sha256 → fetch model config
        → provenance.env_snapshot_sha256 → fetch env snapshot
        → provenance.benchmark_suite.artifact_sha256 → fetch suite definition
        → tasks[i].prompt_sha256 → fetch exact prompt
        → tasks[i].output_sha256 → fetch exact model output
        → grader_input_sha256 → fetch what grader saw
        → grader_output_sha256 → fetch grader's raw response + rationale
```

Every hop is a content hash. The reader never trusts a name or a mutable reference. If any blob is missing, the chain breaks loudly rather than silently returning stale data.

## 7. Immutability Guarantees

| Mechanism | What it protects |
|---|---|
| Content-addressed blobs | You can't modify a blob without changing its hash; the manifest still points at the old hash |
| Append-only manifests | Written once, never rewritten. Corrections = new manifest |
| Grading separated from run | A regrade never touches the run manifest or the model output blob |
| Git SHA in provenance | The exact harness code is pinned, not a branch name |
| Docker image digest (not tag) | The exact environment is pinned |
| Object store WORM / versioning | At the storage layer, delete/overwrite is disabled or versioned |

If you're on S3: enable **Object Lock** (compliance mode) on the `artifacts/` prefix. On a local filesystem: `chattr +i` or just discipline + the hash verification on read.

## 8. Schema Evolution

Two axes of evolution, handled differently:

**Artifact blobs (Tier 1):** The bytes are frozen. Schema evolution here means *interpretation* evolves. Each blob carries a `content_type` and optionally a `format_version` in its header. A reader dispatches on these:

```json
{"format_version": 2, "content_type": "model_output",
 "text": "…", "tokens": [42,…], "logprobs": null,
 "finish": "stop", "latency_ms": 2340}
```

When you add a field (e.g., `reasoning_tokens`), old blobs simply lack it. Readers must treat missing fields as `null`, not error. This is the "additive evolution" rule: **never rename or repurpose a field; only add new ones.**

**Manifests (Tier 2):** Each manifest carries `schema_version`. A registry in `schemas/` maps version → JSON Schema or protobuf descriptor. The manifest reader loads the right schema for the version. Old manifests parse with old schemas; new manifests use new schemas. No migration of old data.

```
schemas/
├── run_manifest.v1.json      ← original
├── run_manifest.v2.json      ← added "sampling.seed"
└── run_manifest.v3.json      ← added "provenance.env_snapshot_sha256"
```

**Index (Tier 3):** Rebuilt from manifests, so it always reflects the current schema. Old runs that lack a new field simply have `null` in that column. Parquet's schema evolution handles adding columns without rewriting old files.

## 9. Deduplication

Content addressing gives you dedup for free at the blob level:

- **Prompts:** 1,319 tasks in GSM8k → 1,319 prompt blobs. Run the benchmark 50 times → still 1,319 blobs.
- **Model configs:** 10 configs × 50 runs → 10 blobs, not 500.
- **Model outputs:** With `temperature=0` and a fixed seed, identical inputs produce identical outputs → same hash → one blob. With stochastic sampling, each run produces new blobs (correctly, because they *are* different).

The only real dedup concern is at the **manifest** level: don't re-run a (benchmark, model, config, seed) tuple you've already run. The pipeline checks the index before launching:

```python
existing = index.query(
    benchmark="gsm8k", model="gpt-4o", config_hash=cfg_hash,
    seed=42, benchmark_version="2025-07"
)
if existing:
    skip_or_reuse(existing.run_id)
```

## 10. Pipeline Flow

```
┌──────────────────────────────────────────────────────────────────┐
│  ORCHESTRATOR (cron / CI trigger)                                │
│  1. Resolve run spec: benchmark, model, config, seed            │
│  2. Check index for dedup → skip if exists                     │
│  3. Snapshot env (docker digest, lib versions, git SHA)         │
│  4. Write env_snapshot blob → hash                             │
└──────────────┬───────────────────────────────────────────────────┘
               │
               ▼
┌──────────────────────────────────────────────────────────────────┐
│  RUNNER (one process per run, or parallel workers per task)      │
│  1. For each task in suite:                                    │
│     a. Hash prompt → store blob (dedup)                        │
│     b. Call model with exact config                            │
│     c. Hash raw output → store blob                            │
│  2. Assemble run manifest (hashes + provenance)                │
│  3. Write manifest to manifests/runs/<date>/                   │
│  4. Append row to index (or mark for batch rebuild)            │
└──────────────┬───────────────────────────────────────────────────┘
               │
               ▼
┌──────────────────────────────────────────────────────────────────┐
│  GRADER (can run later, independently, multiple times)          │
│  1. Load run manifest → fetch outputs by hash                  │
│  2. For each task:                                            │
│     a. Prepare grader_input → hash → store                    │
│     b. Invoke grader (rule-based or LLM)                      │
│     c. Hash grader_output → store                             │
│  3. Write grading manifest → manifests/gradings/<date>/        │
│  4. Append rows to metrics.parquet                            │
└──────────────┬───────────────────────────────────────────────────┘
               │
               ▼
┌──────────────────────────────────────────────────────────────────┐
│  INDEX REBUILDER (batch, nightly or on-demand)                  │
│  Walk all manifests → extract flat columns → rewrite Parquet   │
│  Idempotent: INSERT OR IGNORE on natural key                   │
└──────────────────────────────────────────────────────────────────┘
```

The critical decoupling: **the runner never grades, and the grader never runs the model.** They communicate only through the artifact store and manifests. This is what makes regrading a non-event.

## 11. Practical Notes

- **Volume math:** Dozens of runs/week × ~1,000 tasks × ~2 KB per output blob ≈ ~100 MB/week of artifacts. A single SSD or a small S3 bucket handles years of data. This is not a big-data problem; it's a *correctness* problem.

- **Verification on read:** Every time a reader fetches a blob, re-hash it and compare to the manifest's hash. A mismatch means corruption or tampering; fail loudly. This makes the content-addressing a real integrity guarantee, not just a naming convention.

- **LLM graders are non-deterministic:** Even at `temperature=0`, LLM graders can produce different rationales across calls. This is fine — each grading is its own immutable record. If you need stable scores, run the grader k times and store all k grading manifests. The aggregate in the index can be the mean.

- **Retention:** Artifacts are effectively permanent (they're small). Indexes are cheap to rebuild. If you ever need to purge, delete the manifest and its referenced blobs become garbage-collectable (refcount by hash across all manifests).

- **Tooling:** A thin CLI (`benchctl`) wraps the layout: `benchctl add-run`, `benchctl grade --run run_9f2c --grader llm-judge`, `benchctl show run_9f2c --task gsm8k_0001` (fetches and displays the full I/O chain), `benchctl compare run_a run_b`. The CLI is the human-facing interface; the storage layout is the machine-facing contract.

## Response B
# Benchmark Results Pipeline & Storage Design

## Core Principle: Separate Generation from Evaluation

The single most important architectural decision: **model outputs and grader scores are different entities with different lifecycles.** Generation is expensive, immutable, and produced once. Evaluation is cheap, repeatable, and may be re-run with a new grader version. Conflating them into one record makes regrading either impossible or destructive.

```
prompt ──► [model + config] ──► generation (immutable artifact)
                                         │
                                         ▼
                              [grader v1] ──► evaluation_1
                              [grader v2] ──► evaluation_2   ← regrade, no regeneration
                              [grader v3] ──► evaluation_3
```

---

## Entity Model

Five entities, each with a stable identity:

| Entity | Identity | Mutability | Cardinality |
|---|---|---|---|
| **BenchmarkSuite** | `suite_id` + `suite_version` | Immutable (new version = new id) | 1 per suite release |
| **Run** | `run_id` (ULID) | Immutable | 1 per model-config execution |
| **Generation** | `gen_hash` (SHA-256 of content) | Immutable | 1 per (run × task) |
| **Evaluation** | `eval_id` (ULID) | Immutable | 1 per (generation × grader × grader_version) |
| **Grader** | `grader_id` + `grader_version` | Immutable | 1 per grader release |

Every entity carries a **provenance block** (see below).

---

## Storage Layout

Two tiers: **content-addressed object store** for artifacts, **structured metadata store** for everything else.

### Object store (S3 / GCS / local filesystem)

```
benchmarks/
  suites/
    {suite_id}/{suite_version}/
      manifest.json          # task list, prompt hashes, schema version
      prompts/
        {task_id}.json       # prompt content, metadata, expected-output hints
  runs/
    {run_id}/
      run.json               # provenance + config snapshot (see schema below)
  generations/
    {sha256[0:2]}/{sha256[2:4]}/{sha256}.json
    # content-addressed: hash of canonicalized generation record
  evaluations/
    {eval_id}/
      eval.json              # scores, rationale, grader provenance
```

Content-addressed generations are the deduplication mechanism. If two runs produce byte-identical output for the same task, they share one blob. The run-level record still exists separately, preserving the *fact that a run happened* even if its output was a duplicate.

### Metadata store (Postgres / DuckDB / Parquet + index)

```
suites(suite_id, suite_version, name, schema_version, created_at, manifest_uri)

runs(run_id, suite_id, suite_version, model_name, model_revision,
     config_jsonb,            -- full config snapshot, not a reference
     code_commit, code_repo,
     env_fingerprint,         -- OS, CUDA, library versions
     started_at, finished_at,
     status,                  -- completed | partial | failed
     provenance_jsonb)

generations(gen_hash, run_id, task_id, suite_id, suite_version,
            schema_version,
            content_uri,      -- pointer to object store
            token_count, latency_ms,
            created_at)

evaluations(eval_id, gen_hash, grader_id, grader_version,
            grader_model,     -- if LLM-judge: which model judged
            scores_jsonb,     -- the actual metric values
            rationale_text,
            schema_version,
            created_at,
            provenance_jsonb)

evaluations_index(eval_id, gen_hash, grader_id, grader_version,
                  metric_name, metric_value)
                  -- denormalized for fast "best score per metric" queries
```

The `evaluations_index` table is the key to making regrading practical: you can query "what is the current score for generation X under grader Y v3" without scanning all evaluations.

### Generation record (content-addressed blob)

```json
{
  "gen_hash": "sha256:3f2a…",
  "schema_version": 2,
  "run_id": "01J9XK3M7PQ2R8T4W5V6N1B0C3",
  "task_id": "mmlu/physics/q_0042",
  "suite": { "suite_id": "mmlu", "suite_version": "2024-12-01" },
  "prompt": {
    "messages": [
      { "role": "system", "content": "You are a helpful assistant." },
      { "role": "user",   "content": "What is the SI unit of force?" }
    ]
  },
  "output": {
    "text": "The SI unit of force is the newton (N).",
    "finish_reason": "stop",
    "token_count": 12,
    "logprobs": null
  },
  "latency_ms": 847,
  "created_at": "2025-01-15T09:23:14Z"
}
```

The `gen_hash` is computed over the canonicalized JSON (sorted keys, no whitespace, no `run_id`/`created_at` fields). This means two runs that produce identical prompt+output pairs hash to the same value regardless of when or where they ran.

### Evaluation record

```json
{
  "eval_id": "01J9XK7Q2W8R4T6Y1B3N5C9D0E",
  "schema_version": 1,
  "gen_hash": "sha256:3f2a…",

    "grader_id": "exact-match",
    "grader_version": "1.3.0",
    "implementation": "bench-graders/exact_match.py",
    "code_commit": "e4a7c1f"
  },

    "exact_match": 1.0,
    "answer_extracted": "newton"
  },

  "created_at": "2025-01-15T12:01:00Z"

```

For LLM-judge graders, `grader.implementation` points to the judge model + prompt template, and `rationale` carries the judge's explanation. A regrade with judge v2 writes a *new* `eval_id` against the same `gen_hash`.

## Pipeline Stages

```
┌─────────────────────────────────────────────────────────────────────┐
│ 1. SUITE LOADING                                                   │
│    Load suite manifest → validate against schema_version           │
│    Compute per-task prompt hashes → write to object store          │
└──────────────────────────┬──────────────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 2. GENERATION                                                      │
│    For each task: call model → capture output                      │
│    Canonicalize → hash → write generation blob (skip if exists)    │
│    Record run.json on completion                                   │
│    Checkpoint after every N tasks (resume on crash)                │
└──────────────────────────┬──────────────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 3. EVALUATION                                                      │
│    For each generation × each configured grader:                   │
│      Run grader → write eval.json                                  │
│      Insert into evaluations_index                                 │
│    Idempotent: skip (gen_hash, grader_id, grader_version)          │
│    tuples that already exist                                       │
└──────────────────────────┬──────────────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 4. AGGREGATION (derived, recomputable)                             │
│    Compute per-run, per-suite, per-category aggregates             │
│    Store as derived views — never the source of truth              │
└─────────────────────────────────────────────────────────────────────┘
```

Stage 3 is the one that runs again on regrade. Everything else is one-shot.

## How Each Requirement Is Met

### Provenance

Every record is self-describing. A reader with an `eval_id` can walk the chain:

```
eval_id → gen_hash → run_id → run.json
                                    ├─ model name + revision (weight hash)
                                    ├─ full config snapshot (inlined)
                                    ├─ code commit
                                    └─ environment fingerprint
```

No external lookup needed. The run record is a **snapshot**, not a reference, so it survives deletion of the source config file, the git repo, or the GPU node.

### Immutability

- Object store blobs are write-once (S3 object lock, or simply: the hash *is* the path, so overwriting would corrupt the index).
- Metadata rows are append-only. Corrections are new rows with a `supersedes` field pointing at the old row.
- The `evaluations_index` table is the one mutable surface, but it's a derived view — delete all rows for a `gen_hash` and re-derive from `evaluations`.

### Schema Evolution

Three layers of protection:

1. **`schema_version` on every record.** The reader dispatches on this. A v1 generation reader and a v2 reader can coexist.
2. **Additive-only metadata schema.** New columns default to NULL. Old rows simply lack the new field. The `evaluations_index` table uses EAV-style `(metric_name, metric_value)` rows so a new metric is a new row, not a new column.
3. **Suite versioning.** A new prompt in the benchmark suite is a new `suite_version`. Old runs reference the old version and remain interpretable. You never mutate a suite in place.

For the content-addressed blobs, the canonicalization format is pinned by `schema_version`. A migration script can re-canonicalize and re-hash, writing new blobs and a mapping table from old hash → new hash, without touching the originals.

### Deduplication

Two levels:

- **Artifact-level:** Content-addressed generations. Identical output = one blob. The `generations` metadata table has a unique constraint on `(run_id, task_id)` but *not* on `gen_hash`, so two runs can legitimately share a generation while each retaining its own run-level record.
- **Evaluation-level:** Unique constraint on `(gen_hash, grader_id, grader_version)`. Re-running the same grader on the same generation is a no-op (or, if you want to track re-runs for variance, relax to allow multiple and add a `regrader_run` field).

### Reader Reconstruction

A reader given any `eval_id` reconstructs the full execution:

```python
def reconstruct(eval_id):
    ev  = load(f"evaluations/{eval_id}/eval.json")
    gen = load(ev["content_uri"])          # the actual prompt + model output
    run = load(f"runs/{gen['run_id']}/run.json")

    return {
        "prompt":      gen["prompt"],
        "model":       run["model"],        # name, weight revision, sampling params
        "config":      run["config"],        # system prompt, few-shot, seed
        "code":        run["code"],          # exact commit
        "environment": run["environment"],   # OS, CUDA, library versions
        "output":      gen["output"],        # the model's actual response
        "grader":      ev["grader"],         # grader id, version, code commit
        "scores":      ev["scores"],
        "timeline":    {
            "generated_at": gen["created_at"],
            "evaluated_at": ev["created_at"],
            "run_window":   (run["started_at"], run["finished_at"])
        }
    }
```

No ambiguity. The exact prompt, the exact model weights, the exact sampling parameters, the exact grader code — all recoverable from the record alone.

## Practical Details Worth Getting Right

**Checkpointing.** Generation of 500 tasks takes hours. Checkpoint after every 50 tasks by writing a `runs/{run_id}/checkpoint.json` with the list of completed `task_id`s. On crash, resume from there. The content-addressed store makes this safe — re-generating a task that already has a blob just overwrites nothing.

**Partial runs.** A run that crashes at task 300/500 has `status: "partial"`. Its 300 generations are valid and evaluable. Don't block evaluation on run completion.

**Grader drift.** If you regrade 500 generations with grader v2, you get 500 new evaluation records. The `evaluations_index` now has two rows per generation (one per grader version). Aggregation queries must always filter by `grader_version` or you'll conflate scores from different graders. Make this a required filter in the query API.

**LLM-judge non-determinism.** If the grader is an LLM, the same generation can get different scores from the same grader version. Store the judge's full response (prompt + completion) in the evaluation record, not just the extracted score. This makes disagreement auditable and lets you compute judge variance across repeated evaluations.

**Retention.** Generations are the expensive artifacts. If you have a policy to purge old runs, purge the *run metadata* but keep the content-addressed blobs (they may be shared with other runs). Use reference counting or a GC pass that checks whether any surviving run references a `gen_hash` before deleting the blob.
