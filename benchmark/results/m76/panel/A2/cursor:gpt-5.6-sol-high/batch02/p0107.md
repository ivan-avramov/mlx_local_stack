## Response A
# HTTP API for a Single-Host GPU Job Queue

## 1. Resource naming

URI-versioned, noun-oriented resources. Jobs are the only first-class entity; everything else hangs off them.

```
POST   /v1/jobs                        submit a job
GET    /v1/jobs/{id}                   fetch job
GET    /v1/jobs?status=&after=&limit=  list (cursor-paginated)
POST   /v1/jobs/{id}/cancel            cancel
GET    /v1/jobs/{id}/events?cursor=    state-transition log
GET    /v1/jobs/{id}/logs?cursor=      output log (SSE stream)
GET    /v1/jobs/{id}/artifacts         signed download URLs
GET    /v1/capacity                    queue depth, GPU state
GET    /v1/health                      liveness/readiness
```

- Job IDs are server-generated **ULIDs** — sortable, URL-safe, and safe to embed in URLs/paths without escaping.
- Artifacts are never streamed through the API; the artifacts endpoint returns short-lived signed URLs. The API server stays a thin control plane; bulk bytes go client↔object storage.
- Actions (`cancel`) are verbs on sub-resources, not `DELETE /jobs/{id}` — cancelling is a state transition with side effects (process kill, GPU drain), not resource deletion. Jobs are immutable records and are never deleted.

Job object:

```json
{
  "id": "01J9ZK8Q3M2XV4R7T6W5P3N0AB",
  "status": "queued",
  "queue_position": 3,
  "created_at": "2025-01-14T09:00:00Z",
  "queued_at": "2025-01-14T09:00:00Z",
  "started_at": null,
  "finished_at": null,
  "spec": { "command": "train.py --epochs 10", "inputs": ["s3://data/train.parquet"],
            "timeout_seconds": 3600, "gpu": "any" },
  "exit": null,
  "artifacts": []
}
```

## 2. Lifecycle and state machine

```
                 ┌────────────► cancelled  (preempted before start)
                 │
            ┌────┴────┐   admit    ┌─────────┐
            │  queued │───────────►│ running │
            └────┬────┘            └──┬───┬──┘
                 │ TTL expires        │   │
                 ▼                    │   ├──► succeeded
             expired                  │   ├──► failed
                                      │   └──► cancelling ──► cancelled
```

- **Terminal states:** `succeeded`, `failed`, `cancelled`, `expired`. Terminal is forever; no retry/resume transitions (resubmit = new job).
- **`cancelling` is a real, observable state**, not a lie: killing a GPU process and reaping VRAM takes time. Clients polling during this window see `cancelling` and know the job is dead but not yet cleaned up.
- Every transition appends to `/events` with a server timestamp and reason (e.g. `{"type":"state_changed","to":"failed","reason":"exit_code=1"}`), so a client that missed a transition can reconstruct history.
- Jobs carry all four timestamps, letting clients compute wait time vs. run time — the two numbers that matter for a single-GPU queue.

## 3. Idempotency

- `POST /v1/jobs` accepts an `Idempotency-Key` header (client-generated UUIDv4). The server stores `key → {status, response body}` for 24h.
- First call: `202 Accepted` + job object. Replay: the **stored response verbatim**, including the original status code and body.
- Same key with a *different* request body → `409 Conflict` with the original job ID. This catches the classic bug of regenerating a key per retry.
- Optional `client_ref` field in the spec for client-side dedup and correlation; the server never dedups on it automatically.

## 4. Cancellation semantics

`POST /v1/jobs/{id}/cancel` with optional body `{"grace_seconds": 30}` (default 30, max 300).

- **Queued job:** removed from queue, status → `cancelled`. Reliable and immediate.
- **Running job:** status → `cancelling`; scheduler sends SIGTERM to the process group, waits `grace_seconds`, then SIGKILL, then verifies GPU memory is actually released before admitting the next job (on a single host, leaked VRAM is the real failure mode). Status → `cancelled`.
- **Idempotent and forgiving:** cancelling an already-terminal job returns `200` with the current state. Clients must read `status`, never infer "it's cancelled now" from a 2xx. This makes retry loops trivially safe.
- Documented guarantee: *eventual* cancellation. A job is guaranteed dead within `grace_seconds + kill_timeout`; the API never promises a particular wall-clock deadline.

## 5. Back-pressure

A single GPU host has exactly one admission point, so the queue is **bounded** (e.g., 1,000 jobs):

- Queue full → `429` with `Retry-After` (estimated wait, derived from current queue depth and average job duration) and `X-Queue-Position`.
- `GET /v1/capacity` exposes `queue_depth`, `queue_limit`, `gpu: {utilization, reserved_memory, free_memory}`, and `admitting: true|false` for clients that want to check before submitting.
- Queued jobs have a **TTL** (default 24h) → `expired`, so a crashed client can't pin queue slots forever.

The 429 path is the load shedder: clients with many jobs to run should check capacity or honor `Retry-After` instead of hammering submit.

## 6. Observability

- **Polling:** `GET /jobs/{id}` returns an `ETag`; clients send `If-None-Match` and get `304` while nothing changed. Cheap, works everywhere.
- **Streaming:** `/logs` is **SSE** with a `cursor` parameter for resume-after-reconnect. `/events` is the same pattern for state changes.
- **Webhooks (opt-in):** client registers a callback URL; server POSTs the terminal job object. Best-effort with retries — explicitly documented as a *notification*, not a delivery guarantee. Clients must still poll or fetch the job before acting.
- Every response carries `X-Request-Id`; the job object and all events reference it, so support/debugging traces connect.
- Internal metrics (queue depth, wait-time histogram, cancellation latency, VRAM leak detection) are exposed at `/v1/metrics` in Prometheus text format.

## 7. Versioning

- **URI prefix:** `/v1/`. Additive changes (new optional fields, new endpoints, new status values documented as "may appear") are free within a version. Breaking changes (renamed fields, changed semantics, removed states) require `/v2/`.
- Old versions are sunset with `Deprecation` + `Sunset` headers and a documented EOL date, not silent removal.
- Clients are told to ignore unknown fields and treat unknown `status` values as "poll again" — forward-compatible by contract.

## Tradeoffs rejected

| Rejected | In favor of | Why |
|---|---|---|
| **Unbounded queue** (accept everything, `202`) | Bounded queue + `429`/`Retry-After` | With one GPU, an unbounded queue silently accumulates multi-hour waits and pins input data; clients get zero signal. Explicit rejection is honest back-pressure. |
| **WebSockets for logs** | SSE | SSE survives proxies/LBs that drop long-lived WS connections, has built-in auto-reconnect, and is resumable via cursor. WS buys nothing here and breaks behind more infrastructure. |
| **gRPC streaming** | HTTP + SSE | Public API: curl-ability, browser-friendliness, and trivially debuggability matter more than framing efficiency. |
| **Idempotency key in the request body** | `Idempotency-Key` header | The spec body may be hashed for caching/dedup; mixing transport concerns into it makes that ambiguous. Header keeps the spec canonical. |
| **Webhooks as the primary notification** | Poll-with-ETag + SSE, webhooks opt-in | Clients with flaky public endpoints would lose terminal-state notifications permanently. Make the pull path the source of truth; push is a convenience. |
| **`409` when cancelling a terminal job** | `200` no-op with current state | 409 forces clients into error-handling branches for the common "I cancelled twice" retry case. No-op + read-status is strictly friendlier. |
| **`DELETE /jobs/{id}` for cancellation** | `POST /cancel` sub-resource | DELETE implies the record vanishes; jobs are audit records. Also DELETE has no body, so no `grace_seconds`. |
| **Streaming artifact bytes through the API** | Signed URLs | The API server becomes a bandwidth bottleneck and a DDoS surface; bulk transfer belongs in object storage. |
| **`Accept: application/vnd.api.v2+json` header versioning** | URI prefix | URI versioning is visible in logs, bookmarks, and error messages; header versioning hides the version from anyone reading a trace. |
| **Multi-tenant GPU sharing (MIG/MPS) in v1** | One job = whole GPU | Sharing multiplies the security and isolation surface (VRAM escapes, side channels) for a single-host service. `gpu: "any"` is a reserved field so v2 can introduce it without breaking. |

The one design bet worth flagging: this API optimizes for **dumb, retrying clients over unreliable networks** — idempotent submit, idempotent cancel, resumable streams, ETag polling — and treats everything push-based as best-effort sugar. For a long-running job service, that bias pays off more than any single clever feature.

## Response B
# GPU Job Queue — Public HTTP API Design

## 1. Resource naming

Shallow REST, one level of nesting max. All resources live under `/v1`.

| Resource | Path | Meaning |
|---|---|---|
| Jobs | `/v1/jobs` | The queue of work |
| Job | `/v1/jobs/{job_id}` | One unit of work + its lifecycle record |
| Job logs | `/v1/jobs/{job_id}/logs` | stdout/stderr, offset-paginated |
| Job events | `/v1/jobs/{job_id}/events` | SSE stream of state transitions |
| Job artifacts | `/v1/jobs/{job_id}/artifacts` | Output files, listed/downloaded |
| Queue | `/v1/queue` | Depth, wait times, admission state |
| Host | `/v1/host` | GPU health, current job, utilization |
| Health | `/v1/healthz`, `/v1/readyz` | Liveness / readiness |

**IDs:** ULIDs for `job_id` — unique, sortable by creation time (so `GET /v1/jobs?order=created` is trivial and list cursors are stable), and safe to embed in URLs. Client-supplied `external_id` (opaque string) is stored for correlation with the caller's own systems.

## 2. Job lifecycle & state machine

```
                 ┌────────────┐
   POST /jobs →  │   queued   │
                 └──┬───┬───┬─┘
        scheduler   │   │   │ queue TTL expires
                    │   │   ▼
                    │   │ timed_out
                    ▼   │
              ┌────────┐│
              │ running││
              └─┬─┬─┬──┘│
     succeed    │ │ │   │
                ▼ ▼ ▼   │
          succeeded failed cancelled
```

States: `queued → running → {succeeded | failed | cancelled | timed_out}`. The four terminal states are permanent; there is no server-side retry.

Key design points:

- **`cancel_requested` is a flag, not a state.** A running job that has received a cancel signal is still `running` until the worker acknowledges. The job object carries `cancel_requested_at` so clients can distinguish "cancel accepted, worker still draining" from "cancel ignored."
- **`timed_out` is distinct from `failed`.** Exceeding `deadline_seconds` is a policy outcome, not a program error; clients retry logic should treat them differently.
- **Timestamps are first-class:** `created_at`, `queued_at`, `started_at`, `finished_at`. On a single GPU, `started_at - queued_at` *is* the wait time — clients can compute queue latency without a separate metric.
- **Retries are the client's job.** The API returns `failed` with a structured `error {code, message}`; the client decides whether to resubmit. This keeps the state machine acyclic.

## 3. Idempotency

`POST /v1/jobs` accepts an `Idempotency-Key` header (client-generated UUID).

- First request with a key → `201 Created`, key bound to the new `job_id` for a 24h TTL.
- Retry with the same key → `200 OK` returning the **original** job object, no new job enqueued.
- Missing key → the request is processed once but not deduplicated; the client is on its own.

The job object is returned synchronously with `201` — creation is durable before the response, so a client that times out mid-POST and retries with the same key gets a consistent answer.

## 4. Cancellation semantics

```
POST /v1/jobs/{job_id}/cancel
→ 200 { "state": "queued", "cancel_requested_at": "..." }
```

- **Always `200`, never `409`.** Cancellation is idempotent: cancelling a `succeeded` job returns 200 with the current terminal state. Clients can fire-and-forget.
- **From `queued`:** the job is removed from the queue and transitions to `cancelled` immediately (worker never sees it).
- **From `running`:** the server sends SIGTERM to the worker process, waits up to `cancellation_grace_seconds` (default 30s, settable at submission), then SIGKILL. State becomes `cancelled` when the worker acks or is killed.
- **Why not `DELETE /v1/jobs/{id}`?** DELETE implies resource removal; the job record is retained for observability and audit. Cancel is a state transition, so it's a POST to a sub-resource — and it's safe/repeatable, which DELETE semantics would not promise.

## 5. Back-pressure

A single GPU means exactly one job runs at a time, so the queue is the only admission control surface.

- **Bounded queue.** `max_queue_depth` (e.g., 100). When full, `POST /v1/jobs` returns **`429 Too Many Requests`** with `Retry-After` (server-computed from the current job's remaining ETA and average job duration) and the current `queue_depth`.
- **Queue TTL.** Queued jobs expire after `queue_ttl_seconds` → `timed_out`. This guarantees the queue drains even if all queued jobs are stale or the caller vanished.
- **`GET /v1/queue`** exposes `depth`, `admitting` (bool), and `estimated_wait_seconds` so well-behaved clients can throttle themselves before hitting 429.

## 6. Observability

- **Job object** carries the full timeline (section 2), `error` on failure, and client-supplied `metadata` (free-form, echoed back, indexed for `GET /v1/jobs?metadata[k]=v`).
- **Logs:** `GET /v1/jobs/{id}/logs?offset=N&max_bytes=...` — byte-offset pagination, no re-download.
- **Events:** `GET /v1/jobs/{id}/events` is a Server-Sent Events stream of state transitions. Clients that can't do SSE just poll `GET /v1/jobs/{id}`; the API is polling-first, SSE is an optimization.
- **Host:** `GET /v1/host` reports GPU health, the currently-running job's id/age, and utilization — this is how a client answers "why is my job waiting?"
- **Operator-facing** (not part of the public contract): Prometheus `/metrics` with queue depth, wait-time histogram, state-transition counters, and GPU utilization.

## 7. Versioning

- **URI versioning:** `/v1/...`. Breaking changes (removed fields, changed semantics) ship as `/v2/`. Additive changes (new fields, new endpoints) are allowed within a version; clients must ignore unknown fields.
- **Deprecation:** retired versions return `200` for a sunset window with `Sunset` and `Deprecation` headers, then `410 Gone`.
- No `Accept`-header negotiation — content type is always `application/json`.

## Tradeoffs I rejected

| Rejected | Why |
|---|---|
| **WebSockets for live updates** | Public API behind arbitrary proxies/CDNs; auth, reconnect, and TLS-termination pain outweigh the benefit. SSE gives 90% of the value over plain HTTP. |
| **DELETE for cancellation** | DELETE semantics are ambiguous about whether the record persists; cancel is a state transition and must be idempotent and auditable. |
| **Priority queue** | With one GPU, priorities cause starvation and priority inversion without any throughput win. FIFO + bounded depth is predictable; priority can be added in v2 if demand shows up. |
| **Payload-hash idempotency** (auto-dedupe identical submissions) | It silently swallows *legitimate* re-runs (same input, want a fresh run). Explicit `Idempotency-Key` puts the decision with the client. |
| **`Accept: application/vnd.api.v2+json` versioning** | Harder to cache, harder to debug, and most HTTP clients/proxies mishandle it. URI versions are boring and work everywhere. |
| **Server-side retries** | Makes the state machine cyclic (`failed → queued`) and hides failure signals from the client. The client knows its own retry policy; the server reports `error.code` and stays out of it. |
| **Webhooks** | Delivery reliability, callback authentication, and replay are a whole subsystem. Polling + SSE covers v1; webhooks are a plausible v2 addition. |
| **`202 Accepted` for job creation** | The job is durably queued *before* the response, so `201` is truthful. `202` would suggest the client must poll to learn whether the job even exists. |
| **gRPC** | Public API consumed by scripts, CI systems, and non-Go/Java clients; REST+JSON has zero friction. gRPC could be offered as an internal/SDK transport later. |
| **Multi-GPU sharding** | Out of scope by the single-host constraint — but the design (queue depth, host endpoint, job timeline) degrades gracefully: a fleet version is just N hosts each exposing `/v1/host` behind a dispatcher. |

The one structural bet worth flagging: **the job record is the source of truth for everything** — state, timing, errors, logs, artifacts all hang off it. That's what makes polling sufficient, makes cancellation idempotent, and makes observability a read of the same object clients already fetch.
