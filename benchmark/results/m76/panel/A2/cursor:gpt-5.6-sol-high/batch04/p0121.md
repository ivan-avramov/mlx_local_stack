## Response A
# Local Model-Serving Router — Architecture

## The core problem

You have one device, one model resident at a time. Everything reduces to **time-sharing a single GPU with two traffic classes that have opposite latency tolerances**:

- **Interactive** (daily-driver): human at the keyboard. Cares about time-to-first-token (TTFT) and inter-token latency. Abandons after a few seconds. Can be interrupted by the user. **Latency-sensitive, low-volume.**
- **Benchmark**: unattended. Cares about throughput and completion. Tolerates queuing and preemption. **Throughput-oriented, bursty, preemptible.**

The router is therefore not a load balancer — it's a **scheduler + model lifecycle manager + memory accountant** running a single control loop. The dominant cost in the whole system is the **model swap** (unload weights → load new weights), which is seconds-to-minutes and dwarfs everything else. Nearly every policy below exists to *minimize and predict swaps*.

```
                    ┌─────────────────────────────────────────────┐
                    │                ROUTER                       │
  interactive ─────►│  ┌──────────┐   ┌──────────────┐            │
  (SSE/stream)      │  │ Admission│──►│  Scheduler   │            │
                    │  │  Control │   │ (priority +  │            │
  benchmark ───────►│  │ (classify│   │  preemption) │            │
  (queue/deadline)  │  │  accept) │   └──────┬───────┘            │

                    │        ┌───────────────┼───────────────┐    │
                    │        ▼               ▼               ▼    │
```

## 1. Admission control

Every request carries a **class** and a **model id**. Admission does three things:

1. **Classify** — interactive vs benchmark (explicit tag; never infer from client identity).
2. **Fast-path check** — if `requested_model == resident_model`, admit immediately to the serving path. This is the common case and must be near-zero-latency.
3. **Otherwise** — route to the scheduler's queue with the class as priority.

Reject policy: interactive requests are **never rejected** — they queue or trigger a swap. Benchmark requests are **admitted with backpressure**: if the benchmark queue depth exceeds a cap, shed the oldest unstarted benchmark job (it's unattended; it can retry). This protects interactive from a benchmark flood.

---

## 2. Model swap policy (the centerpiece)

Model swap = `unload(M) → load(M')`. Treat it as a **state machine over the resident model**, with **hysteresis** on both edges to prevent thrash.

### Resident state
Exactly one model `M` is loaded in VRAM. The lifecycle manager owns the transition and exposes `RESIDENT = M`.

### Decision table

| Resident | Request for | Action |
|---|---|---|
| `M` | `M` (any class) | Serve immediately (fast path) |
| `M` | `M'` interactive | **Swap** (interactive wins), but see commit rule below |
| `M` | `M'` benchmark | **Queue.** Swap only when interactive has been idle > `idle_cooldown` *and* no interactive is queued |

### The commit rule (avoids the worst failure mode: thrash)

Swapping is expensive, so a *single* interactive turn on a non-resident model is not always worth a swap. Decide with an **expected-dwell heuristic**:

- **Swap now** if `M'` is the user's active/default model, or the user has touched it recently (within a session window). Human intent signals they'll stay.
- **Otherwise** present the user a choice rather than silently stalling: *"Switching to M' — ~Xs to load."* If they confirm, swap; if they cancel, queue. This turns a blind guess into an informed one and keeps TTFT honest.

### Hysteresis parameters (tunable, start here)

- `idle_cooldown` (e.g. 60–120s): benchmark may claim a model only after interactive silence this long.
- `interactive_commit_window` (e.g. 5 min): recent interactive use of `M'` biases toward swapping.
- **Preempt at boundaries, not mid-token.** You cannot cheaply interrupt generation without losing KV. Preempt a benchmark request *after it completes its current request*; never tear down an interactive turn mid-stream.

### Preemption granularity
- **Benchmark**: preemptible at request boundaries. On preemption, optionally **checkpoint its KV to CPU RAM** (see §3) so it resumes without recomputing its prefix.
- **Interactive**: never preempted. It always runs to turn completion.

---

## 3. Session caching (tiered, per-model)

KV cache is **bound to a specific model** — model A's KV is useless to model B. So the session cache is a per-model tiered structure:

| Tier | Where | Holds | Cost to restore |
|---|---|---|---|
| **Hot** | VRAM | KV of sessions on the *resident* model | 0 |
| **Warm** | CPU RAM | KV offloaded when its model swapped out | memcpy + re-paginate |
| **Cold** | none | metadata only (system prompt, summary) | recompute prefix |

Key decisions:

- **Offload to CPU RAM on swap-out.** When the lifecycle manager evicts model `M`, walk its hot sessions and spill KV to system RAM *if* the session is likely to return (interactive sessions, or benchmarks with long prefixes). This is the single biggest win for resume latency.
- **Eviction is LRU with protection.** Active interactive sessions are pinned and never evicted while their model is resident. Warm tier evicts by least-recently-resumed.
- **Metadata always in RAM.** Conversation state, system prompts, summaries are tiny — keep them forever; only KV is the scarce resource.
- **Cap warm tier size** against real CPU RAM; when full, demote to cold (drop KV, keep metadata).

---

## 4. Memory accounting (the VRAM ledger)

Use a **paged KV allocator** (vLLM-style PagedAttention) so KV is allocated in fixed blocks and can be capped, swapped, and evicted — not one giant contiguous tensor that fragments.

Maintain an explicit ledger with named pools, reconciled against the real allocator:

```
VRAM total
├── weights(M)          fixed, known at load time
├── kv_cache            dynamic, grows per token (paged)
│   ├── interactive slice   ← RESERVED, never lent to benchmark
│   └── benchmark slice     ← reclaimable on preemption
├── activations         peak during generation (∝ batch size)
└── headroom            reserved slack (fragmentation + framework)
```

Rules:

- **Reserve an interactive KV slice** that benchmark traffic can never consume. This is what guarantees a human request can always start even under benchmark load.
- **Pre-reserve KV per request** based on `max_tokens`, or admit-and-grow with a hard per-request cap. The failure you're defending against is **OOM mid-generation** when KV grows past free memory — the allocator must reject/evict *before* the kernel faults.
- **Reconcile ledger vs. device** on every allocation and every swap. The ledger is a prediction; the allocator is truth. A divergence is a bug (see §7).

---

## 5. Request cancellation

Three distinct cancellation paths, all must be **idempotent** and must **release every resource they hold** (KV blocks, ledger entries, GPU syncs):

1. **User stop (interactive).** Abort current generation, free its KV, return the partial output. Must be fast and must not block on a GPU sync that the in-flight kernel is waiting on — use a generation flag the loop checks between steps, not a hard interrupt.
2. **Scheduler preemption (benchmark).** Cancel at request boundary; checkpoint KV to CPU (optional) or drop; release ledger; requeue the job.
3. **Timeout / shed (benchmark).** Drop unstarted jobs past the queue cap.

Invariant: **a cancelled request that already allocated KV must release it.** Track allocations per-request-id so cancellation is a clean release, not a leak. This is the most common source of slow memory creep in these systems.

---

## 6. Failure modes to instrument first

Ordered by "what actually breaks first and is hardest to debug":

1. **VRAM OOM / fragmentation.** The #1 killer. Instrument: free VRAM over time, allocator high-water mark, fragmentation ratio, OOM events with the ledger snapshot at the moment. *If the ledger said free but the allocator faulted, you have a reconciliation bug.*
2. **Swap latency distribution.** If loads are slow or variable, the whole design degrades. Instrument: load time, unload time, swap count, and **TTFT-after-swap** (the user-visible cost). A long-tail here means a disk/driver/weights problem.
3. **Stuck / zombie model load.** A load that hangs (driver wedge, corrupt weights, disk stall) bricks the device for everyone. Instrument: a **load timeout** with a forced reset path, and a "stuck-in-load" state metric. This is the failure that turns a router into a dead machine.
4. **Preemption thrash.** Swapping A→B→A→B because hysteresis is too tight. Instrument: swaps/hour, and *wasted load cycles* (loads where the model served < N requests before being evicted).
5. **KV thrashing.** Sessions evicting each other, forcing prefix recompute. Instrument: eviction rate and recompute rate per session. High recompute = warm tier too small.
6. **Interactive latency regression.** Instrument: TTFT p50/p95, inter-token latency, and **abandonment** (requests that get no second turn). This is your ground-truth that the policy is working.
7. **Ledger drift.** Reconcile ledger vs. allocator periodically; alert on divergence. Slow drift = a leak in cancellation or a missed release.
8. **Cancellation deadlock.** Cancel latency and stuck-request count. A cancel that blocks on GPU sync and hangs is a silent wedge.

---

## Summary of the load-bearing decisions

- **Minimize swaps; predict them.** Hysteresis + dwell heuristic + explicit user confirmation for ambiguous interactive swaps.
- **Interactive is protected by construction**: reserved KV slice, never preempted, never rejected.
- **Benchmark is the elastic class**: it queues, it's preempted at boundaries, it's shed under pressure.
- **Offload KV to CPU RAM on swap-out** to make resume cheap.
- **Paged KV + explicit ledger** so memory is capped, evictable, and reconcilable.
- **Instrument OOM, swap latency, and stuck-loads first** — those are the three that take the machine down.

One deliberate relaxation to consider later: if you have VRAM headroom, allow *small* models to co-reside with the large one (the "one large model" constraint doesn't forbid a small resident). That collapses the small-model swap cost to zero and is usually the cheapest latency win available — but the design above holds under the hard single-resident constraint.

# Local Model-Serving Router — Architecture

## The Core Constraint

One GPU (or one VRAM pool), one model resident at a time. Everything else is a consequence of that: every routing decision is really a *swap-or-wait* decision, and every byte of KV cache is a byte you can't give to the next model.

## Component Overview

Everything runs as a single process (or a small supervisor + worker) on the machine. There is no cluster, no sharding. The "router" is a state machine, not a network fabric.

---

## 1. Traffic Classification & Scheduling

Two queues, one slot:

| Class | Queue | Scheduling rule |
|---|---|---|
| **Interactive** | `interactive_q` (priority) | Preempts benchmark. A new interactive request arriving while a benchmark is mid-generation triggers a **preempt-and-swap** decision. |
| **Benchmark** | `benchmark_q` (FIFO, batchable) | Runs only when `interactive_q` is empty **and** the resident model matches the benchmark's target model. Batches of N prompts are admitted together. |

The router is a small finite-state machine:

```
IDLE ──► LOADING(model) ──► SERVING(model) ──► UNLOADING ──► IDLE
                                │
                                ├──► SERVING (next request, same model)
                                │
                                └──► SWAPPING(old→new)  [only if policy allows]
```

A request is admitted only when the router is in `SERVING` with the correct model, or it is queued and the router will transition.

---

## 2. Session Caching

### What is cached

Per `(model_id, session_id)` you store:

- **KV cache** (the dominant cost). For a 70B model at 4-bit, a 4K-context conversation can occupy 1–4 GB of VRAM.
- **Chat template state**: system prompt, tool definitions, tokenized prefix — cheap, keep in RAM.
- **Metadata**: last-active timestamp, token count, model revision hash.

### Tiering

```
Tier 0 – PINNED:   The interactive user's active session. Never evicted
                    while the user is "at the keyboard" (idle < 120 s).
Tier 1 – WARM:     Recently used sessions for the *currently resident* model.
                    LRU, bounded by a KV budget (e.g. 30% of VRAM).
Tier 2 – COLD:     Sessions for a model that is NOT resident. KV is flushed
                    to disk (or discarded). Only the tokenized prefix is kept
                    in RAM so re-prefill is fast.
```

### Invalidation rule

When the router transitions to `SWAPPING`, **all Tier-1 KV for the outgoing model is invalidated immediately**. You do not try to "save" it — the next time that model is loaded, the KV is cold. The tokenized prefix (Tier-2 metadata) survives, so a returning user pays a prefill cost, not a full re-tokenization.

This is the single biggest UX tradeoff in the system. The mitigation is the swap policy below: you try very hard not to evict the interactive user's model.

---

## 3. Model Swap Policy

This is the heart of the router. A swap costs:

- **Unload**: flush KV, free weights, sync GPU memory. ~1–5 s.
- **Load**: mmap / page-in weights, build CUDA graphs. ~5–60 s depending on model size and page cache warmth.
- **Opportunity cost**: every request queued during the swap.

### Decision function

When a request for model **B** arrives while model **A** is resident:

```
if  request.class == interactive
    and  interactive_q is empty
    and  (B == A  →  serve immediately)
    else:
        swap_cost  = estimate_load_time(B) + unload_time(A)
        wait_cost  = expected_interactive_wait_if_we_dont_swap
        if swap_cost < wait_cost * urgency_multiplier:
            → SWAP now (preempt any in-flight benchmark)
        else:
            → queue; serve benchmark to completion first

if  request.class == benchmark:
    → queue; only admitted when interactive_q is empty
    → batch up to max_batch before admitting
```

### Anti-thrash guard

Track a **swap-rate counter** (swaps per 5-minute window). If it exceeds a threshold (e.g., > 4 swaps/5 min), the router enters a **sticky mode**: it will not swap for at least `sticky_ttl` (default 60 s) regardless of incoming traffic. This prevents a benchmark suite that cycles through 8 models from thrashing the interactive user's session.

### Page-cache warmth

Keep the *next* model's weights in the OS page cache (RAM) while the current model is resident. On swap, the load becomes a GPU page-in rather than a disk read, cutting load time by 3–10×. The Memory Governor (below) allocates a fixed RAM budget for this "hot standby" slot.

---

## 4. Request Cancellation

Three distinct cancel paths:

| Trigger | Scope | Mechanism |
|---|---|---|
| **User hits Stop** (interactive) | Single generation | Cooperative: set a `cancel_flag` on the generation task. The inference loop checks it every N tokens (N=4 is cheap). On cancel: stop decoding, free KV for that sequence, return partial output. |
| **Preempt for swap** (router) | All in-flight benchmark generations | Hard: signal the inference engine to finish the current token, abort the rest. KV for benchmark sequences is discarded. Interactive sequences are **never** preempted — the router swaps *between* interactive requests, not mid-generation. |
| **Client disconnect / timeout** | Single request | Same as user-stop, but triggered by the transport layer (SSE connection close, gRPC `Cancel`). |

Implementation detail: the inference engine (llama.cpp, vLLM, etc.) must support **per-sequence abort** within a batch. If it doesn't, you run one sequence at a time in the interactive path and batch only in the benchmark path. This is a real constraint — check your engine.

---

## 5. Memory Accounting

The Memory Governor is a ledger that must answer one question before every admission: **"Can I fit this request without OOM?"**

### Ledger entries (tracked in VRAM)

```
total_vram
  − model_weights        (static, known at load time)
  − cuda_overhead        (~500 MB–1 GB, measured once)
  − kv_cache_used        (sum across active sequences)
  − kv_cache_pinned      (Tier-0 interactive session)
  − activation_scratch   (peak during a forward pass; model-specific)
  = kv_cache_free
```

### Admission rule

A new request with context length `L` is admitted only if:

```
kv_cache_free ≥ kv_per_token(model) × L × safety_margin (1.15)
```

If not, the router either:
- **Truncates** the context (drop oldest turns, re-prefill), or
- **Rejects** with a `503 model_memory_exhausted` and queues the request.

### Swap feasibility check

Before initiating a swap to model B:

```
total_vram ≥ weights(B) + cuda_overhead + min_kv_budget + activation_scratch(B)
```

If the current model's KV usage is so high that unloading it won't free enough space (e.g., a 128K-context session eating 12 GB), the governor forces a **KV flush** before the swap, even for Tier-1 sessions. The interactive Tier-0 session is the last thing flushed.

### RAM side

The page-cache hot-standby for the next model is a fixed allocation (e.g., 25% of RAM). The governor refuses to admit a swap if the next model's weights don't fit in that budget — it falls back to a cold disk load with a longer estimated wait.

## 6. Failure Modes to Instrument First

Ordered by "how often this silently corrupts your day":

### 1. Partial / corrupted model load
**Symptom**: model loads, serves garbage tokens, or crashes mid-generation.
**Instrument**: After every load, run a **canary prompt** (a fixed 32-token prompt with a known expected output). Hash the output. Log `load_duration`, `canary_pass`, `canary_hash`. Alert if canary fails — the model is resident but useless, and the router will keep routing to it.

### 2. VRAM OOM during generation (not at admission)
**Symptom**: CUDA OOM kills the process or the generation mid-stream. The user sees a truncated, non-cancelled response.
**Instrument**: Track `kv_cache_free` at admission vs. at the end of each generation. Log the **peak** KV per sequence. Alert when observed peak exceeds the admission estimate by >10% — your `kv_per_token` constant is wrong for this model.

### 3. Swap deadlock
**Symptom**: Router is in `UNLOADING` but the inference engine won't release memory because a generation is still "in flight" (a zombie task that wasn't cancelled). Router waits forever.
**Instrument**: Every state transition gets a **deadline** (e.g., unload must complete in 10 s). On timeout, log the stuck sequence IDs, force-kill the CUDA context, and recover. Alert on any timeout.

### 4. KV cache thrash / eviction storm
**Symptom**: Tier-1 sessions are evicted and re-prefilled every few minutes. Interactive latency spikes to prefill times.
**Instrument**: Log every eviction with `(session_id, model_id, age, evicted_by)`. Compute an **eviction rate** per model residency window. If eviction rate > threshold, the KV budget is too small or the benchmark batch size is too large.

### 5. Benchmark flooding
**Symptom**: A benchmark suite submits 500 prompts; the router admits them all into `benchmark_q`; an interactive user's request sits behind 400 queued items.
**Instrument**: Track `benchmark_q_depth` and `benchmark_q_wait_p99`. Enforce a **max concurrent benchmark sequences** (e.g., 8) and a **max queue depth** (e.g., 64). Reject excess with backpressure. Alert when interactive wait time > 2 s due to benchmark pressure.

### 6. Silent GPU hang
**Symptom**: Inference loop stops returning tokens. No error, no crash. The SSE stream just… stops.
**Instrument**: A **heartbeat watchdog**: the inference loop must emit a token (or a keep-alive) every `T` seconds (e.g., 30 s for a slow model). If no heartbeat, the router marks the slot `STUCK`, force-kills the CUDA context, and enters `IDLE`. Log the last token timestamp and the stuck request.

### 7. Session cache inconsistency after swap
**Symptom**: User resumes a conversation; the router finds a Tier-2 cached prefix for model A, but model A was loaded from a different checkpoint (user updated the model file). The cached prefix is wrong.
**Instrument**: Every cached session stores a **model content hash** (SHA-256 of the GGUF/Safetensors file, computed at load). On session resume, compare hashes. Mismatch → discard cache, re-prefill. Log every mismatch.

One Prometheus-style metrics endpoint, scraped locally. The metrics that matter:

```

```

The single most useful chart: **interactive first-token latency over time**, overlaid with swap events. If you see latency spikes that correlate with swaps, your swap policy is too aggressive or your hot-standby budget is too small.

## Design Principles That Tie It Together

1. **The interactive user is the system's only real-time constraint.** Everything else — benchmarks, session cache, swap scheduling — exists to not hurt them. When in doubt, serve the human.

2. **Swaps are expensive and rare by design.** The router should aim for < 1 swap per 10 minutes in steady state. The hot-standby page cache and sticky mode exist to make that true.

3. **Every state transition is bounded.** No transition waits indefinitely. Timeouts produce logged, recoverable failures, not hangs.

4. **The memory ledger is the source of truth, not the inference engine.** You don't ask llama.cpp "do you have room?" You compute it from your own ledger and refuse admission before the engine ever sees the request.

5. **Instrument the failure modes that are silent.** OOMs that kill the process are loud. Partial loads, KV inconsistency, and heartbeat misses are quiet and corrupt your day silently. Those get the canary, the content hash, and the watchdog.
