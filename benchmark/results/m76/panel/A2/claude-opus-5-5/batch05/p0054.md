# AI Triage for Radiology: Architecture & PACS Deployment

## 1. Model Architecture

For triage (not diagnosis), the goal is **prioritization and flagging**, so you want a system that's fast, calibrated, and explainable. A practical stack:

### Backbone: Efficient Vision Transformer or CNN
- **ViT-B/16 or Swin-B** for CT/MR, **EfficientNet-B4 or ConvNeXt-T** for X-ray/ultrasound. Transformers give better global context for whole-study triage; ConvNeXt is faster for high-throughput screening.
- For **multi-modal triage** (CT chest + X-ray + clinical metadata), use a **cross-attention fusion head**: encode images with the vision backbone, encode structured data (age, chief complaint, referring physician, order code) with a small MLP, then fuse via cross-attention. This is the pattern in systems like NVIDIA Clara and Aidoc.
- **Output head:** multi-task. One branch → urgency score (e.g., 1–5 triage level or "stat / urgent / routine"). Another branch → binary flags for top-N critical findings (PE, pneumothorax, intracranial hemorrhage, free air, etc.). Use **focal loss** for the rare critical-finding branches (positive rate <2%); standard cross-entropy for the urgency regression.

### Training specifics
- **Data:** 50k–200k+ labeled studies minimum. Source from your own PACS (de-identified) plus public sets (NIH ChestXray, RSNA, CT-RATE, TCIA). Label with radiologist-attended reports parsed via NLP (use a clinical NER model to extract findings from structured/unstructured reports).
- **Augmentation:** intensity perturbation (CT HU noise ±10), small rotations (≤5°), elastic deformation. **Do not** do aggressive geometric augmentation on CT — it corrupts anatomical plausibility.
- **Normalization:** CT → window-specific normalization (lung, mediastinal, bone windows as separate channels or separate models). X-ray → CLAHE + z-score. MR → z-score per slice.
- **Validation:** stratified k-fold by **patient**, not study, to avoid data leakage. Report **AUC, sensitivity at fixed specificity (e.g., 95% spec → what's the recall for critical findings), and calibration (ECE)**. Calibration matters more than raw AUC for triage — a model that says "80% urgent" must actually be urgent 80% of the time.
- **Training infra:** 4×A100 or 8×A100, mixed precision, ~12–24 hrs per epoch on 100k studies. Use **W&B or MLflow** for experiment tracking. Freeze the backbone after epoch 2, fine-tune the fusion head.

```
        │  HL7v2 ORU^RSL / FHIR DiagnosticReport
        ▼
   RIS worklist (reorders queue)
        │
        ▼
   Radiologist sees prioritized queue
```

### PACS-side specifics

- **DICOM conformance:** Your service must implement a **DICOM SCP** (Service Class Provider) that accepts C-STORE. In production, you don't pull from PACS; the VNA or PACS **pushes** new studies to your endpoint via DICOM. Use **pynetdicom** (Python) or **Orthanc** as a lightweight DICOM gateway in front of your inference service.
- **Orthanc as the DICOM shim:** Deploy Orthanc (Docker container) with the **DICOMweb plugin** and a **custom plugin** (C or Python via `pydicom`) that, on `OnStore`, extracts the series, runs inference, and emits an HL7v2 message. Orthanc handles the DICOM protocol, association negotiation, and modality-specific parsing so your ML code only sees numpy arrays.
- **HL7v2 messaging:** When a new study arrives, the RIS sends `ORU^OBS`. Your service responds with `ORU^RSL` containing the triage score. Use **hl7apy** (Python) or **HAPI** (Java). The critical fields: `ORC-1` (order control), `OBX-3` (observation name = "AI_Triage_Urgency"), `OBX-5` (value = "STAT"/"URGENT"/"ROUTINE"), `OBX-11` (value qualifier).
- **FHIR alternative:** If your EMR is FHIR-native (Epic with FHIR API, Cerner), publish results as a `DiagnosticReport` resource with `code` = a LOINC code you register (e.g., 80000-1 for "AI Triage Assessment"). Use `ServiceRequest` for the input. This is cleaner than HL7v2 but not all PACS speak FHIR natively — you'll need a **FHIR-to-DICOM bridge** (e.g., HAPI FHIR + a DICOM gateway).
- **Worklist reordering:** The triage score must actually **reorder the RIS worklist**. This requires a bidirectional interface: your service sends the score → RIS updates queue priority. In Epic, this is the **Epic API** (HL7v2 or FHIR). In Cerner, it's **Cerner Millennium API**. If the RIS doesn't support programmatic reordering, the fallback is to inject a **DICOM SR (Structured Report)** into the PACS that the radiologist sees as a "flag" on the study thumbnail.

### Inference serving

- **Model serving:** TorchServe, Triton Inference Server, or a plain FastAPI + ONNX Runtime. For triage, latency budget is **<2 seconds per study** (not per slice — per entire study). Batch slices within a study; process studies in parallel.
- **GPU:** 1×A10 or T4 per inference node handles ~10–20 studies/min for CT. For a 500-study/day department, 2–3 nodes with autoscaling.
- **DICOM preprocessing in the serving path:** `pydicom` → extract pixel data → resample to model input size (224×224 or 256×256) → normalize → tensor. Do this in a **separate preprocessing microservice** so the GPU node only does forward pass.
- **DICOM SR output:** Generate a **DICOM Structured Report** (content type `1.2.840.10008.5.1.4.1.1.88.34` for findings) with the triage score, flagged findings, and confidence intervals. Store it back in the PACS as a new object linked to the source study via `ReferencedSOPInstanceUID`. This makes the AI output visible in any DICOM viewer.

### Deployment topology (concrete)

```
docker-compose / Kubernetes:
  - orthanc (DICOM gateway, port 4242)
  - triage-api (FastAPI, receives DICOMweb, calls model)
  - triage-model (Triton/TorchServe, GPU, port 8000)
  - hl7-bridge (HL7v2 MLLP listener, port 2575)
  - postgres (audit log, model versioning, feedback loop)
  - prometheus + grafana (latency, throughput, drift monitoring)
```

Run behind the hospital's **DMZ** with a **DICOM firewall** (only allow C-STORE from the VNA's IP). All traffic is DICOM/HL7v2 — no HTTP across the firewall boundary.

## 3. Feedback Loop & Monitoring

- **Radiologist override:** When the radiologist reads a study, capture whether they agreed with the triage level. Store in Postgres. Retrain quarterly.
- **Drift detection:** Track the distribution of triage scores weekly. If the model starts flagging 40% of studies as "urgent" when it used to flag 8%, something's wrong (new scanner, new protocol, data drift). Alert via Grafana.
- **Model versioning:** Pin model versions in the DICOM SR (add a private tag `0009,1001` with the model hash). If a model update changes behavior, you can trace which version scored which study.

## Response B
# AI Triage for Radiology: Architecture, Training, and PACS Deployment

## 1. What "Triage" Actually Means Here

Radiology triage is **not** diagnosis. The model's job is to assign an urgency score (e.g., STAT / urgent / routine / non-urgent) and flag findings that shouldn't wait for the next scheduled read. Think of it as a prioritization layer that sits *in front of* the radiologist's queue, not a replacement for them.

This distinction drives every design decision below: you want high recall on dangerous findings (aneurysms, PE, pneumothorax, free air, fractures) and you accept false positives because a radiologist dismissing a flag costs seconds, while a missed STAT costs lives.

---

## 2. Model Architecture

### Core backbone

For most modalities (chest X-ray, CT, MRI), a **Vision Transformer (ViT-L/14 or ViT-H/14)** or a **swin-transformer** backbone outperforms ResNet-50/101 on fine-grained localization, which matters because triage needs to know *where* the finding is, not just *that* it exists.

A practical architecture:

```
DICOM NIfTI volume (CT) or 2D series (X-ray)
        │
        ▼
  Preprocessing (resample to 1mm³, window/level normalize,
  pad/crop to fixed dims, z-score per study)
        │
        ▼
  ┌─────────────────────────────────┐
  │  Backbone: ViT-L/14 @ 224×224  │   ← 2D slices
  │  OR Swin-V2 @ 224×224          │   ← 2D
  │  OR 3D ViT (ViT-3D, Swin3D)   │   ← volumetric CT/MRI
  │  OR ResNeXt-101 (2D, cheaper)  │   ← X-ray only
  └─────────────────────────────────┘
        │
        ▼
  Multi-task head:
    • Urgency classifier (4-class: STAT/urgent/routine/non-urgent)
    • Finding multi-label head (e.g., 200 ICD-9-CM codes)
    • Attention heatmap (Grad-CAM / attention maps)
    • Confidence / calibration head (temperature scaling)
        │
        ▼
  Fusion: per-slice logits aggregated via
  attention pooling → study-level prediction
```

### Key architectural choices

- **Multi-task, not single-task.** Train urgency classification *and* finding detection jointly. The finding head forces the backbone to learn anatomy and pathology features that transfer to urgency scoring. Use a shared trunk with separate linear heads.
- **Calibration is non-negotiable.** Apply **temperature scaling** (a single learned scalar on logits) or **Platt scaling** on a held-out calibration set. Radiologists will ignore the tool if it says "99% urgent" for routine studies. Report ECE (expected calibration error) < 0.05.
- **Ensemble for the top-risk classes.** For the 5–10 most dangerous findings (PE, aortic dissection, pneumothorax, subdural hematoma, free intraperitoneal air), run a second, more specialized model (e.g., a U-Net-based segmentation model) and combine via a small learned fusion network. This is where most of the clinical value lives.
- **2D vs 3D.** For chest X-ray, 2D is fine and cheap. For CT, use **3D Swin Transformer** or a **2D-slice ensemble with attention pooling** (faster to train, easier to deploy, within ~2% of full 3D on most triage tasks). Full 3D ViT is the gold standard but demands A100/H100-class GPUs for training.

### What to avoid

- Don't use a single ResNet-18 and call it done. You'll get mediocre sensitivity on rare findings.
- Don't skip the attention/heatmap output. Radiologists need to see *why* the model flagged a study, and regulators (FDA, MHRA, CE) will ask for it.

---

## 3. Training Pipeline

### Data

- **Source:** Your own PACS archive (de-identified) + public datasets (NIH ChestX-ray14, RSNA, CT-RATE, MIMIC-CXR) as pretraining.
- **Annotation:** Urgency labels come from **radiologist report timestamps** vs. **clinical outcome data** (did the patient go to OR within 2 hrs? did they die?). This is a weakly-supervised signal. For the finding head, you need structured report NLP: run a **MedSpaCy / cTAKES** pipeline over the radiology reports to extract structured findings, then have radiologists adjudicate a subset.
- **Volume:** Aim for ≥ 50k studies for pretraining, ≥ 5k with urgency labels for the triage head. For rare findings (aortic dissection), you'll have hundreds, not thousands — use **focal loss** or **class-balanced sampling**.

### Preprocessing specifics

- **DICOM → NIfTI:** Use `pydicom` + `nibabel`. Resample CT to **1 mm isotropic** with `scipy.ndimage.zoom` or `SimpleITK`. Apply **window/level normalization** (lung window for chest, brain window for head) before feeding the model.
- **X-ray:** Convert to 224×224, apply CLAHE contrast enhancement, z-score normalize.
- **Augmentation:** Random rotation (±15°), elastic deformation, slice dropout (for 3D), intensity perturbation. No horizontal flip for X-ray (laterality matters).

### Training loop

- **Framework:** PyTorch + `torchvision`/`timm` for 2D, `MONAI` for 3D.
- **Optimizer:** AdamW, lr 1e-4 with cosine schedule, 8×A100 or 4×H100 for ~2–4 weeks of training.
- **Loss:** Weighted cross-entropy for urgency + binary cross-entropy with focal weighting for findings + a small KL-divergence term to encourage calibrated outputs.
- **Validation:** 5-fold CV stratified by modality and urgency class. Report **sensitivity at fixed specificity** (e.g., sensitivity at 95% specificity) rather than AUC alone — that's what clinicians care about.
- **External validation:** Test on a held-out institution's PACS to measure domain shift. Expect a 5–15% drop; this is your real-world number.

## 4. PACS Integration and Deployment

This is where most "radiology AI" projects actually fail. The model is 20% of the work; the integration is 80%.

### DICOM / PACS architecture

```

                                                │  Cerner,    │
                                                │  Meditech)  │
                                                └──────────────┘
```

### Integration pattern (the one that works)

1. **Don't embed the model in the PACS.** That's a nightmare for updates, scaling, and security. Instead, run the model as a **standalone inference service** that the PACS or a PACS-adjacent middleware talks to.

2. **Trigger mechanism:** Subscribe to PACS events. Two options:
   - **DICOMweb polling:** Poll `QIDO-RS` for new studies matching your modality filter every 30–60s. Simple, works everywhere, but adds latency.
   - **DICOMweb subscription / HL7 ORU^R01:** The PACS (or a **VNA**) pushes a notification when a new study is stored. This is the better path. If your PACS doesn't support it, deploy a **DICOM gateway / VNA** (e.g., Orthanc, or a custom `pynetdicom` listener) that receives studies and triggers the AI service.

3. **Retrieval:** On trigger, the AI service fetches the study via **WADO-RS** (Retrieve the DICOM objects, convert to NIfTI in-memory). For large CT studies, this can be 1–5 GB — use **WADO-RS bulkdata** with range requests and stream slices.

4. **Inference:** Run the model, produce:
   - Urgency score + class
   - Top-N findings with bounding boxes / heatmaps
   - Confidence intervals

5. **Return the result:** Push back to the PACS/RIS as:
   - A **DICOM SR (Structured Report)** object stored back into the PACS, so it appears in the radiologist's worklist.
   - An **HL7v2 ORU^R01** or **FHIR DiagnosticReport** sent to the EMR/RIS to update the worklist priority.
   - Optionally, a **FHIR Observation** with the urgency score.

6. **Worklist integration:** The radiologist's PACS workstation (e.g., Agfa IMA X, GE Centricity, Philips IntelliSpace) should show the AI flag as a **worklist badge** — "AI: STAT suspected" — so the radiologist sees it before opening the study. This requires PACS vendor cooperation or a PACS plugin.

### PACS choice / deployment

- **On-prem PACS:** Orthanc (open-source, Python/JS plugins, DICOMweb built-in) is the most developer-friendly. For enterprise, you're stuck with Agfa/GE/Philips and their plugin APIs.
- **Cloud PACS:** AWS HealthImaging, Azure Health Data Services, or Google Cloud DICOM. These give you DICOMweb natively and make the AI service a Lambda/Cloud Run function that triggers on new studies.
- **Hybrid (most common in hospitals):** PACS on-prem, AI service in a VPC or on-prem GPU server, connected via a DICOM gateway.

### Inference serving

- **Framework:** `Triton Inference Server` (if you want multi-model, GPU batching, dynamic batching) or a plain **FastAPI + TorchScript/ONNX** service for a single model.
- **GPU:** A single **A100 40GB** or **L40S** can serve ~5–15 studies/sec for a ViT-L 2D model. For 3D CT, budget **A100 80GB** and expect ~1–3 studies/sec.
- **Latency budget:** Triage should return within **30–60 seconds** of study completion. For true STAT detection (e.g., a trauma CT), you want < 15s. Use **dynamic batching** and **TensorRT** (if NVIDIA) or **ONNX Runtime** for 1.5–3× speedup.
- **Scaling:** Auto-scale GPU nodes based on the DICOM event queue depth. Keep a warm pool of 1–2 GPUs so the first study after idle doesn't pay cold-start latency.

### Security and compliance

- **HIPAA / GDPR:** All DICOM traffic must be TLS 1.3. De-identify at the DICOM gateway (strip PHI tags per DICOM PS3.18 Annex E) before data hits the AI service. The AI service should never see patient names, MRNs, DOBs.
- **Audit trail:** Log every inference (study UID, timestamp, prediction, latency) to an immutable audit log. FDA/CE reviewers will ask.
- **Model versioning:** Track model version with every prediction. Store in the DICOM SR report.

## 5. Regulatory and Validation

- **FDA (US):** This is a **Class II SaMD** device. You'll need a 510(k) submission. The triage/decision-support framing (not diagnostic) helps, but you still need:
  - A **clinical validation study** at ≥ 2 external sites.
  - **Real-world performance metrics**: sensitivity/specificity by urgency class, false-alarm rate per 100 studies, time-to-read reduction.
  - **Change control** documentation for every model update.
- **CE (EU):** MDR Class IIa. Similar clinical evaluation requirements.
- **In practice:** Most hospitals deploy these as **clinical decision support (CDS)** tools first, not as FDA-cleared devices. This lets you iterate faster. The AI output is advisory; the radiologist makes the call.
