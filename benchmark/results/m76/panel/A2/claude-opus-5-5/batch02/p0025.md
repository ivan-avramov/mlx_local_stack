## Response A
# Critique and Redesign of "Effective Context Length"

## Problems with the Proposed Metric

The definition—"the longest context at which a model still answers a retrieval question correctly"—has several structural flaws that make it misleading or unusable.

**1. A single point, not a curve.** By construction you get one number. But degradation is almost never a cliff. A model that is 99 % accurate at 8 K tokens and 40 % at 32 K tokens has a very different operational profile from one that is 99 % at 28 K and 5 % at 29 K. Collapsing both into a threshold erases the slope, which is the quantity practitioners actually need to plan around.

**2. One question is one Bernoulli trial.** A single retrieval question at a single length gives you one bit. The variance of that bit is enormous; the "longest correct context" will be dominated by whether that particular needle happened to be easy or hard, not by the model's capability. You cannot distinguish a model that is genuinely strong from one that got lucky on the one probe.

**3. It conflates two different failure modes.** A model can fail a retrieval question at length *L* for at least two unrelated reasons:

- **Retrieval failure:** the model cannot attend to or locate the target fact at its position. This is a positional-encoding / attention-span problem.
- **Reasoning failure:** the model *does* attend to the fact but cannot combine it with other facts, or is overwhelmed by distractors, or misparses the question once the context is long. This is a working-memory / composition problem.

A single "correct / incorrect" label at length *L* does not tell you which one happened, so the number is uninterpretable.

**4. Position is uncontrolled.** The well-known "lost-in-the-middle" effect means accuracy depends on *where* the fact sits, not just on total length. A single question tests one position. The "effective context length" you report will silently encode the position of that one needle.

**5. Binary correctness is too coarse.** Partial credit (right entity, wrong attribute; right fact, wrong phrasing) carries information about *how* the model is failing, and discarding it forces a noisy threshold.

**6. No distractor control.** If the surrounding text is topically similar to the needle, retrieval gets harder even at short lengths. The metric as stated does not specify distractor content, so results are not comparable across benchmarks.

---

## A Better Framework: Two Axes, Two Curves

Replace the single scalar with two measurement surfaces, each reported as a curve (or 2-D surface) rather than a threshold.

### Axis 1 — Retrieval Depth

**Question:** *Given a single fact at position p inside a context of length L, can the model extract it?*

**Design:**

- Use a needle-in-a-haystack protocol, but **sweep two variables independently**:
  - **Position p** ∈ {5 %, 15 %, …, 95 %} of the context (captures the lost-in-the-middle curve).
  - **Context length L** ∈ {1 K, 2 K, 4 K, 8 K, 16 K, 32 K, 64 K, …} tokens.
- At each (p, L) cell, run **n ≥ 50 randomized needles** (different facts, different distractor text) to get a stable accuracy estimate with a confidence interval.
- Control distractor content: report at least two conditions—*topically neutral* filler and *topically similar* filler—so you can separate positional degradation from interference.

**Output:** a 2-D surface *accuracy(p, L)*. The practical summary is the **accuracy-vs-length curve at each position**, i.e., a family of curves.

**Threshold semantics (if a single number is required):** report the context length at which accuracy falls below a stated floor (e.g., 95 % or 90 %), **with a bootstrap confidence interval**, and specify the position at which it is measured. Do not report a bare integer.

### Axis 2 — Reasoning Depth

**Question:** *Given k relevant facts scattered across a context of length L, can the model combine them into a correct answer?*

**Design:**

- Place **k facts** at random, non-adjacent positions in a context of length L.
- The question must require **all k facts** (e.g., "What is the sum of the three temperatures mentioned?" or "Of the four people described, which has the longest tenure?"). This forces multi-hop aggregation, not single-fact lookup.
- **Sweep k** ∈ {1, 2, 3, 4, 6, 8, …} and **L** independently.
- At each (k, L) cell, run **n ≥ 30 randomized fact sets**.
- Critically, **hold retrieval fixed**: verify (or design the task so) that each individual fact is retrievable at the chosen L. Then any failure is attributable to the *combination* step, not to a missed needle.

**Output:** a 2-D surface *accuracy(k, L)*. The practical summary is the **accuracy-vs-k curve at each L**, showing how the model's compositional capacity degrades as the number of facts to juggle grows.

**Threshold semantics:** report the maximum k at which accuracy stays above the floor for a given L, again with CIs. Equivalently, report the "reasoning span": the largest L at which the model can still combine k facts, for a fixed k.

### Why the separation matters in practice

| Failure mode | Shows up in | Typical cause |
|---|---|---|
| Can't find fact at position p | Retrieval surface, specific p | Positional-encoding degradation, attention dilution |
| Finds all k facts but combines them wrong | Reasoning surface, high k | Working-memory / composition limits |
| Finds fact but is swamped by distractors | Retrieval surface, similar-distractor condition | Interference, not positional |
| Fine at k=1, collapses at k=4 | Reasoning surface, low L | Multi-hop aggregation, not context span |

A model that scores 97 % on the retrieval surface but drops to 40 % on the reasoning surface at k=4, L=8 K has a very different practical profile from one that scores 70 % on retrieval at L=32 K but 95 % on reasoning at k=4. The old metric would collapse both into one ambiguous number.

---

## Reporting Convention (summary)

1. **Never report a bare integer.** Always report the curve (accuracy vs. length, or vs. k) with confidence intervals.
2. **If a single number is demanded** (for a leaderboard, a product spec), define it explicitly as "the context length at which accuracy ≥ τ across ≥ 95 % of position cells" (retrieval) or "the maximum k at which accuracy ≥ τ for a given L" (reasoning), with τ stated, and include the CI.
3. **Report the slope**, not just the threshold. A linear ramp from 100 %→50 % over 2 K→32 K is operationally very different from a cliff at 12 K.
4. **Report both distractor conditions** for retrieval so readers can see how much of the degradation is positional vs. interference.
5. **Use many trials per cell** (n ≥ 30–50) so the curves are stable; a single trial per cell is not a measurement, it is a coin flip.

This gives you two interpretable, independently diagnosable curves instead of one fragile scalar, and it tells an engineer exactly *why* a model fails at a given length rather than merely *that* it does.

## Response B
# Critique and Redesign of "Effective Context Length"

## The Proposed Metric

> *Effective context length* = the longest context at which the model still answers a retrieval question correctly.

It's a single scalar, derived from a binary outcome, applied to one question type. Almost every design choice in it is the wrong one.

---

## Critique

### 1. A binary threshold discards the curve

"Longest context at which it's correct" is a step function. The model that answers correctly at 8 000 tokens and incorrectly at 8 010 tokens and the model that degrades smoothly from 100 % to 0 % between 4 K and 128 K both get a single number, and the second is far more informative. You throw away the *shape* of degradation—graceful slope vs. cliff vs. "lost-in-the-middle" U-curve—which is exactly the information a practitioner needs.

### 2. One question, one difficulty, one conflation

A "retrieval question" in a long context can require any of:

| Operation | Example |
|---|---|
| Locate a single fact | "What was the company's Q3 revenue?" |
| Aggregate across items | "How many of the 40 invoices are overdue?" |
| Multi-hop chain | "Who reported to the person who signed the contract?" |
| Compare / contrast | "Which of the three proposals best satisfies all constraints?" |

All of these are called "retrieval questions" in the metric, but they stress **retrieval** (attending to the right tokens) and **reasoning** (manipulating what was retrieved) in very different proportions. The metric cannot tell you which one is failing.

### 3. Position is uncontrolled

Lost-in-the-middle effects mean accuracy at 64 K depends on *where* the answer lives. "Longest context at which it's correct" implicitly bakes in one position. A model that nails the first and last 8 K but misses the middle 48 K looks fine on this metric.

### 4. Context composition is uncontrolled

Coherent prose, random token soup, related-but-irrelevant passages, and adversarial distractors all change the effective length. The metric doesn't specify the filler, so results aren't comparable across papers.

### 5. The threshold is a single point on a noisy estimator

With one question you get one bit. With *k* questions you get *k* bits, but "the longest context at which *all* are correct" is dominated by the hardest question, while "the longest context at which *any* is correct" is dominated by the easiest. Neither is the quantity you want.

---

## A Better Framework: Two Axes, Each with a Full Curve

The core idea is to **factor the task into retrieval and reasoning**, measure each on its own axis, and report **curves** (accuracy vs. length) rather than a single threshold.

### Axis A — Retrieval Depth

**Question form.** A single-fact lookup. The context contains exactly one relevant sentence (the "needle"); everything else is controlled filler. The question asks for that fact verbatim or with a trivial paraphrase. Zero reasoning beyond identification.

**What you vary.**

- **Context length** *L* (e.g., 1 K → 256 K, on a log grid).
- **Needle position** *p* ∈ {beginning, 25 %, 50 %, 75 %, end, uniform}.
- **Filler type** (matched-length coherent text, random tokens, topically related distractors).

**What you measure.** Accuracy *A_ret(L, p, filler)*, averaged over many needles and questions at each cell. This is a **2-D surface** (L × p) for each filler type.

**Reporting.** Don't collapse to one number. Report:

- The full accuracy-vs-length curve at each position (or position-averaged).
- The "lost-in-the-middle" gap: A(L, end) − A(L, middle) as a function of L.
- If you must give a single number, define it at an explicit operating point (see Threshold Semantics below).

### Axis B — Reasoning Depth

**Question form.** The relevant information is present, but the question requires *N* reasoning operations: multi-hop chains, aggregation over *N* items, constraint satisfaction across *N* clauses, comparison of *N* candidates.

**The critical design choice: decouple reasoning from retrieval.**

Three complementary designs, ideally all reported:

1. **Fixed-retrieval, varying-reasoning.** Place all *N* relevant facts in a **short, easy-to-retrieve** window (e.g., the first 2 K tokens) and pad the rest of the context with filler. Vary *N* (number of hops / items) independently of *L*. This isolates reasoning: if retrieval is trivial, any failure is reasoning.

2. **Varying-retrieval, fixed-reasoning.** Fix *N* small (e.g., a 2-hop question) and vary *L* and *p* of the premises. This isolates retrieval: the reasoning step is simple, so failures track retrieval difficulty.

3. **Joint grid.** Vary both *L* and *N* on a 2-D grid. This reveals the **interaction**: does retrieval degrade faster when the model also has to reason? (In practice it does—attention budget is shared.)

**What you measure.** Accuracy *A_rsn(L, N, p, filler)*. Again a surface, not a point.

### The Separation in Practice

| Probe | Retrieval load | Reasoning load | Vary |
|---|---|---|---|
| A_ret | High (long context, varied position) | None (1 fact, 0 hops) | L, p |
| A_rsn (design 1) | Low (facts in first 2 K) | High (N hops) | N |
| A_rsn (design 2) | High (long context) | Low (2 hops) | L, p |
| A_rsn (design 3) | High | High | L, N jointly |

A model that scores 0.95 on A_ret at 128 K but 0.30 on A_rsn at 128 K has a **retrieval depth of ~128 K** and a **reasoning depth of ~32 K**. The old metric would have reported "128 K" and hidden the reasoning cliff entirely.

---

## Threshold Semantics

Replace the binary "correct / not correct" gate with a **parametric family of thresholds** applied to the accuracy curves.

### Definition

For a curve *A(L)* (accuracy as a function of context length, with all other axes held at a reference value), define:

$$D(\theta) \;=\; \max\bigl\{L : A(L) \ge \theta\,\cdot\, A_{\text{oracle}}\bigr\}$$

where *A_oracle* is the model's accuracy on the same question at a trivially short context (e.g., 512 tokens). This normalises for question difficulty: a hard question that the model gets right 80 % of the time even at 512 tokens doesn't drag the effective length down to zero.

### Report multiple operating points

| Symbol | Meaning | Typical use |
|---|---|---|
| D(0.95) | 95 % of oracle accuracy | "Safe" operating range |
| D(0.80) | 80 % of oracle | Typical production threshold |
| D(0.50) | 50 % of oracle | "Knee" / cliff point |
| D(0.00) | Chance level | Absolute limit |

Reporting the **vector** *(D(0.95), D(0.80), D(0.50), D(0.00))* for each of retrieval and reasoning gives four numbers per axis—eight total—instead of one. The *spread* between them tells you whether degradation is gradual (all four are close) or cliff-like (D(0.95) ≈ D(0.50)).

### Why relative-to-oracle, not absolute

An absolute threshold (e.g., "accuracy ≥ 0.80") conflates model capability with question difficulty. A question the model can't solve even at 512 tokens would make D(0.80) = 0, which says nothing about context length. Normalising by *A_oracle* removes that confound.

### Statistical hygiene

- Use **many** questions per cell (≥ 20, ideally ≥ 50) and report confidence intervals on *A*, not just point estimates.
- Pre-register the question set; don't select the "longest correct" post-hoc.
- Report the **full curve** in the paper/supplement even if the headline number is a threshold.

---

## Summary of What Changes

| Aspect | Proposed metric | Revised framework |
|---|---|---|
| Output | 1 scalar | 2 curves × 4 thresholds = 8 numbers + full surfaces |
| Task type | "retrieval question" (ambiguous) | Explicit retrieval probe vs. reasoning probe |
| Outcome | Binary correct/incorrect | Accuracy, normalised by oracle |
| Position | Uncontrolled | Explicit axis (beginning / middle / end) |
| Filler | Uncontrolled | Explicit axis (coherent / random / related) |
| Reasoning load | Implicit, confounded | Explicit axis *N* (hops, items) |
| Degradation shape | Invisible | Visible in the curve |

The single most important change is the **factorial design**: by varying retrieval difficulty and reasoning difficulty on separate axes, you turn one uninterpretable number into a map of *where* the model breaks down, which is what actually matters for choosing a model for a given workload.
