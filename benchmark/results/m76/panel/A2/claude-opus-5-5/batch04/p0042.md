# Transfer Study: Laptop Evaluation Methodology → H200 / B200 Deployment

**Document type:** Methodological transfer analysis
**Source platform:** Laptop (assumed: single GPU, 8–32 GB VRAM, FP16/BF16 only, single-stream inference)
**Target platforms:** NVIDIA H200 (Hopper, 141 GB HBM3e, ~4.8 TB/s, FP8-capable) and NVIDIA B200 (Blackwell, 192 GB HBM3e, ~8 TB/s, FP4-capable)
**Audience:** Anyone who will read the laptop-era report and decide what to believe on the new hardware.

---

## 1. The Core Problem

A laptop evaluation produces two entangled kinds of knowledge:

- **Model-and-task knowledge.** "Model X hallucinates citations in legal-domain prompts." "Quantizing to 4-bit collapses multi-step reasoning." "Task Y is near-saturated at 94% for all models tested." These are properties of the model weights, the task, and the evaluation design.
- **Hardware knowledge.** "Model X does not fit in 24 GB at BF16." "Throughput is 3.2 tokens/s." "You must cap context at 4 096 tokens." These are properties of the silicon, the memory subsystem, and the serving stack.

The laptop report, as written for a laptop audience, presents both in the same prose, the same tables, the same narrative arc. A reader who inherits the report for H200/B200 work will, without a transfer study, treat every sentence as equally portable. This document exists to break that entanglement.

---

## 2. Taxonomy of Findings

Every claim in the laptop report belongs to exactly one of four classes. The class determines whether the claim transfers, what conditions it requires, and where it appears in the new report.

| Class | Definition | Transfers to H200/B200? | Example |
|---|---|---|---|
| **A – Mechanism** | A causal explanation about model behavior, task structure, or evaluation design that is independent of compute substrate. | **Yes, as-is.** | "Model X's refusal behavior is triggered by the word 'guarantee' in the prompt, not by the underlying task difficulty." |
| **B – Measurement** | A numerical score or ranking obtained under specific execution conditions (precision, context length, sampling params, batch size). | **Only if conditions match.** Requires re-measurement or an explicit condition-match argument. | "Model X scores 71.3% on Task Y at 4-bit, 4K context, temperature 0.0." |
| **C – Hardware verdict** | A conclusion whose truth depends on a specific memory size, bandwidth, precision support, or parallelism topology. | **No.** Must be discarded and re-derived. | "Model X is infeasible on this laptop; use 4-bit quantization." |
| **D – Methodology artifact** | A property of the evaluation procedure itself: prompt construction, metric definition, sample selection, statistical design. | **Yes, but must be re-validated** on the new hardware to rule out interaction effects. | "The 200-sample evaluation has a 95% CI of ±4.2 points, which is adequate for ranking models within 5 points." |

The critical subtlety is the **B/C boundary**. A score like "71.3%" looks like a model property (Class A) but is actually a measurement under specific execution conditions (Class B). On the laptop, those conditions were forced by hardware (4-bit because the model doesn't fit in BF16; 4K context because the KV cache fills the remaining VRAM). On B200, you can run the same model at FP8 or BF16 with 32K context, and the score will differ. The number is not a model property; it is a *joint property of model × precision × context × hardware*.

---

## 3. What Transfers and Why

### 3.1 Class A – Mechanisms (transfer as-is)

These are the findings that survive the platform change without modification:

- **Error taxonomies and failure modes.** If model X confuses "shall" and "should" in regulatory text, it will do so on B200. The failure is in the weights, not the silicon.
- **Task difficulty ordering.** If Task Y is harder than Task Z for all models tested, that ordering is a property of the tasks and the models, not of the GPU.
- **Prompt sensitivity findings.** "Adding a system prompt that says 'you are a domain expert' improves model X by 6 points on Task W" is a mechanism about how the model processes instructions.
- **Calibration and uncertainty behavior.** Overconfidence patterns, logit distribution shapes (when measured at the same precision), and self-consistency properties.
- **Qualitative behavioral observations.** Refusal triggers, format-following tendencies, verbosity patterns.

**Why these transfer:** They describe the mapping from input to output that the model implements. The mapping is the same weights. The hardware changes the *speed and cost* of executing the mapping, not the mapping itself.

### 3.2 Class D – Methodology (transfers, with re-validation)

- **Metric definitions and prompt templates.** These are design choices, not hardware properties.
- **Statistical design.** Sample sizes, confidence interval calculations, effect-size thresholds.
- **Evaluation validity arguments.** "This metric correlates with human judgment at r = 0.82" transfers, *but* the correlation was measured on laptop-generated outputs. If the new hardware produces different outputs (different precision → different sampling → different outputs), the correlation must be re-verified.

**Re-validation protocol for Class D:** Run the evaluation on H200/B200 at the *same precision and context length* the laptop used. If scores match within CI, the methodology is confirmed. If they diverge, the divergence is a precision/context effect, not a methodology failure, and the methodology still transfers but the scores do not.

---

## 4. What Does Not Transfer and Why

### 4.1 Class C – Hardware verdicts (discard entirely)

Every statement of the following form is void on the new platforms:

- **Capacity verdicts.** "Model X requires 4-bit quantization to fit." On B200's 192 GB, the same model runs at BF16 with room for a 128K KV cache. The verdict is false.
- **Throughput and latency numbers.** "3.2 tokens/s at batch size 1." B200's 8 TB/s bandwidth and FP4 tensor cores will produce a different number by an order of magnitude.
- **Context-length caps.** "We capped context at 4K because the KV cache filled the GPU." The cap was a hardware constraint, not a model limitation.
- **Parallelism and serving decisions.** "We used llama.cpp with single-stream inference." The serving stack choice on a laptop is irrelevant to a multi-GPU H200 node.
- **Quantization necessity.** "We used AWQ 4-bit because GGUF 8-bit didn't fit." The premise (doesn't fit) is gone.
- **Memory-pressure workarounds.** CPU offloading, paged attention with aggressive eviction, model unloading between tasks. These were survival strategies, not evaluation design.

### 4.2 The precision trap (the most dangerous non-transfer)

This is the single most common source of error in this kind of transfer, and it deserves its own subsection.

On the laptop, you ran model X at **4-bit** because BF16 didn't fit. You reported a score of 71.3%. On B200, you run model X at **FP8** (or BF16). The score will be different — typically 1–4 points higher, because 4-bit quantization introduces approximation error in the weights.

**The 71.3% is not a property of model X. It is a property of model X at 4-bit.** Reporting it as "model X scores 71.3%" and then comparing it to a B200 run at FP8 is comparing apples to oranges.

**Rule:** Every score in the laptop report must carry its execution conditions as a mandatory annotation. A score without its precision, context length, and sampling parameters is an uninterpretable number.

## 5. What Must Be Re-Measured

The following quantities must be measured fresh on each target platform. They are not estimates, not extrapolations, not "the laptop number plus a scaling factor."

| Quantity | Why it must be re-measured |
|---|---|
| **Accuracy / task scores** at the *new* precision and context length | Precision and context change the model's outputs. |
| **Memory footprint** (weights + KV cache + activations) | Determines maximum context length, batch size, and whether the model fits at all. |
| **Throughput** (tokens/s) at target batch sizes | Bandwidth and tensor-core throughput differ by 10–20×. |
| **Latency** (time-to-first-token, inter-token latency) | Bounded by different bottlenecks (prefill vs. decode) on different hardware. |
| **Maximum practical context length** | KV cache size in GB is a function of model architecture and hardware memory, not a model property. |
| **Maximum practical batch size** | Memory and compute limits differ. |
| **Quantization sensitivity** | Re-run the precision sweep (BF16 → FP16 → FP8 → FP4 → INT8 → INT4) on the new hardware. The accuracy-vs-precision curve may differ because the quantization algorithm interacts with the hardware's native precision support. |
| **Sampling distribution fidelity** | Verify that the inference engine on the new hardware produces the same token probabilities as the laptop engine at the same precision. Different kernels, different accumulation orders, different rounding. |
| **Statistical variance of scores** | If the new hardware allows larger batch sizes or more samples in the same wall-clock time, the CI width changes. |
| **Multi-GPU behavior** (if applicable) | Tensor parallelism, pipeline parallelism, and expert parallelism introduce new failure modes (load imbalance, communication latency) that have no laptop analog. |

## 7. Re-Measurement Protocol

### 7.1 Condition-matching runs (validate the methodology)

For each model and task, run the evaluation on H200 and B200 **at the exact conditions the laptop used** (same precision, same context length, same sampling parameters, same prompt). Compare scores to the laptop scores.

- If scores agree within CI: the methodology is confirmed. The laptop scores are valid measurements of the model, and the new scores confirm them.
- If scores diverge: the divergence is a **precision or engine effect**, not a methodology failure. Document the divergence. The laptop scores are valid *for the laptop's conditions* but not for the new conditions.

### 7.2 Condition-upgrade runs (measure the new hardware)

Run the evaluation at the **best practical conditions** on each platform (highest precision that fits, longest practical context, appropriate batch size). These are the scores that go into the new report's Section 4.

### 7.3 Precision sweep (characterize quantization sensitivity)

For each model, run at BF16, FP16, FP8 (H200), FP4 (B200), INT8, INT4. Plot accuracy vs. precision. This curve is a **model property** (Class A) and transfers, but the *practical operating point* on each platform is a **hardware verdict** (Class C).

### 7.4 Engine and kernel validation

Before trusting any score, verify that the inference engine on the new hardware produces the same token probabilities as the laptop engine at the same precision and temperature. Run a fixed-seed, temperature-0.0 comparison on a small subset. If the engines disagree, the scores are not comparable and the divergence must be characterized before proceeding.

## Response B
# Transfer Study: Laptop Eval Methodology → H200 / B200 Server Deployment

## 0. Scope and Premise

An evaluation harness was built and executed on a laptop (≈ 16–32 GB system RAM, optional 12–24 GB consumer GPU, CPU-assisted inference, quantized weights, batch size 1, llama.cpp / Ollama / single-process serving). The same harness will be pointed at NVIDIA H200 (141 GB HBM3e, ~989 TFLOPS FP8, 4.8 TB/s HBM) and B200 (192 GB HBM3e, ~2.25 PFLOPS FP8, 8 TB/s HBM) servers running full-precision or FP8 weights through vLLM / TensorRT-LLM.

The central risk this document addresses: **conflating a property of the model with a property of the hardware that happened to run it.** A finding like "Model X fails 12 % of the math benchmark" is a statement about the weights. A finding like "Model X takes 41 s per generation at 4096 tokens" is a statement about the laptop. Both look the same in a results table. The structure below makes them impossible to confuse.

---

## 1. Taxonomy: Mechanisms vs. Verdicts

Every finding in the laptop study is tagged with exactly one of two labels. This tag is mandatory metadata on every row of every results table.

| Tag | Definition | Example |
|---|---|---|
| **MECH** (mechanism) | A property of the model's weights, architecture, or training. Invariant to the device, precision, batch size, and serving stack that produced it. | "The 70B model confuses 'mitochondria' with 'chloroplasts' on 9 of 200 biology items." |
| **VERD** (verdict) | A property of the *execution configuration*: hardware, memory, precision, batch size, kernel, or serving stack. Changes when any of those change. | "The 70B model at Q4_K_M on the laptop produces 3.1 tok/s and OOMs at 16 k context." |

The tag is not a judgment of importance. A VERD finding can be critical *for the laptop deployment* and completely irrelevant to the server deployment. The tag tells the reader **where the finding is anchored**, not whether it matters.

---

## 2. Findings That Transfer (MECH)

These are stable across hardware because they are determined by the weight tensor and the sampling parameters, not by the silicon.

**2.1 Capability and knowledge findings**
- Benchmark scores that measure *what the model knows or can reason about*: MMLU-style accuracy, GSM8K pass-rate, MATH, HumanEval pass@1, IFEval instruction-following scores.
- Qualitative error taxonomies: the *type* of failure (hallucinated citation, arithmetic slip, refusal on benign prompt, format violation) and its frequency.
- Relative rankings: "Model A > Model B on summarisation fidelity" holds so long as both are run at their intended precision (see §4 caveat on near-ties).

**2.2 Prompt- and task-design findings**
- Prompt sensitivity: if a model's answer flips between two phrasings of the same question, that is a weight-level property.
- Rubric calibration: whether a 5-point scoring rubric discriminates between good and bad outputs is a property of the rubric and the model, not the GPU.
- Contamination detection: if a model answers a "should-not-know" item correctly, that is a training-data property.

**2.3 Generation-behaviour findings at fixed sampling parameters**
- Repetition loops, degenerate token sequences, EOS-early / EOS-late tendencies — when measured at the same `temperature`, `top_p`, `max_tokens`, and seed.
- Structured-output compliance (JSON validity rate, schema adherence).

**Caveat that can demote a MECH to a VERD:** if the laptop run used 4-bit quantisation and the server run uses BF16/FP8, the *exact* token sequence can differ, and a borderline item (score 3 vs 4) can flip. The *distribution* of scores transfers; individual borderline items may not. Tag these as **MECH±** and report the confidence interval, not the point estimate.

---

## 3. Findings That Do Not Transfer (VERD)

These are anchored to the laptop's execution configuration and must be discarded or re-derived.

| Laptop finding | Why it does not transfer | What replaces it |
|---|---|---|
| Tokens/sec, time-to-first-token, end-to-end latency | H200/B200 HBM bandwidth and FLOPS differ by 1–2 orders of magnitude | Re-measure on target hardware (§5) |
| "Model X does not fit in 16 GB RAM" | 141 / 192 GB HBM removes the constraint entirely | Re-derive memory budget at target precision |
| Quantisation quality penalty (Q4_K_M vs FP16) | Server runs BF16 or FP8; the Q4 artefacts are gone | Re-evaluate whether FP8 introduces its own (different) artefacts |
| KV-cache ceiling ("truncates at 8 k tokens") | Laptop RAM limits context; server HBM does not | Re-measure effective context ceiling |
| CPU-offload / layer-splitting behaviour | No CPU offload on a single H200/B200 with 141+ GB | N/A — delete from report |
| Batch-size = 1 throughput | Server runs batch 32–256 via vLLM continuous batching | Re-measure at target concurrency |
| Thermal throttling / sustained-load degradation | Laptop fans and TDP limits are absent on a server | Re-measure if sustained-load testing is in scope |
| Inference-engine quirks (llama.cpp GGUF loader, Ollama scheduler) | Server uses vLLM / TensorRT-LLM / TRT-LLM | Re-characterise the serving stack |
| Specific OOM crash patterns | Different allocator, different precision, different memory | Re-test edge cases (longest context, largest batch) |

**Rule of thumb:** if the finding's truth value would change if you swapped the laptop for a different laptop (more RAM, different GPU), it is a VERD. If it would not change, it is a MECH.

---

## 4. The Grey Zone: MECH± (Re-measure to Confirm)

Some findings *should* transfer but sit near a decision boundary where hardware-induced numerical differences can flip them. Treat these as "transfers in expectation, verify in practice":

- **Benchmark scores within ±2 points of a threshold** (e.g., a model scoring 71.8 vs a 72.0 cutoff). BF16 vs Q4 can shift logits enough to flip a few items. Re-run the benchmark on the server; report both numbers side-by-side.
- **Sampling-parameter sensitivity.** A model that is "stable" at `temperature=0` on the laptop may show different degenerate-behaviour frequency at `temperature=0.7` on a different kernel stack. Re-run the sensitivity sweep.
- **Long-context degradation.** If the laptop could only test 4 k context (RAM limit) and the server tests 128 k, the *shape* of the degradation curve transfers, but the *onset point* may not, because the laptop never exercised the regime where it matters.
- **Multi-turn consistency.** Laptop runs were often single-shot. Server evals may use multi-turn sessions with different KV-cache management. Re-measure.

Tag these **MECH±** and include a "confirmation status" column: `confirmed on H200`, `confirmed on B200`, `pending`.

---

## 5. What Must Be Re-Measured on H200 / B200

Even after the MECH/VERD split, the following items have no laptop analogue and must be measured fresh:

1. **Throughput and latency at target concurrency.** TTFT, TPOT (time-per-output-token), throughput (tok/s at batch 1, 16, 64, 256). Report per-model, per-context-length.
2. **Memory utilisation and headroom.** Peak HBM usage vs 141 / 192 GB at the maximum context length and batch size in the eval suite. This determines whether the eval suite even fits.
3. **Precision artefacts at FP8 / BF16.** If the laptop used Q4_K_M, the server's FP8 introduces a *different* quantisation error profile. Run a small calibration set (n=200) comparing BF16 vs FP8 outputs and report the divergence rate.
4. **Tensor-parallel / pipeline-parallel effects** (if the model exceeds one GPU). Multi-GPU communication can introduce numerical non-determinism that changes borderline outputs.
5. **Serving-stack behaviour.** vLLM scheduler effects (continuous batching, preemption), TensorRT-LLM in-flight batching, chunked prefill. These change *which* tokens get generated under load, not just how fast.
6. **Reproducibility.** Run the full eval suite 3× on the server. Report variance. The laptop's single-process, batch-1 runs were more deterministic than a continuous-batching server; the variance profile is a new finding.
7. **Effective context ceiling.** Test at 8 k, 32 k, 64 k, 128 k, 256 k (or the model's trained limit). The laptop probably only covered 2–4 k.

### 6.4 Executive-summary rule

The executive summary contains **only** MECH and MECH± findings, plus a single deployment-readiness sentence drawn from §5. ## 8. Summary of the Transfer Logic

```
Laptop finding
      │
      ├── Property of weights / training / prompt?
      │         YES → [MECH]  → transfers. Cite in capability section.
      │         NO  → [VERD]  → does NOT transfer. Delete or re-measure.
      │
      └── Near a decision boundary where precision
            or numerical path could flip the outcome?
                  YES → [MECH±] → re-measure on server.
                            Report both numbers. Confirm or flag.
```

The entire methodology reduces to one question asked of every finding: **"Would this still be true if I ran it on a different machine?"** If yes, it is a mechanism and it transfers. If no, it is a verdict and it is anchored to the silicon that produced it. The report structure exists to make that question impossible to skip.
