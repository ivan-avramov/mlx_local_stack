# Zed config for the mlx_local_stack

> **Generated file.** `settings.snippet.jsonc` in this folder is generated by `configgen` from `main_models.yaml` — do not hand-edit it. To change a model, its context window, or its capabilities: edit `main_models.yaml`, then run `uv run python -m configgen generate` (regenerates every client config) or `uv run python -m configgen check` (drift guard; also runs at `runserver.sh` startup). This README is the one hand-maintained file in this directory.

Configures the [Zed](https://zed.dev) agent to use this stack's local models:

- **mlx-serve** — multi-model server on `http://localhost:8000/v1`, serving four chat models on demand: `gemma-4-31B-it-qat-6bit` (dense), `gemma-4-26B-A4B-it-OptiQ-4bit` (MoE), `Ornith-1.0-35B-mlx-uniform-4bit`, `Qwen3.6-27B-Opus-Distill-OptiQ-4bit`. Loads **one model at a time**, swaps on demand (~10s cold start).
- **task model** — standalone, always-on server on `http://localhost:8092/v1` (`Qwen2.5-1.5B-Instruct-4bit`), used by aider/opencode for lightweight roles. Zed's generated config doesn't reference it at all: there's no `agent` block (see below), so there's nowhere to pin a commit-message/summary model.

`settings.snippet.jsonc` holds the keys to **merge** into your Zed settings — it is not a standalone file.

## Install

1. Start the stack: `./runserver.sh` (from the repo root); wait for both servers.
2. Open Zed settings: `cmd-,` → **Edit in settings.json**, or edit `~/.config/zed/settings.json` directly.
3. **Merge** the `language_models` key from `settings.snippet.jsonc` into your settings (don't replace the whole file — deep-merge this top-level key). The generated snippet only populates `language_models.openai_compatible.mlx-local`; there's no `agent` block to merge (see Model roles below).
4. **Set an API key for the `mlx-local` provider — REQUIRED, or the models stay hidden.** Zed treats an `openai_compatible` provider as "not configured" until a key is registered, and silently hides its models from the picker (no error shown). mlx-serve ignores the key's value, but Zed needs *a* non-empty one. Add it via the Agent panel's configuration view: Command Palette → **`agent: open configuration`** (or the gear icon in the Agent panel) → find **`mlx-local`** → enter any string, e.g. `not-needed` → confirm. (Confirmed working with `not-needed`.)
5. In the Agent panel, pick one of the four models under the **mlx-local** provider for that session.

> **Symptom if you skip step 4:** the model picker shows only the frontier/hosted models, not the `mlx-local` ones. That's the missing key, not a config error — the `available_models` list won't surface until a key is set.

## Model roles

None generated. Zed's `agent.*` settings (`default_model`, `inline_assistant_model`, `subagent_model`, `commit_message_model`, `thread_summary_model`) exist in Zed's own schema, but `configgen` doesn't emit an `agent` block — the generated snippet is just the four `mlx-local` model registrations. That means every session starts on whatever model Zed already has selected (or the first one you pick), and there's no way here to pin a lighter model to commit-message/summary roles the way aider and opencode do. Pick a model directly in the Agent panel: a gemma if you want snappier tool-calling for routine edits, `Ornith-1.0-35B-mlx-uniform-4bit` or the Qwen3.6 distill for reasoning-heavy work.

If you want Zed's per-role pinning anyway, add an `agent` block yourself in settings.json — it's just not something `configgen generate` will produce or keep in sync for you.

## How this differs from the aider config

| | aider | Zed |
|---|---|---|
| `max_tokens` meaning | n/a (aider uses `max_input_tokens` = window − output) | **full context window** (Zed reserves output itself) |
| Editing mechanism | text diffs (no tools needed) | **tool calls** (the agent edits via function calls) |
| Custom request params | `extra_params` forwards anything (`enable_thinking`, `thinking_budget`, per-model `api_base`) | **not supported** — can't send thinking knobs or per-model base URLs |
| Default model | `openai/Ornith-1.0-35B-mlx-uniform-4bit` (aider edits via diffs, so any model works) | none generated — pick one manually in the Agent panel each session |

## Notes & caveats

- **All models are tool-capable.** mlx-serve auto-infers the tool parser from each model's chat template, so every entry is `tools: true`. `main_models.yaml` doesn't carry `tool_call_parser` overrides at all anymore — they were never a capability gate, and configgen doesn't need one to emit `tools: true`.
- **No `max_tokens` truncation trap here.** Because each entry sets `max_output_tokens`, Zed sends a real cap and mlx-serve won't fall back to its 2048 default (the bug that truncated Qwen in aider).
- **Thinking is bounded, not budgeted.** Zed can't send `thinking_budget`, so any of the four models thinks until it naturally stops, capped only by that entry's `max_output_tokens` (32768 gemma-4-31B-it-qat-6bit / 49152 gemma-4-26B-A4B-it-OptiQ-4bit / 102400 Ornith and the Qwen3.6 distill). `interleaved_reasoning: true` keeps the `<think>` content out of the answer body.
- **Qwen3.6-27B-Opus-Distill-OptiQ-4bit in the agent:** tool support is real, but its thinking + tool-call interaction can stall or loop in some clients. Verify one agent edit completes before relying on it; prefer a gemma for routine agent work.
- **`agent.model_parameters`** can set `temperature`/`top_p` per provider+model if you want, but it's a manual addition — configgen doesn't emit it — and it can't carry the mlx thinking knobs either way.
- **`capabilities` must be complete.** Zed's deserializer requires every field in the `capabilities` object — a partial object fails with e.g. `missing field 'parallel_tool_calls'`. Each entry here sets all four: `tools`, `images`, `parallel_tool_calls`, `prompt_cache_key`. If your Zed version complains about a further missing field, add it to every entry. Older builds used flat `supports_tools` / `supports_images` instead of the nested object.
- **Thinking is DISPLAY-only here, not enabled.** `interleaved_reasoning: true` is set on all four chat models so that *if* reasoning is produced, Zed renders it in a separate pane instead of dumping `<think>` into the answer. **It does NOT turn thinking on.** mlx-serve defaults thinking OFF (`DEFAULT_ENABLE_THINKING=False`) and Zed's `openai_compatible` provider can't send the `enable_thinking` body param — so these models will **not actually think** under Zed until thinking is enabled *server-side* in mlx-serve. (aider and opencode can enable it per-request; Zed and VS Code can't.) See the repo's main_models.yaml / mlx-serve `enable_thinking` discussion.
- **`parallel_tool_calls: true`** on all four models — verified safe: mlx-serve's `process_tool_calls` (`re.findall` over every `<tool_call>` block) returns *all* tool calls the model emits in one turn, so the agent can fan out (e.g. read several files at once). If the model emits only one, you still get one — no downside. `prompt_cache_key: false` because mlx_vlm does its own server-side prefix caching, not client-keyed caching.
