### 10. `instability_flags`'s spread rule divides by `abs(mean - 1.0)` — a mean of exactly 1.0 with a nonzero spread is a silent divide-by-zero-equivalent (no flag)
**Location:** `p475_kv.py:716-719` (`elif max(r) - min(r) > 0.5 * abs(mean - 1.0)`).
**Severity:** minor.
**Problem:** When `mean == 1.0` exactly (e.g., r1 = 0.9, r2 = 1.1, mean = 1.0, spread = 0.2), the `elif` compares `0.2 > 0.5 * 0.0` = `0.2 > 0.0` → True, so it *does* flag. So the divide-by-zero-equivalent is actually fine (the comparison is `>`, not `/`). The real gap: a mean *very close* to 1.0 (e.g., 1.0001) with a tiny spread (e.g., 0.0002) compares `0.0002 > 0.5 * 0.0001` = `0.0002 > 0.00005` → True, flagging a 0.02% spread as unstable. The rule is sensitive near 1.0 — a pair of legs that agree to within measurement noise (ratios 0.9999 and 1.0001) trigger a deciding block, costing ~5 extra hours. No test exercises a near-1.0 mean with a tiny spread.
**Failure scenario:** AF8's b1 and b2 decode ratios vs N16 are 0.9999 and 1.0001 (the two blocks agree to within noise). `mean = 1.0`, `spread = 0.0002`, `0.0002 > 0.0` → flag. The pick schedules a deciding third block (~5 hours of GPU time) for a non-instability. The operator, reading the matrix, sees an "instability flag" for a codec that is actually stable.
**Proposed change:** Add a minimum absolute spread floor (e.g., flag only if `max(r) - min(r) > max(0.05, 0.5 * abs(mean - 1.0))`), so sub-percent noise near 1.0 doesn't trigger a deciding block. Or document that the rule is sensitive near 1.0 and the operator should expect occasional noise-triggered deciding blocks.
