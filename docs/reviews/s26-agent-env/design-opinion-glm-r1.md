# S26 spec review — findings (round 1 of 3)

Material traced against `docs/specs/s26-agent-env.md`, the starting-code diff, `bench/host_env.py.draft`, `bench/p426_wave2.py`, `bench/arm_opencode.py`, `bench/opencode_v2_core.py`, `bench/p426_freeze.py`, `bench/corpus_tg2.py`, `bench/tg2_materialize.py`, `m62/inject_verify.py`.

**F1 — Major (confirmed). Post-leg host-env check is not on the exception path the spec mandates.**
Location: spec §2 ("After every launched leg, on every path that reaches the end of supervision … and any exception raised between the launch and `leg.json`"); draft `p426_wave2.py` `Sequencer.run_leg` post-`classify_leg` insertion.
Problem: The spec requires the post-leg check to run even when an exception is raised between `ops.launch` and the `leg.json` write, then propagate. The draft inserts the check as straight-line code after `classify_leg` (after `supervise` returns), with no `try/finally` around the launch→`leg.json` region. Tracing `run_leg` (`p426_wave2.py:759-789`): `supervise` calls `ops.alive`/`ops.wait`/`atomic_text` (OVERRUN), any of which can raise; `atomic_text(self.wd/pl.LAST_LEG_END,…)` and `classify_leg`'s `planned_slots`/`leg_items_problems` paths can raise `fz.Refusal`/`ValueError`. On any such raise the host-env check is skipped, so a leg that `brew install`-ed and then crashed in supervision is recorded as nothing (no INVALID, no reason) — the exact failure the spec exists to catch. An implementer following the spec literally (as the draft models it) builds the straight-line version and misses the exception path; the spec states the requirement but does not specify the mechanism (a `try/finally` spanning launch→`leg.json`, with the check in `finally` and re-raise).
Scenario: agent runs `brew install openjdk@17` mid-leg; the chain then hits a transport abort that raises out of `supervise`; the leg is never classified, no `leg.json` is written, the run aborts with no host-env signal and no INVALID row — the operator sees a crash, not the host mutation.
Proposed change: specify the post-leg check as a `try/finally` in `run_leg` whose `try` covers from `ops.launch` through the `leg.json` write (and the overrun/classify computation), with the check executed in `finally`; on a `finally`-time difference, write `leg.json` with `state=INVALID`/`reason=host environment changed during the leg: …` (or, if classification itself raised, a minimal INVALID record) and then re-raise the original exception. State explicitly that the pre-existing `Stop`/`Refusal` semantics are preserved (the check logs and propagates).

**F2 — Major (confirmed). Post-leg INVALID keeps the wrong `class`; the spec's "the class an INVALID infrastructure leg gets" is misreadable and the draft mis-implements it.**
Location: spec §2 ("the `class` an INVALID infrastructure leg gets from `classify_leg` today (r1 P5; the implementer names the value it uses)"); draft `run_leg` `cls = dict(cls, state="INVALID", reason=…)` (keeps the original `class`).
Problem: `classify_leg` (`p426_wave2.py:366-405`) returns `class="systemic"` only via its `invalid(reason)` helper; a clean leg returns `class="valid"`, a DNF leg `class="dnf"`. The draft's `dict(cls, state="INVALID", …)` preserves the original `class`, so a host-changed clean leg becomes `state=INVALID, class="valid"` and a host-changed DNF leg becomes `state=INVALID, class="dnf"` — neither is "the class an INVALID infrastructure leg gets" (`"systemic"`). The spec's wording ("the class an INVALID infrastructure leg gets from classify_leg today") is ambiguous: it can be read as "keep whatever class classify_leg returned" (what the draft did) or "set it to `systemic`" (what an infrastructure INVALID actually gets). Downstream the harvest/pair-gate/recheck and any consumer that keys off `class` for INVALID legs (the run files, the dossier `differences`) will see an unprecedented `INVALID/valid` or `INVALID/dnf` combination.
Scenario: a VALID leg that `brew install`s is harvested as `state=INVALID, class=valid`; the pair-gate / recheck / published run files now contain an INVALID leg whose `class` is not `systemic`, breaking any consumer that assumes INVALID⇒`systemic` and mis-labeling the failure as a non-infra DNF.
Proposed change: specify that the post-leg host-env INVALID sets `class="systemic"` (the value `classify_leg`'s `invalid()` uses today), and require the implementer to record that literal in the spec's "names the value it uses" clause. Equivalently: re-run `classify_leg`'s `invalid(reason)` shape rather than `dict(cls, …)`.

**F3 — Major (confirmed). `cmd_positives` after-check is not in a `finally`, and the spec does not define the record's fate when an inject raises.**
Location: spec §2 ("`cmd_positives`: fingerprint before the serving session and after it (in a `finally`, also when an inject raises); a difference adds … to `problems`; the record carries `host_env` … and the verdict FAILs"); draft `cmd_positives` (`p426_wave2.py:197-218`).
Problem: The draft takes `env0` before the `with ops.positives_session(...)`, then runs the after-check as plain code after the `with` (`if env0 is not None: problems += …`). That is not a `finally`: if `positive_inject`/`inject_verify`/the session teardown raises, the after-check is skipped and no FAIL record is written — directly contradicting the spec's "in a `finally`, also when an inject raises." More, the spec says "the record carries `host_env` … and the verdict FAILs," implying a sealed record is still produced on the raise path, but neither the spec nor the draft shows how: `cmd_positives` builds `doc` and calls `ph.write_exclusive(out, doc)` only on the non-exception path (`p426_wave2.py:215-219`). An implementer following the spec literally has no defined structure for "write a FAIL positives record when an inject raised and the host also changed."
Scenario: an inject run raises (transport-timeout from `run_tg2_probe.py`, or `inject_verify` rc nonzero raising); the positives command exits nonzero with no sealed record; the host change that caused or coincided with the failure is never recorded — the C360 goal for the positives is lost exactly when it matters most.
Proposed change: specify a `try/finally` over the whole `with ops.positives_session` body (and the grade loop before it, since `env0` is taken before the session but `positive_grade` can also raise), where the `finally` computes the diff, appends to `problems`, and the outer `try/except` ensures `ph.write_exclusive(out, doc)` runs with `verdict=FAIL` and `host_env=env0` even when an inject raised (capturing the inject's failure into `problems` as well). State whether a session that never opened (e.g. ":8000 already has a listener" `Refusal` from `BoxSeqOps.positives_session`) still owes an after-check (the spec's "after it" implies no session ⇒ no after-check, but "in a finally" implies yes).

**F4 — Major (confirmed). End-of-run host-env check is required by the spec but absent from the draft, and its placement vs `--through` and `main()`'s finally is unspecified.**
Location: spec §2 ("End of run: after the last leg of the command (the `DONE` path), one more check … `sequence.json` records `host_env_after_last_leg` = the diff"); draft `Sequencer.run` (`p426_wave2.py:1214-1226`) and `main` (`p426_wave2.py:1655-1678`).
Problem: The draft `run()` never calls `host_env_problems()` after the leg loop; it only publishes run files and returns. So a literal follower of the draft omits the end-of-run check. The spec requires it but does not pin where: `run()` has two exits — the `--through` early return (`p426_wave2.py:1221-1224`) and the `DONE` return (`1225`). The spec says "the `DONE` path," so `--through` is excluded, but that is not stated. Also `main()` wraps `seq.run()` in a `try/finally` that calls `publish_run_files` again (`1666-1672`); the end-of-run check must run before that finally or its own `Stop(1)` would be masked by the publish-failure path (which forces `rc=4`). An implementer following the spec literally could place the check inside `run()` after the loop (correct) or inside `main()`'s finally (wrong: masked by rc=4, and runs even on `--through`).
Scenario: the last leg finishes clean but mutated the host after its post-leg check (e.g. a daemon wrote to `~/.gradle` after the leg's post-check but before process exit); with no end-of-run check the run reports PASS and publishes, and the mutation is only caught on the next run's pre-launch refusal.
Proposed change: specify the end-of-run check as the last statement of `run()` before the `DONE` return (not in `main()`'s finally), explicitly exclude the `--through` early return, and specify that on a difference it raises `Stop(1)` with the mandated message and writes `host_env_after_last_leg` into `sequence.json` (via `save()`) before raising.

**F5 — Major (confirmed). `GRADLE_USER_HOME` set in `build_env` does not reach the Gradle process; the spec's mechanism is wrong for the stated root cause.**
Location: spec §3 ("`OpencodeArm.build_env` (tg2 only): `env["GRADLE_USER_HOME"] = <folder>` after `check` succeeds"); `OpencodeArm.build_env` (`arm_opencode.py:437-442`); `_opencode_env` (`opencode_v2_core.py:106-129`); `BoxSeqOps.positive_inject` (`p426_wave2.py:1449-1457`).
Problem: The spec puts `GRADLE_USER_HOME` in `OpencodeArm.build_env`. But `build_env` is the opencode *client* spawn env, consumed by the opencode probe — the agent's shell tool then spawns `./gradlew` as a grandchild. Tracing: `positive_inject` runs `run_tg2_probe.py` with `env=pos["ops"].env_base()` (`p426_wave2.py:1456`), NOT `build_env`; the probe spawns opencode via the arm; opencode's shell tool spawns `./gradlew`. `GRADLE_USER_HOME` set in `build_env` would only reach the opencode client, and would be inherited by `./gradlew` only if the shell tool preserves it (opencode's shell does inherit the parent env, so it likely propagates — but this is unverified in the spec and the draft). More critically: the *real* legs (the tg2 chain, `run_tg2_chain.py` → `run_tg2_probe.py`) do not go through `OpencodeArm.build_env` at all — the chain builds its own env via the probe entry's `_opencode_env`. The spec scopes the change to "tg2 only" inside `build_env`, but `build_env`'s `self.tg2` branch is never differentiated today (`arm_opencode.py:437-442` has no `if self.tg2`), and the spec does not say how `build_env` learns it is in a tg2 leg (the arm is constructed with `scaffold="tg2"`, so `self.tg2` is available — but the spec doesn't name that flag). And `positive_inject`'s `env_base()` path bypasses `build_env` entirely, so the positives' own Gradle items (the Java injects) would NOT get `GRADLE_USER_HOME` from this change.
Scenario: implementer adds `env["GRADLE_USER_HOME"]=…` in `build_env` under `if self.tg2`; the tg2 chain legs inherit it into `./gradlew` (maybe), but the tg2 positives' Java inject runs via `positive_inject`→`env_base()` which never calls `build_env`, so the positives still write to the operator's real `~/.gradle` — the exact C361 (2) failure the spec claims to fix, for the very run that found it.
Proposed change: specify the `GRADLE_USER_HOME` injection at the env-construction seam that *all* tg2 Gradle spawns share. Either (a) put it in `_opencode_env` (opencode_v2_core) gated by a new `tg2`/`gradle_home` parameter threaded from both the chain and `positive_inject`, or (b) require both `OpencodeArm.build_env` (chain path) AND `BoxSeqOps.positive_inject`/`env_base()` (positives path) to set it, naming both call sites. The spec must trace and name both paths; the current single `build_env` site does not cover the positives.

**F6 — Major (hypothesis, high confidence). The "JVM ignores `$HOME`" assumption is unverified and the spec's non-goal admits the residual it relies on.**
Location: spec §3 ("the JVM ignores `$HOME`"); spec Non-goals ("hashing contents of existing directories … a change inside an already-present `~/.gradle` is not seen"); `host_env.py.draft` `home_toolchains` only records present/absent for `.gradle`.
Problem: The spec's whole premise for `GRADLE_USER_HOME` is that the JVM ignores `$HOME` on macOS. The designer flags this as an unverified assumption. But `_opencode_env` already sets `HOME=<run_dir>/home` (`opencode_v2_core.py:117`), so the agent's `$HOME` is already a bench-owned scratch dir, not the operator's real home. If the JVM actually honors `$HOME` (the common case on macOS: the JVM reads `user.home` from the system property, which defaults to `~` resolved via the OS, and on macOS the JVM does honor `$HOME` for `user.home` in practice), then the operator's real `~/.gradle` was never at risk from a `$HOME`-set env and the C361 (2) incident's root cause is mis-diagnosed. Conversely if the JVM truly ignores `$HOME`, setting `GRADLE_USER_HOME` is the right fix — but the spec's `home_toolchains` fingerprint only records `.gradle` present/absent under the *real* HOME, so a daemon-created `~/.gradle` (the actual incident) is detected only at creation, not at content change (admitted as a non-goal). The spec thus both (a) rests on an unverified assumption and (b) declares the residual it relies on as a non-goal.
Scenario: the JVM honors `$HOME` (the agent's `$HOME` is already scratch); `GRADLE_USER_HOME` is set but redundant, and the real risk — a Gradle daemon writing into an already-present operator `~/.gradle` because some other path resolved there — is invisible to the fingerprint by the spec's own non-goal, so a repeat of the incident is undetected.
Proposed change: before implementation, verify on the box whether the JVM's `user.home` follows `$HOME` (one `java -XshowSettings:properties` under a custom `$HOME`). If it does, narrow C361 (2) to "set `GRADLE_USER_HOME` for determinism and to survive a future JVM that drops `$HOME`-honoring," and stop claiming the JVM ignores `$HOME`. If it does not, keep the fix but add to the spec that the fingerprint's `home_toolchains` is a presence-only signal and the C361 (2) residual is "content change inside an already-present `~/.gradle`," accepted by the operator.

**F7 — Minor (confirmed). `fingerprint` runs `--version` subprocesses per tool, contradicting the spec's "no subprocess calls" and the cited r1 P3.**
Location: spec §1 ("`fingerprint` … no subprocess calls … (no `--version` call; S26-P9 r1 P3)"); `host_env.py.draft` `_version` runs `subprocess.run([exe, *VERSION_ARGS…])` and `fingerprint` stores `"<realpath> | rc <n>: <first version line>"`.

The draft instead runs `--version`/`-version` for every tool and stores a version string, with no sha256. This is a literal mismatch with the spec interface. Consequence: a fingerprint takes ~14 subprocess spawns per leg (TOOLS has 14 entries) on the critical pre-launch path of every Wave 2 leg and around the positives; a slow/missing `java -version` (the JVM can take seconds) adds latency and a failure mode (`error: TimeoutExpired`) the spec excluded. It also changes the `diff` output (`tool cargo: absent -> /opt/… | rc 0: cargo 1.100.0` in the tests) vs the spec's `tool cargo: absent -> /opt/…`.
Scenario: on a cold box `java -version` takes 2-3 s; with 8 legs × 2 checks plus positives, the fingerprint cost alone is minutes, and a hung `gradle --version` (Gradle can hang on a daemon) times out at 30 s, blocking a launch.
Proposed change: align theContinuing the findings (F7 onward), then closing.

**F9 — Minor (confirmed). `npm_global` is specified but the draft's `listed`/`npm_global` split diverges; spec acceptance references `npm_global` and `bin_dirs` by name but the draft names the seam `listed`.**
Location: spec §1 (`npm_global: {package: version}`; `bin_dirs: for /opt/homebrew/bin and /usr/local/bin`); spec §1 `fingerprint` signature in the spec uses `bin_dirs=…, npm_global=…, files=()`, but the draft signature is `fingerprint(*, path=, cellar=, listed=, home=, run=)` — no `npm_global`, no `files`, no `home` keyword named `home_toolchains`.

Scenario: implementer follows the draft signature; `fingerprint_for_run()` from the spec cannot be implemented (no `files` param); the tg2 `gradle.properties` hash is never recorded, so a prefill that silently changed `gradle.properties` (e.g. an editor) is not detected.
Proposed change: reconcile the signature — add `files=()` and `npm_global`/`bin_dirs` (or rename the spec to match `listed`), and implement the `files` sha256/absent/error semantics in both `fingerprint` and `diff`. Pick one shape and use it in the acceptance tests.

**F13 — Minor (confirmed). `classify_leg` is called before the post-leg host-env check, so an already-INVALID leg (chain rc≠0, no `chain.json`) that also mutated the host keeps the original INVALID reason, not the host-env reason.**
Location: spec §2 ("a difference sets the leg `state: INVALID`, `reason: "host environment changed during the leg: <diff>"`"); draft `run_leg` order: `classify_leg` → overrun adjust → host-env check (`cls = dict(cls, state="INVALID", reason=HOST_ENV_REASON+…)` only `if changed`).
Problem: This is actually fine when `changed` is non-empty (host-env reason wins). But when the leg is already INVALID with a useful reason (e.g. "chain rc 2, status 'finished'") AND the host changed, the draft *replaces* the reason with the host-env reason, losing the original chain-failure reason. The spec says "sets the leg state INVALID, reason: host environment changed during the leg" — it does not say whether to append or replace. An operator debugging a leg that both crashed the chain and mutated the host loses the chain-failure signal.
Scenario: chain exits rc 2 (model transport abort) and the agent had already `brew install`-ed; `leg.json` reason is "host environment changed during the leg: …", hiding the transport abort.
Proposed change: specify whether the host-env reason replaces or prepends to the existing `cls["reason"]`. Recommend prepend: `reason = HOST_ENV_REASON + ": " + diff + " (prior: " + cls["reason"] + ")"` when `cls["state"]` was already INVALID.
