## Findings

**Finding 1 — minor — the frozen suite does not pin the OWUI `excluded_model_ids` order that AC2 v3.1 requires.**
- Location: `review/frozen_stack_test_p476_frozen.py:277-310` (`TestCarrierIds::test_no_carrier_names_a_pruned_entry`).
- Problem: AC2 v3.1 (C229) requires `excluded_model_ids` to be "the surviving non-menu ids followed by the retired ids in `retired_model_ids` order." The frozen test asserts the six pruned ids are present (as a set) and not leaked elsewhere, but never asserts the order. The new `configgen/tests/test_owui.py::test_excluded_model_ids_are_the_surviving_non_menu_ids_then_the_retired_ids_in_registry_order` does pin it, so the overall suite covers the order — but the frozen suite (the spec's acceptance-criteria pinning) has the gap.
- Failure scenario: A future emitter edit reorders `excluded_model_ids` (e.g. sorts, or splices retired ids before surviving) for readability; the frozen suite stays green; the spec's deterministic order is silently lost; a certification byte-diff audit that expects the spec's order, or a downstream consumer relying on retired ids being last, breaks.
- Proposed change: Add a frozen assertion `excluded_model_ids == ["Qwen3.6-27B-Opus-Distill-OptiQ-4bit"] + list(PRUNED_SIX)` so the frozen suite pins AC2's order directly.

**Finding 2 — minor — the frozen `_carrier_model_ids` membership test does not scan bare string elements of JSON arrays.**
- Location: `review/frozen_stack_test_p476_frozen.py:210-244` (`_carrier_model_ids`).
- Problem: The walker extends the stack with list elements but only matches dict keys/values and prefix-tagged tokens; a bare string element of a JSON array is popped and ignored. So `test_every_carrier_id_is_in_registry_or_task_model` would not flag a non-pruned, non-registry id sitting in a bare array of a non-OWUI carrier. The new `test_registry_published_set.py` structural EXTRACTORS do scan arrays, so the overall suite covers it; the frozen suite alone has the blind spot.
- Failure scenario: A future carrier format places a stale or foreign model id in a bare JSON array (not a dict key/value); the frozen membership test passes; only the new structural test catches it — and only while the EXTRACTOR for that target is kept in sync with the carrier format.
- Proposed change: Add `elif isinstance(node, str) and node in known: found.add(node)` to the walker so the frozen membership test is format-agnostic.

**Finding 3 — minor — `FIXTURE_SOURCE = "P476-STACK-COMMIT"` placeholder is not a real commit (spec-letter deviation).**
- Location: `mlx-vlm/mlx_vlm/tests/test_mtp_verify_scan.py:1734`; `mlx-vlm/mlx_vlm/tests/fixtures/stack_registry_golden.yaml:2`.
- Problem: S4 requires the fixture header's source commit to be updated to the real stack S1–S3 commit. The placeholder is a transient marker (the stack commit does not exist yet in this uncommitted candidate). `test_p387_the_fixture_is_the_last_mtp_on_registry` checks `f"stack {FIXTURE_SOURCE}" in header` circularly, so it passes but no longer verifies a real commit. The brief confirms this is "substituted at commit."
- Failure scenario: The fork S4 commit is published with the placeholder still in place; a future reviewer chasing fixture provenance cannot resolve `P476-STACK-COMMIT` to a real stack commit and must trace it by hand.
- Proposed change: Before publishing the fork S4 commit, replace `"P476-STACK-COMMIT"` with the real stack S1–S3 sha in both locations; or add a guard test refusing a non-hex placeholder.

**Finding 4 — minor (judgement: acceptable) — P371 tests mutate tracked carrier files and restore in `finally` (the brief's specific question).**
- Location: `mlx_local_stack/benchmark/bench/tests/test_p371_baseline.py:94-100` and `:587-597`.
- Problem: Two tests write into the live tracked carriers `benchmark/opencode_bench_v2_web.json` and `benchmark/opencode_bench_v2_web_tg1.json` and restore them in `finally`. If the process is killed mid-test (SIGKILL/OOM/crash), `finally` does not run and the carriers are left mutated. The P371 goldens read the pinned overlay (not the live tree), so they would NOT catch the corruption (false green). `configgen check` and the frozen `test_configgen_check_rc_zero` / `test_no_carrier_names_a_pruned_entry` WOULD catch it on the next run — a downstream safety net that depends on the operator running `configgen check` before committing.
- Failure scenario: The test process is OOM-killed after mutating `opencode_bench_v2_web.json` (trailing `\n` appended) but before `finally`; the carrier is left mutated; if the operator commits without re-running `configgen check`, the corrupted carrier ships and the P371 goldens stay green (they read the pin).
- Judgement: **Acceptable.** Each test's purpose requires mutating the live tree — the first proves the bundle ignores the live tree, the second proves the new side reads the live carrier; monkeypatching the reader would defeat the test. On a clean exit `finally` restores, and the full suite confirmed restoration (`configgen check` rc 0 post-run, live carrier sha256 still matches `OVERLAY_SHA256`). The residual gap (kill mid-test) is low-probability and has a downstream safety net.
- Proposed change (non-blocking): Back up originals to a temp file on disk (survives a process kill) instead of an in-memory dict, and/or add a session-level `conftest.py` safety net that restores the two carriers from `git show HEAD:path` if they differ at session end.

**Finding 5 — scope request (no severity) — the P371 bundle overlay is a standing code change beyond S3b's stated regen procedure.**
- Location: `mlx_local_stack/benchmark/bench/tests/p371_baseline/bundle.py:23-35,89-108`.
- Problem: S3b says the P371 goldens are "refreshed by its own procedure (P371: `P371_REGEN_GOLDEN=1`)." The implementer added a *standing* overlay step to `make_bundle` that replaces two archived carriers with pinned post-P476 copies on every bundle build, recorded in the manifest as `overlaid_files`. This is necessary because S3b's analysis only names `probe_code_sha256` (tg1 carrier, re-derived by the TABLE) as moving — but the web carrier also moves `carrier_source_sha256` / `opencode_bench_config_sha256` / `carrier_sha256`, which the compare TABLE does NOT re-derive; without the overlay the differential would fail on those fields after the prune. The round-2 fix made the overlay minimal (only the two carriers the scenarios read) and provenance-honest (manifest + docstring). It is sound, but it is a standing code change the spec does not name.
- Failure scenario: A future maintainer, unaware the overlay is standing, regenerates carriers for a non-P476 change and sees the P371 differential fail on `carrier_source_sha256`; the docstring tells them to refresh the pin, but they must also understand the overlay is permanent (not a one-time regen) — otherwise they may delete it and reintroduce the original failure.
- Proposed change: Either (a) amend S3b to name the standing overlay as the P371 refresh procedure for carrier-derived fields the TABLE does not re-derive; or (b) add the web carrier's `carrier_source_sha256` / `opencode_bench_config_sha256` to the compare TABLE's rederived set and drop the overlay, so the differential absorbs web-carrier drift the same way it absorbs tg1 drift.

**Finding 6 — scope request (no severity) — `load_source` does not validate that `retired_model_ids` are not live models (latent hazard the change introduces).**
- Location: `mlx_local_stack/configgen/source.py:97-103`; `configgen/emitters/owui.py:89`.
- Problem: `load_source` validates `retired_model_ids` is a list of strings but does not reject a retired id that is also a live `models:` entry. The emitter dedups retired ids against the surviving excluded, but a retired id that is in the OWUI menu would also be appended to `excluded_model_ids` (it is not in surviving excluded), producing a policy where the id is both in `main_model_ids` and `excluded_model_ids` — a contradiction `reconcile_models.py` would then flag every saved registration of that now-desired model as stale and refuse `--apply`. The spec S2b does not require this validation; the current registry has no collision.
- Failure scenario: A future edit promotes a retired id back to the menu but leaves it in `retired_model_ids`; `configgen check` passes (no validation); the OWUI policy lists the id in both `main_model_ids` and `excluded_model_ids`; reconcile flags every saved registration of the now-desired model as stale.
- Proposed change: Add a `load_source` check that `set(retired_model_ids).isdisjoint({m.name for m in models} | set(router_only_models))`, refusing a registry that retires a live id.

## What would fail in use

Nothing I found. The serving stack resolves no pruned name from the live registry at runtime (production references in `cycles.py:20`, `aider_adapter.py:11`, `bfcl_adapter.py:47` are comment-only; `model_params.PARAMS` retains the six by operator ruling Q1 and is read by regrading tests against synthetic/fixture registries, not the live one). Every generated client and bench carrier names only the five; the OWUI tombstones keep unmanaged saved registrations of pruned ids flagged stale on every box (and managed ones via the pre-existing `retired` set). Campaign identity / pairing that depends on carrier bytes is consistent: the C147 `OLD_CAMPAIGN_HASH` and the P371 goldens' `carrier_sha256` / `scaffold_policy_sha256` both derive from the same post-P476 tg1 carrier (live for C147, pinned for P371); the two pinned copies are byte-identical to the live carriers, so the differential and the campaign pin agree. The fork's `classify` / `overlay_on` round-trip the pruned live registry against the regenerated fixture, `load_references` passes on the real pruned table, and the served-arm code path stays tested via the synthetic entry. The residual OWUI pre-check (S1b) on boxes that carry saved registrations is an operator workflow step, not a candidate defect.
