## Findings

**Finding 1 — minor — no test pins that `openwebui.retired_model_ids` is exactly the six baseline-pruned names.**
- Location: `mlx_local_stack/benchmark/bench/tests/test_registry_published_set.py:107-130` (`test_live_registry_names_exactly_the_published_entries` pins the five live names against `PUBLISHED`; `configgen/tests/test_owui.py:260-261` `test_load_source_reads_shipped_retired_model_ids` only asserts `len == 6`).
- Problem: The five live names are pinned against an explicit set, and the clash check (`source.py:99-103`) refuses a retired id that names a live model. But nothing asserts the six retired ids ARE the six names removed from the baseline `models:` (an explicit list, or `baseline_models_names − live_models_names`). `len == 6` passes for any six strings; the clash check passes for any six never-published strings. AC1/S2b require the tombstones to be "the six pruned names."
- Failure scenario: a future edit swaps one retired id for a typo (e.g. `gemma-4-31B-it-qat-8bit`); `len == 6` and the clash check both pass; a box with a saved unmanaged registration of the real `gemma-4-31B-it-qat-6bit` is no longer flagged stale after pulling the prune; the S2b invariant is silently lost and the OWUI reconcile dry-run stops listing it.
- Proposed change: add `assert set(retired_model_ids) == {<the six explicit names>}` (mirroring `PUBLISHED`), or `assert set(retired) == baseline_models_names − {live names}` by reading `git show c4faf574:main_models.yaml`.

**Finding 2 — minor — no test verifies the five remaining entries' parsed settings and all top-level keys are byte-identical to the baseline (AC1).**
- Location: `mlx_local_stack/benchmark/bench/tests/test_deployed_profile.py:99-105` (`test_deployed_profile_is_the_registry_block` compares the registry to itself for 3 entries); `test_registry_published_set.py` (no baseline comparison).
- Problem: AC1 requires "parsed settings of every remaining entry and all top-level keys identical to the baseline except the added `openwebui.retired_model_ids`." The candidate's diff is clean deletions plus the one list, but no test pins that against the baseline. `test_deployed_profile_is_the_registry_block` asserts `params_for(name, "deployed", REGISTRY) == registry_generation_defaults(name, REGISTRY)` — the registry compared to itself, so a silent edit to a remaining entry's `generation_defaults`/`max_kv_cache_size`/top-level key passes. Only a few keys are spot-checked (`test_reads_ornith_generation_defaults`, `test_reads_distill_generation_defaults`).
- Failure scenario: a future commit edits a remaining entry's `max_kv_cache_size` or a top-level key (e.g. `mlx_port`) alongside a legitimate change; `configgen check` rc 0 (it regenerates from the current registry); the deployed-profile tests pass (registry == registry); the AC1 "identical to the baseline" invariant is silently lost and a certified tune ships with an unreviewed setting.
- Proposed change: add a test that parses `git show c4faf574:main_models.yaml` and asserts `{k: v for k, v in doc.items() if k != "models"} == baseline` and each remaining entry's parsed dict equals its baseline dict (skippable on shallow clones, like the gemma fixture test).

**Finding 3 — minor — the gemma-fixture verbatim-baseline guard skips on shallow clones, leaving the fixture untethered.**
- Location: `mlx_local_stack/benchmark/bench/tests/test_deployed_profile.py:39-55` (`test_gemma_fixture_is_the_verbatim_baseline_block` `pytest.skip`s when `git show c4faf574` is unavailable).
- Problem: The only test that ties `fixtures/gemma_31b_qat_registry.yaml` to the real baseline `git show`s on git-history availability. In a shallow clone (CI without `--unshallow`), the test skips, so the fixture's verbatim-baseline property is unverified; a future edit to the fixture drifts undetected there.
- Failure scenario: shallow-clone CI skips the test; a maintainer edits the fixture (e.g. bumps `thinking_budget`); the skip masks the drift; `test_deployed_gemma_is_the_daily_driver_not_the_coding_profile` reads the wrong fixture value and passes (it compares the fixture to itself).
- Proposed change: pin the fixture's sha256 to a committed constant and assert it unconditionally (the `git show` check stays as a stronger, skippable guard), so the fixture bytes are always verified.

**Finding 4 — minor (known) — the `P476-STACK-COMMIT` placeholder makes the fork's "last MTP-ON registry" check circular until substitution.**
- Location: `mlx-vlm/mlx_vlm/tests/test_mtp_verify_scan.py:173- Location: `mlx-vlm/mlx_vlm/tests/test_mtp_verify_scan.py:1734` (`FIXTURE_SOURCE = "P476-STACK-COMMIT"`); `:2078` (`assert f"stack {FIXTURE_SOURCE}" in header`); `mlx-vlm/mlx_vlm/tests/fixtures/stack_registry_golden.yaml:2`.
- Problem: S4 requires the fixture header's source commit to be the real stack S1–S3 sha. The placeholder is a transient marker; the test checks `f"stack {FIXTURE_SOURCE}" in header` circularly, so it passes against the placeholder and no longer verifies a real commit. The brief confirms "substituted at commit."
- Failure scenario: the fork S4 commit is published with the placeholder still in place (the substitution is forgotten); a future reviewer chasing fixture provenance cannot resolve `P476-STACK-COMMIT` to a real stack commit and must trace it by hand; the "last MTP-ON registry" claim is unverifiable.
- Proposed change: before publishing the fork S4 commit, replace `"P476-STACK-COMMIT"` with the real stack S1–S3 sha in both locations; or add a guard test refusing a non-hex, non-`P476-STACK-COMMIT` placeholder so the substitution is enforced.

**Finding 5 — scope request (no severity) — the P371 bundle overlay is a standing code change beyond S3b's stated refresh procedure.**
- Location: `mlx_local_stack/benchmark/bench/tests/p371_baseline/bundle.py:23-35,89-108`.
- Problem: S3b says the P371 goldens are "refreshed by its own procedure (P371: `P371_REGEN_GOLDEN=1`)." The implementer added a *standing* overlay step to `make_bundle` that replaces two archived carriers with pinned post-P476 copies on every bundle build, recorded in the manifest as `overlaid_files`. This is necessary because S3b's analysis only names `probe_code_sha256` (tg1, re-derived by the TABLE) as moving — but the web carrier also moves `carrier_source_sha256` / `opencode_bench_config_sha256` / `carrier_sha256`, which the compare TABLE does NOT re-derive; without the overlay the differential would fail on those fields after the prune. It is sound and provenance-honest, but it is a standing code change the spec does not name.
- Failure scenario: a future maintainer, unaware the overlay is permanent, regenerates carriers for a non-P476 change and sees the P371 differential fail on `carrier_source_sha256`; the docstring tells them to refresh the pin, but they must also understand the overlay is standing (not a one-time regen) — otherwise they may delete it and reintroduce the original failure.
- Proposed change: either (a) amend S3b to name the standing overlay as the P371 refresh procedure for the carrier-derived fields the TABLE does not re-derive; or (b) add the web carrier's `carrier_source_sha256` / `opencode_bench_config_sha256` to the compare TABLE's rederived set and drop the overlay, so the differential absorbs web-carrier drift the same way it absorbs tg1 drift.

## What would fail in use

Nothing of substance beyond the above. The serving stack resolves no pruned name from the live registry at runtime (production references in `cycles.py:20`, `aider_adapter.py:11`, `bfcl_adapter.py:47` are comment-only; `model_params.PARAMS` retains the six by operator ruling Q1 and is read against synthetic/fixture registries, not the live one). Every generated client and bench carrier names only the five — verified by shasum for the four bench carriers and by `test_registry_published_set.py` for all configgen outputs; the OWUI policy carries the six tombstones in `excluded_model_ids` (order pinned by `test_shipped_policy_excluded_model_ids_follow_the_registry_order`, consumed as a set by `reconcile_models.py:181`). Campaign identity / pairing that depends on carrier bytes is consistent: the C147 `OLD_CAMPAIGN_HASH` and the P371 goldens' `carrier_sha256` / `scaffold_policy_sha256` both derive from the same post-P476 tg1 carrier; the two P371 pinned copies are byte-identical to the live carriers (`cc76c89f…` / `5673d726…`), and the m59 fixture's `opencode_bench_config_sha256` (`757121d7…`) equals the live `opencode_bench_v2.json`. The fork's `classify` / `overlay_on` round-trip the pruned live registry against the regenerated fixture, `load_references` passes on the real pruned `ENTRIES`, and the served-arm code path stays tested via the synthetic `STATIC` injection. The round-3 hermeticity fix (throwaway clone for the mutation test, `_tree_copy` for the differential test, session-level carrier-sha guard) resolves the round-3 tracked-carrier-mutation finding; the `load_source` clash check resolves the round-3 scope request.
