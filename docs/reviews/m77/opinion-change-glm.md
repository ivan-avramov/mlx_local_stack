## Findings

I traced the served-worker load order (`_initialize_model` → `_resolve_tq4_mode_from_env` → `_apply_attention_policy_from_env` → `_apply_mtp_verify_from_env` → `_apply_tq4_attention_from_env` → drafter load → `require_loaded_mtp_drafter` → the new post-load refusal), the mlx-serve validation order (`_validate_tq4_attention` before `_validate_mtp_verify_scan`), and `process_manager._build_command`. Direct answers to the three sub-questions first:

- **Can any MTP-ON configuration now load without its `joint_v1` protection?** No. `configured_draft_kind == "mtp"` makes `_mtp_off` return `False` in both fork gates, so `require_environment` still requires `mtp_verify_scan == "joint_v1"`, `require_policy_stamps` still requires a `joint_v1` stamp on every module (reached via the sentinel branch — see F1), and `require_loaded_mtp_drafter` still fires after load. The MTP-ON call shape is pinned by `test_load_mtp_with_joint_v1_unchanged` and the implementer's spy test.
- **Can an OFF configuration serve with a drafter or a verify stamp?** No verify stamp can be served: OFF + `joint_v1` env is refused at `_resolve_tq4_mode_from_env` ("joint_v1 requires a drafter"); OFF + `MLX_VLM_MTP_VERIFY_AB=1` is refused inside `_apply_mtp_verify_from_env` (`resolve_policy("per_query", ab=True)` raises → `_mv._fail`); OFF + `per_query`/`""`/unset applies no stamp. No drafter can be served: the post-load check at `generation.py:1703-1712` refuses `tq4_mode is not None and configured_draft_kind in (None, "") and draft_model is not None`. The only drafter-load path that escapes refusal is `drafter_incompat_policy` returning `(None, None)` under `MLX_VLM_DRAFT_ALLOW_FALLBACK=1`, which leaves `draft_model is None` — the mode then serves the intended OFF state with no drafter (F5 below).
- **Does mlx-serve now accept anything the worker refuses, or the reverse?** Under the supported path (config → `_build_command` → env → `_initialize_model`) they are aligned: the OFF success entry validates in mlx-serve and builds an argv with no `--mtp-verify-scan`/`--draft-*`, so the worker sees `configured_draft_kind=None`, scan defaults to `per_query`, ab to `"0"`, and accepts; every mlx-serve refusal (mode + `mtp` without `joint_v1`; mode + no drafter + `joint_v1`; mode + no drafter + `ab`; mode + `suffix`/`dflash`/`eagle3`) is also refused by the worker when forced via env directly. I found no asymmetry in either direction under supported conditions.

### F1 — `_initialize_model` omits `draft_kind` on the MTP-ON apply call (minor, confirmed)
- **Location:** `mlx-vlm/mlx_vlm/server/generation.py:1600-1607` (`_tq4_dk = {} if tq4_mode is None or configured_draft_kind == "mtp" else {"draft_kind": configured_draft_kind}`).
- **Problem:** The spec (Interfaces, `server/generation.py`) states `_apply_tq4_attention_from_env(model, mode, *, draft_kind)` "passes it to `require_policy_stamps`" and that `_initialize_model` "passes the same value to the TQ4 calls". The candidate passes `draft_kind` to the resolve call always, but to the apply call only when `configured_draft_kind` is None/`""` or another kind — when it is `"mtp"` it passes `{}` (sentinel). Behaviour is identical because `_mtp_off(_UNSET) == _mtp_off("mtp") == False`, so both take today's `joint_v1`-stamp branch. The implementer's `test_init_mtp_on_passes_the_m72_calls_unchanged` pins the omission (`calls[2] == ("tq4", "m72_exact", {})`), so it is self-consistent with the implementer's tests but conflicts with the spec's literal wording.
- **Failure scenario:** A hidden acceptance test that asserts `_apply_tq4_attention_from_env` is called with `draft_kind="mtp"` explicitly on the MTP-ON path fails; the frozen `test_load_mtp_with_joint_v1_unchanged` only checks outcome, so it does not surface this either way.
- **Proposed change:** Drop the `configured_draft_kind == "mtp"` special-case in `_tq4_dk` so the apply call always receives `{"draft_kind": configured_draft_kind}`, and update the implementer's spy test to expect `{"draft_kind": "mtp"}`. (If keeping the omission, the spec's "passes the same value" wording should be relaxed instead.)

### F2 — generation helpers default `draft_kind` to a sentinel (minor, confirmed)
- **Location:** `mlx-vlm/mlx_vlm/server/generation.py:204-210` (`_resolve_tq4_mode_from_env(*, kv_bits, kv_quant_scheme, draft_kind=_TQ4_DRAFT_UNSET)`) and `:233` (`_apply_tq4_attention_from_env(model, mode, *, draft_kind=_TQ4_DRAFT_UNSET)`).
- **Problem:** The spec's interface signatures show `draft_kind` as required. The candidate gives both a sentinel default so existing fakes (`test_tq4_impl_wiring.py`'s `tq4(m, mode)` and the `lambda m:` `require_policy_stamps` stub) keep working. This is the ambiguity the test-writer flagged in delivery 1; the sentinel is the mechanism that makes "omitted ⇒ today" work, so it is load-bearing.
- **Failure scenario:** None behavioural; a hidden test asserting the parameter is required (no default) would fail. The frozen `test_require_environment_existing_call_shape_still_works` asserts the opposite (that the old call shape still works), so the candidate is consistent with the frozen tests.
- **Proposed change:** Accept as-is; the sentinel default is what implements the spec's "omitted ⇒ today" row. Optionally note the deviation in the spec.

### F3 — mlx-serve keeps M72's "requires joint_v1" message for other drafter kinds (minor, confirmed)
- **Location:** `mlx-serve/src/mlx_serve/config.py:178-187`. For mode + `suffix`/`dflash`/`eagle3` + no scan, `mtp_off` is False (draft_kind != ""), so the raise is "tq4_attention ... requires mtp_verify_scan 'joint_v1'". With `joint_v1`, `_validate_mtp_verify_scan` raises "joint_v1 requires draft_kind 'mtp'".
- **Problem:** The refusal outcome is correct and matches "refused as today", but a user with `draft_kind: suffix` is told to add `joint_v1`; if they follow that, they are refused again by the `joint_v1`-needs-`mtp` rule. There is no drafter-kind-specific message. This is the implementer's P2 / test-writer's F3.
- **Failure scenario:** Operator confusion only; no protection gap. The fork side does have a kind-specific message ("supports draft_kind mtp or no drafter (got 'suffix')") because the fork's own `_mtp_off` refuses other kinds, but mlx-serve never gets there for the no-scan case.
- **Proposed change:** Optional: in `_validate_tq4_attention`, raise a kind-specific message when `draft_kind` is a known non-`mtp` kind before falling back to the scan message. Not required by the spec.

### F4 — OFF + `MLX_VLM_MTP_VERIFY_AB=1` through `_initialize_model` is not tested (minor, hypothesis)
- **Location:** `mlx-vlm/mlx_vlm/server/generation.py:265-276` (`_apply_mtp_verify_from_env`).
- **Problem:** By reading, OFF + ab=1 (scan `per_query`/unset) passes `_resolve_tq4_mode_from_env` (scan defaults `per_query`, mtp_off accepts), then `_apply_mtp_verify_from_env` skips the early return (ab=="1"), `resolve_policy("per_query", ab=True)` raises `--mtp-verify-ab requires --mtp-verify-scan joint_v1` → `_mv._fail` → refused. mlx-serve refuses this at config level (`test_ab_without_a_drafter_is_refused`), so the worker path is only reachable by setting env directly. No frozen or implementer test exercises this through `_initialize_model` (the `_init`/`loader` helpers `delenv` `MLX_VLM_MTP_VERIFY_AB`).
- **Failure scenario:** A regression that weakens `resolve_policy`'s ab-guard would let an OFF+ab load proceed untested on the worker side.
- **Proposed change:** Add one `_initialize_model` test with `MLX_VLM_MTP_VERIFY_AB=1`, no drafter, asserting refusal. The behaviour is correct; this closes the test gap.

### F5 — OFF + stray drafter path + `MLX_VLM_DRAFT_ALLOW_FALLBACK=1` + incompat silently serves OFF (minor, hypothesis)
- **Location:** `mlx-vlm/mlx_vlm/server/generation.py:1703-1712` (post-load check) and `speculative/drafters/__init__.py:221-244` (`drafter_incompat_policy`).
- **Problem:** If OFF is configured (`configured_draft_kind` None/`""`) but `MLX_VLM_DRAFT_MODEL` is set, `require_draft_config(None, path)` does not refuse (None is not a weights-backed kind), so `load_drafter(path, kind=None)` auto-detects and loads. If `validate_drafter_compatibility` then raises and `MLX_VLM_DRAFT_ALLOW_FALLBACK=1` is set, `drafter_incompat_policy` returns `(None, None)`; `draft_model` becomes None and the post-load check does not fire, so the mode serves OFF. This is the intended OFF state (no drafter, no stamp) and the protection the request asks for holds; the only oddity is that a stray drafter path is silently ignored under a deliberate degraded-start flag. Not tested.
- **Failure scenario:** None against the request — the OFF state is served correctly. A user surprised by a stray `draft_model` being ignored under fallback would not get a refusal.
- **Proposed change:** Optional: when a mode is configured OFF and a drafter path is present, refuse regardless of fallback (the OFF invariant should not depend on the incompat policy). Or accept as-is and document.

### Scope requests (no severity)
- **S1:** The spec's `_apply_tq4_attention_from_env(model, mode, *, draft_kind)` signature and "passes the same value to the TQ4 calls" wording are both literal contracts; the candidate satisfies one (resolve call) and deviates on the other (apply call) via F1. A clarifying sentence in the spec — "the apply call may use the sentinel when the configured kind is `mtp`, since the sentinel and ``mtp` are behaviourally identical" — would make F1 a non-deviation.

### Summary
Nothing of substance fails under the supported conditions. The three protection questions all hold: MTP-ON keeps `joint_v1` everywhere, OFF cannot serve a drafter or a verify stamp, and mlx-serve and the worker agree on every accepted and refused configuration under the supported path. The five findings above are all minor: F1 is a literal spec deviation with no behavioural consequence (risk is hidden tests asserting the explicit `draft_kind="mtp"` pass); F2 is the load-bearing sentinel default; F3 is a misleading-but-correct mlx-serve message; F4 and F5 are test gaps for edge paths reachable only via direct env or the fallback flag. No blocker or major defect.
