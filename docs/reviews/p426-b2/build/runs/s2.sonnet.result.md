## Abort manifest in P426 mode
- `transport_abort.gate` is the gate report plus the full `request_usage`.
- `transport_abort.session_id` is the session id.
- `transport_abort.in_flight` is `{in_flight, message_id, requests_started}`.
- The termination evidence and `cause` use the existing `termination` and `cause` keys.
- The spec doesn't fix the key names, so s3 and s4 must read these. Without a gate for the item, all three are `None`.

## What the tests confirm
- `TG1_EVIDENCE` and the probe default are unchanged.
- `--evidence p426` selects `TG1_P426_EVIDENCE` and is recorded in `runtime.evidence_policy`.
- The item barrier files appear only in P426 mode.
- The generation identity does not depend on the flag. I compared a plain run, a control run and a P426 run, and also compared the composite directly.
- The chain adds `--evidence p426` only in P426 mode, and never in the legacy chain.
- `transport_cause` returns the cause for `m64` and P426, and `None` for plain tg1.
- A real `OpencodeArm` in tg1 + P426 mode stamps `connection`, `dropped_stream` and `timeout`.
- A plain tg1 abort has no cause, gate, `session_id` or `in_flight`.
- An M64-style abort has the gate report without the P426 additions.
- Aborts at a request boundary and with a request in flight carry `request_usage`, `session_id`, the in-flight message id (`m2`) and `termination`.

## Not satisfied or caveats
- `client_timeout` is not stamped by the probe. It comes from the chain's classification of an idle-cancelled probe (`chain_incident.py`), so this slice does not cover it.
- The in-flight message id comes from the stream's `active` message. It is `None` if the client died before a `step_start` was parsed.
- The manifest-check on `runtime.evidence_policy` and the chain-side `p426_continue` handling belong to s3 and are not touched.
