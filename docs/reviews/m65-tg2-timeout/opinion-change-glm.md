## Findings

**F1 — major — solution code that deletes or corrupts its own marker file turns a real `timeout` into `TransportAbort` (infrastructure).**
Location: `benchmark/bench/tg2_grade.py:1496-1501` (`_marker_evidence` `seen = names[0] in files and "<TAG> <nonce>" in files[names[0]]...`), `:589-595` (`_readback_script`), `:1444-1446` (the `if not _marker_evidence(exe, ...): raise TransportAbort`).
Evidence: confirmed (traced). The marker file is written by `echo "TAG nonce" > /report/.tg2-marker-<step>-<nonce>` before the runner (`_marker_write`, `:538-541`), then the solution runs inside the same container with `/report` writable. The solution can read the nonce from its parent's argv (spec `Known limit`, `:60`) and `rm /report/.tg2-marker-execute-*` or overwrite it with garbage. On a timeout the stream is empty (box fact), so `_marker_evidence` falls through to the read-back; the read-back tars the two names; if the marker file is gone or its content line is not exactly `"<TAG> <nonce>"`, `seen` is `False`, `_marker_evidence` returns `False`, and `_grade_steps` raises `TransportAbort("tg2 execute: runner-start marker absent")`. A genuine runaway is then classified as infrastructure, the one outcome the request says must not happen, and Stage 3b counts it as a transport DNF.
Problem: the request asks whether solution code running after the marker can turn a timeout into the wrong class. It can — by deleting/corrupting the file, not by forging it (forgery with the *wrong* nonce is already guarded; the *correct* nonce is readable from argv).
Scenario: a Rust solution appends `std::fs::remove_file("/report/.tg2-marker-execute-<nonce>").ok(); loop {}` — the runner spins, the marker file is gone, the grade is `TransportAbort` instead of `timeout`.
This is the spec's recorded `Known limit` (`docs/specs/m65-tg2-grade-timeout-evidence.md:60`), so per the contract it is a **hazard the material introduces**, not a defect against the literal spec. I flag it because the request explicitly asks the question and the candidate's own tests never exercise it (see F5). Proposed change: none required by the spec; if hardening is wanted, write the marker with `chmod 0444` (or to a path the solution can't read from argv, e.g. a fixed-name file the grader owns) so the solution can read but not remove/replace it.

**F2 — major — a failed read-back step turns a real `timeout` into `TransportAbort`, and the read-back's own `head -c` cap can make that happen under a full `.out` file.**
Location: `benchmark/bench/tg2_grade.py:599` (`READBACK_CAP = OUTPUT_CAP + (1 << 20)`), `:589-595` (`_readback_script` ends `... | head -c READBACK_CAP+1; exit ${PIPESTATUS[0]}`), `:1486-1489` (`if back["timed_out"] or back["oom"] or back["mem_kill"] or back["rc"] != 0: raise TransportAbort`).
Evidence: confirmed (traced). The read-back script's exit status is `PIPESTATUS[0]` = `tar`'s exit. If the tar stream reaches `READBACK_CAP+1` bytes, `head` closes the pipe early, `tar` takes `SIGPIPE` (rc 141), so `back["rc"] == 141 != 0`, and `_marker_evidence` raises `TransportAbort`. The marker file *is* present and correct, but it is never checked because the rc-guard fires first.
Problem: under current constants this is latent — the `.out` file is bounded to `OUTPUT_CAP` (16 000 000) and the tar of (16 MB out + ~40 B marker) is ~16 002 560 B, under `READBACK_CAP` (17 048 576). But the slack is only ~1 MB and the coupling is silent: if `OUTPUT_CAP` is ever raised, or a member lands on a 512 B boundary that adds padding, or a future step writes a second capped file, the read-back SIGPIPEs and a real runaway becomes infrastructure — exactly the misclassification the request is about.
Scenario: raise `OUTPUT_CAP` to 17 MB (a plausible future tuning) → every execute-timeout with a full `.out` becomes `TransportAbort`.
Proposed change: make the read-back's exit status independent of `tar`'s SIGPIPE — e.g. `... | head -c READBACK_CAP+1; rc=0` (or `exit 0` on a bounded read-back, since the cap is enforced by `parse_readback` anyway), and/or assert `READBACK_CAP > OUTPUT_CAP * 2 + 4096` as a named invariant next to the constant.

**F5 — minor — both test sets miss the same real-box paths the request asks about.**
Location: tests `test_tg2_grade_timeout_impl_docker.py` and `test_tg2_grade_timeout_fe_docker.py`.
Evidence: confirmed by reading both files.
- **No compile-step or collect-step spin on the real box.** Both docker suites spin only `execute` (compile finishes, execute hangs). The read-back for `compile` and `collect` on the real image — where the marker file is written by a *different* echo, on stderr for collect, and the read-back tars `collect.marker` with `out_sha256 = None` — is exercised only on the fake (`test_tg2_grade_timeout_impl_fake.py:64-66`, `fe_fake:191-200`). A compile that hangs the compiler (a real failure mode for a runaway `build.rs` / macro) is unproven on the box.
- **No solution-driven marker-file deletion/corruption** (F1). Both sets test `no_marker` (the echo *never ran*) and a forged *wrong-nonce* file (`impl_fake:69-71`, `fe_fake:240-257`). Neither tests the solution *removing or overwriting* the file after the echo wrote it — the actual code path of the spec's known limit. The fake's `no_marker` and the real deletion are different on the box (the file exists transiently, then is unlinked).
- **No real-box read-back timeout / non-zero rc / truncated-but-valid tar.** The fake covers `timeout`, `rc=125`, `no_marker`, `raise_os`, unparseable tar, `../escape`, symlink (`impl_fake:78-90`, `fe_fake:269-282`). The docker sets cover none of these; a read-back that SIGPIPEs near the cap (F2) or hangs is unproven on the image.
- **No FIFO/device/hardlink marker file.** The read-back script's `[ -f "$f" ] && [ ! -L "$f" ]` excludes symlinks (tested) and FIFOs/devices (via `-f`, untested); hardlinks pass both and rely on the content-line check (untested).
Problem: the request asks what both test sets miss; the above are the gaps. None is a candidate defect on its own, but F1 and F2 are exactly the untested paths where a real timeout could become infrastructure.
Proposed change: add docker spins for a hanging compile (e.g. a `build.rs` that loops) and a collect timeout; add a fake+docker case where the solution unlinks its marker file and assert it is `TransportAbort` (documenting the known limit, not fixing it); add a fake case feeding a valid-header/truncated-body tar and a FIFO marker file.

### Direct answers to the question

- **Runaway → infrastructure?** Yes, in two supported-by-the-material ways: (a) the solution deletes/corrupts its own marker file after the echo (F1, spec's acknowledged known limit); (b) the read-back step itself fails — most plausibly by `tar` SIGPIPE when the tar stream hits `READBACK_CAP+1` (F2, latent under current constants). Both yield `TransportAbort` for a genuine timeout.
- **Never-started runner → model outcome?** No. A runner that never started leaves no stream marker and no marker file (the echo never ran); the read-back finds nothing, `seen` is `False`, and the grade is `TransportAbort`. The per-step, per-grade nonce in the filename and the exact-line content check prevent cross-step/cross-grade collision. This path is correctly held as infrastructure.
- **Leak / corruption?** No leak found: the read-back container is launched with the grade nonce (`gnonce`) via `_launch`/`_step` and removed in `_step`'s nonce-verified finally; the volumes are removed by `_grade`'s finally. No corruption of retained evidence: `<step>.marker`/`<step>.out` are new files beside `<step>.stdout`/`<step>.stderr`, and `parse_readback` rejects symlinks, unexpected/duplicate names, non-regular members, over-cap and (defensively) truncated members.
- **D1 (`stdbuf -o0 head | tee`, preflight):** accept. The marker file is written by a separate `echo >` before the bounded pipe, so it is durable regardless of `tee` buffering; the `.out` copy's completeness depends on `stdbuf -o0 head` flushing before the kill, which the docker spins prove on the box for all four languages. The `stdbuf -o0 true` preflight turns a missing `stdbuf` into infrastructure (not a false `compile_failure` via SIGPIPE/rc 141). Sound.
- **D2 (collect writes no `.out`):** accept. Collect's stdout is the report tar; teeing it would duplicate up to 32 MB into the 64 MB volume. `out_sha256` is `null` for collect. Consistent with the spec ("the step's bounded output" = `_bounded` output, which collect lacks).
- **Read-back failure paths:** covered above; the rc-guard-before-marker-check ordering creates F2.
- **OOM / output-cap / mem-kill:** unchanged and correct. `_marker_evidence` returns `True` from the stream (the marker is echoed before the runner, and OOM/cap happen during the runner), so no read-back runs; `_resource` then classifies `oom`/`output_cap`/`mem_kill`. `timed_out` is checked before `output_cap` in `_resource`, so a timeout with a full stream is `timeout`, not `output_cap`.
- **Frozen universe / `VERSION` bump:** the bump is required and correct; it forces a planned re-freeze outside this change's scope (F4). The candidate's regrade test bypasses the version check, matching the existing B4b-1 workaround pattern.

The one change I would ask for before merge is **F2** (decouple the read-back's exit status from `tar`'s SIGPIPE, or widen and assert the `READBACK_CAP`/`OUTPUT_CAP` invariant). F1 is the spec's recorded known limit but should at least be covered by a test that documents it (F5).
