## Other defects and hazards

**D1 — major — `tq4_attention.py:227–229` `attend` rejects in-scope prefill chunks with `mask=None`.** Evidence: confirmed in source. The spec's `supports` predicate (`SPEC.md` Scope-settled) says `mask in (None, "causal")` — `None` is in scope. The spec's prefill-chunk routing row has no mask condition; p2s is always causal. The candidate adds, after `supports` returns True: `if mask is None: f.count("fallback:mask"); return None`. So a multi-query call with `mask=None` that passes `supports` is then bounced to today's path. Problem: the spec's `supports` contract is the only gate; an in-scope prefill chunk (L > 5, T_eff > 2048, `mask=None`) that the spec routes to p2s is instead routed to today's `quantized_attention`, contradicting the routing table. Scenario: a caller invokes `scaled_dot_product_attention` with `cache=TurboQuantKVCache`, `queries` of shape (1, 24, 37, 256) bf16, `mask=None`, `sinks=None` (a perfectly valid prefill chunk per the spec). `supports` returns True; `attend` then returns None with `fallback:mask`. The mode is silently inert for that call. The frozen test suite does not cover `mask=None` on a multi-query prefill chunk (the routing tests use `mask="causal"` or the verifier's mask), so this is missed. Proposed change: drop the `if mask is None: fallback:mask` branch — `supports` already gates `mask` to `None`/`"causal"`; for p2s, treat `None` as causal (the spec says "MLX fused SDPA `mask='causal'`"), and for the short-chunk row likewise. (The implementer disclosed this as a beyond-spec strictness; it is more than that — it misroutes a spec-supported call.)

**D2 — major — `tq4_attention.py:98–101` refuses `TQ_DECODE_2PASS_LEGACY` set to `"0"` / `"false"` / `"no"`.** Evidence: confirmed in source (`os.environ.get("TQ_DECODE_2PASS_LEGACY")` is truthy for any non-empty string). The cache's own parser (`turboquant.py`) treats only `1`/`true`/`yes` as on, so `=0` is off for the cache but the mode still refuses to start. Problem: an operator who exports `TQ_DECODE_2PASS_LEGACY=0` (a common shell pattern to "make sure it's off") gets a start-up error under a mode the spec allows, with no wrong-output risk. The spec says "is set" — the literal reading — but the spec's intent (F5) is to refuse the *legacy decode path*, which `=0` does not engage. Scenario: a deployment script sets `export TQ_DECODE_2PASS_LEGACY=0` defensively; `tq4_attention: m72_v1` load fails with "TQ_DECODE_2PASS_LEGACY is set". The frozen test `test_require_environment_accepts_the_legacy_flag_spelled_off` (which the test-writer flags as arguably unsupported) exercises exactly this. Proposed change: parse with the cache's own spelling (refuse only on `1`/`true`/`yes`), or document the strict reading in the spec. The implementer disclosed this; flagging because it changes a spec-supported start-up under a benign env.

**D3 — minor — `tq4_fast.py:117–135` `_check_cache` does not assert the cache class.** Evidence: confirmed (frozen `test_kernels_refuse_a_batch_cache` reproduced). `decode_attention` on a one-row `BatchTurboQuantKVCache` returns an output instead of raising. The dispatch gate (`supports` → `batch_cache`) prevents this on the served path; the kernel entry points are public. Scenario: a caller using `tq4_fast.decode_attention` directly on a left-padded batch cache reads padded rows as real tokens. Not reachable from the server. Proposed change: add `assert type(cache) is tq.TurboQuantKVCache` in `_check_cache`.

**D4 — minor — `tq4_attention.py:319–333` `require_policy_stamps` is a load-time check beyond the spec's load order.** Evidence: confirmed in source; called from `generation.py:233` before `check_fp16_range`. The spec's load-order line is resolve → require_environment → fused_v1 → joint_v1 → check_fp16_range → apply_to_model → self_test_model; `require_policy_stamps` is not in that list. Problem: a model stamped with the mode but missing a policy stamp (an easy mistake in a custom loader) refuses to start with an error that names the module, which is helpful, but the spec doesn't authorise the refusal and the frozen load-order/abort tests fail under it (the test-writer's fixture stubs `ap.apply_to_model`/`mv.apply_to_model`, so the stamps aren't applied). The test-writer shows all 26 load tests pass once `require_policy_stamps` is neutralised. Scenario: a third-party loader that stamps `tq4_attention` first then policies gets a start-up error ordering mismatch. Proposed change: either add `require_policy_stamps` to the spec's load-order line (it is consistent with F14/F15's intent) or move the check into `apply_to_model` (which the spec names). The implementer disclosed this; the spec gap is the issue.

**D5 — minor — `mlx-serve/src/mlx_serve/config.py:315` `tq4_attention=entry.get("tq4_attention") or ""` silently coerces `false`/`0`/`null` to absent.** Evidence: confirmed in source. The spec's registry key is "absent | `m72_v1` | `m72_exact`"; `false`/`0`/`null` are not in that set. Problem: a YAML typo (`tq4_attention: false`) loads as absent rather than refusing, so a model intended to run with the mode silently runs without it. Scenario: an operator sets `tq4_attention: false` meaning "off"; the model starts with kv_bits 4 + fused_v1 + joint_v1 but no TQ4 mode, so TQ4 layers fall back per call (counted `fallback:cache_class` would not fire — the cache is `TurboQuantKVCache`; actually `supports` would return True and the call would route to today's `quantized_attention` via the unchanged `base.py` TQ branch, uncounted). The frozen mlx-serve suite does not cover this. Proposed change: refuse any value outside `""`, `m72_v1`, `m72_exact` (including `false`/`0`/`null`), or document the coercion.

**D6 — minor — `stack/benchmark/bench/provenance.py:1944` `tq4_route_counts` is gathered once at manifest creation.** Evidence: confirmed in source (called from `gather` at manifest build time). If `gather` runs at run start the counters are zeros; the manifest then records `route_counts` all absent although the run used `d2`. The spec says "exposed in … the manifest"; it does not say when. Scenario: a benchmark harness that builds the manifest before generation records empty counters. Proposed change: re-fetch `tq4_route_counts` after generation, or record a snapshot before and after.

**D7 — minor (test miss) — the frozen suites do not cover `mask=None` on a multi-query prefill chunk.** See D1. The routing tests use `mask="causal"` or the verifier's mask; none drives `attend` with L > 5 and `mask=None`. So D1's misroute is not caught. Proposed change: add a routing row for `mask=None` prefill chunks asserting `p2s`.

**D8 — minor (test miss) — the frozen suites do not cover `kv_quant_mode: prod` at load.** `tq4_attention.require_environment` refuses `kv_quant_mode not in (None, "", "mse")`, but it reads it from `TQ_KV_QUANT_MODE`. The test-writer's F2 notes the registry's `kv_quant_mode` reaches the worker as `--kv-quant-mode`; whether that sets `TQ_KV_QUANT_MODE` is outside this diff. If it does not, a `prod` registry entry starts the mode and then counts `fallback:codec` per call (no wrong output, but the mode is silently inert). No frozen test exercises this. Proposed change: a load test with `kv_quant_mode: prod` asserting a start-up refusal, or wire `--kv-quant-mode` to `TQ_KV_QUANT_MODE`.
