### New findings

**F1 — §3.7(b) `npx jest ./*` is not clearly allowed, yet §7.6 asserts the pilot is eligible. Major, confirmed.**
- Location: `docs/specs/m76-b4b2-a8-consumers.md` §3.7(b) ("`npx jest` / `npm test` without `-u`, `--updateSnapshot`, `--ci=false` or extra script arguments") vs §7.6 ("the pilot's two commands → eligible").
- Evidence: confirmed. Both pilot shell calls contain `npx jest ./*`; `./*` is a positional test-path argument to jest. The phrase "extra script arguments" is undefined. An implementer reading it as "any positional argument after the command name" must reject `./*` → the pilot stays tampered, contradicting §7.6. An implementer reading it as "only npm-script-level flags" accepts `./*`. The two readings diverge on the one real recorded item.
- Problem: the eligibility of the pilot (and of any real javascript item whose agent passes a test path/pattern to jest) is implementation-defined. §7.6's red test cannot be written honestly until the spec states which reading is correct.
- Failure scenario: the implementer chooses the strict reading; the pilot's two commands fail (b); the pilot's lock-file-only row stays tampered and scores 0; the §7.6 red test fails; or the implementer chooses the loose reading and a later agent's `npx jest --coverage`/`--config` (also a "script argument" under the same loose reading) is accepted and writes files.
- Proposed change: state explicitly that `npx jest` / `npm test` may take test-path positional arguments (e.g. `./*`, `*.spec.js`) and forbid only state-changing flags — `-u`/`--updateSnapshot`/`--ci=false` and any flag the function cannot prove is read-only (e.g. `--coverage`, `--config`, `--json`, `--outputFile`) — listing them or, conservatively, allowing no flags at all beyond test paths.

**F2 — §3.7(a)/(b) `node <accepted file>` can create denied files that (a) never traces, so a real config-file tamper is classed eligible and silently forgiven by the regrade. Major, confirmed.**
- Location: §3.7(a) ("every `write` / `edit` / `patch` tool path … is a path of the B8-verified final-tree manifest") and §3.7(b) ("`node <accepted file>`" in the allowlist).
- Evidence: confirmed. (a) inspects only write/edit/patch tool calls; (b) admits `node <accepted file>` unconditionally. `tg2_grade.tamper_reasons` (`tg2_grade.py:958-989`) flags any new denied file (e.g. `babel.config.*`, `jest.config.*`, `.babelrc*` per `DENY_NAMES` at `tg2_grade.py:785`) or any new non-helper file, regardless of how it was created. A `node` script can write such a file; the final-tree tamper check catches it (row is `tampered`), but the eligibility function does not — no write tool touched it, and the shell call `node helper.js` is allowed.
- Problem: C368 (1) rules that only lock-file-only tampers are regraded and "shell-only protected-path edits stay tampered and are listed". A `node <accepted file>` that writes `babel.config.js` is a shell-only protected-path edit, but it passes (a) and (b), so it is deemed eligible. The regrade then runs on the prepared tree + accepted files (the grader strips the denied `babel.config.js` via `accepted_files`), and if the tests pass without it, `regraded_passed` flips to True — the config-file tamper is silently forgiven and the verdict moves.
- Failure scenario: a both-arm javascript item where the agent writes a helper `setup.js` (accepted), runs `node setup.js` which writes `babel.config.js`, then `npm install` and `npx jest`. The final grade is `tampered` (new denied `babel.config.js` + new `package-lock.json`). Eligibility: write paths = {`setup.js`, solution} ⊆ accepted manifest (a ✓); shell calls all in the allowlist (b ✓); bare install present (c ✓) → eligible. The regrade omits `babel.config.js`, tests pass, the row flips to passed. A non-lock-file tamper changed the axis.
- Proposed change: make eligibility require that the tamper reasons re-derived from the final tree vs prepared are exactly the lock-file set (new `package-lock.json`, and `package.json` modified only when a bare `npm install`/`npm i`/`npm ci` ran). Equivalently, enumerate the final-tree files not in prepared and require every one to be `package-lock.json` (or a `node_modules` entry the grader already strips). That closes the `node`-script (and any other shell-side-effect) hole without forbidding `node <accepted file>` outright.

**F3 — §3.7 vs §7.3: B8-A8 enumerates "EVERY" final-tampered javascript row, but §7.3 says the pilot is `accepted` with the decider absent (no regrade records exist). Major, hypothesis.**
- Location: §3.7 ("The tool writes, for EVERY final-`tampered` javascript row …"; "B8-A8 enumerates the final-`tampered` javascript rows … requires exactly one sealed record per row (else the session is `incomplete`)") vs §7.3 ("the pilot accepted, s1 / s2 `incomplete`") and §7.5 ("After the decider, in order: … the javascript regrade tool (§3.7); B8-A8 …").
- Evidence: confirmed for the pilot's tampered row (above); hypothesis on the enumeration scope. The pilot is a diagnostic leg (`§3.2`: diagnostic `("pilot","reload")`), the regrade tool runs only "after the decider" (§7.5), so in the §7.3 decider-absent build no regrade records exist for the pilot's tampered javascript row. If B8-A8 enumerates the pilot's row too, it finds no sealed record → the pilot is `incomplete`, contradicting §7.3's "pilot accepted". If B8-A8 enumerates only confirmatory sessions (s1/s2), the spec's "EVERY" is wrong.
- Problem: the scope of the enumeration (all sessions vs confirmatory only) is unstated; the two acceptance clauses read inconsistently. An implementer following "EVERY" makes §7.3 unpassable; one scoping to s1/s2 contradicts the literal text.
- Failure scenario: the §7.3 golden (pilot accepted, decider absent) fails because the pilot's tampered javascript row has no regrade record; or the implementer special-cases the pilot and the literal "EVERY" is violated for a real s1/s2/reload that the regrade tool skipped.
- Proposed change: state that B8-A8 enumerates final-tampered javascript rows only for the confirmatory sessions (s1, s2), and that the regrade tool runs for those sessions only; or, if the pilot/reload are included, state that a missing regrade record for a diagnostic session is not `incomplete` (e.g. the diagnostic session's tampered javascript rows are reported but not required to have a regrade record before the decider).
