## How the tests are made independent of mechanism (and where they are not)

* **The stated command (T2) is parsed from the prompt**: backtick-quoted spans in the prompt after the last "Do NOT modify", that contain the language's tool (`cargo` / `gradle(w)` / `npm|npx|jest` / `cmake|ctest|make|./build/`). T1 (static and docker) and T3 then use *that* command; when the prompt names none (baseline) they use the language's canonical command. **Assumption the implementer must meet: the command is written in backticks in the prompt tail.** Prose-only naming fails T2 (and T3-stated). <!-- allow-shorthand -->
* T1 static enables a test by any of: the tree (no `#[ignore]`, no macro guard), a flag in the stated command (`--include-ignored`, `-DEXERCISM_RUN_ALL_TESTS=ON`), or a CMake default. The cpp CMake-default detector is a regex over `CMakeLists.txt`; if an implementer enables the macro in some other way the static test will say "disabled" while the docker test (real tool) tells the truth — the docker test is the authority, the static one is the whole-universe screen. <!-- allow-shorthand -->
* T3 / T4: the repo exposes **no production permission matcher**, so the carrier's `permissions` list is evaluated by a port of opencode 2.0.20's wildcard (the one `test_m61_round7.py` verifies against the pinned binary) — **not** a real opencode session. Rule order semantics and shell-command splitting are not exposed either, so every verdict must hold under all four readings {last-matching-rule-wins, any-deny-wins} × {whole command string, each `&&` / `;` / `|` node}: "denied" requires all four to deny, "allowed" all four to allow. This is stricter than any single engine and may force the implementer's patterns to start with `*` (so a node-level and a whole-string engine both match).
* Docker tests run the stated command in the grader image as the agent would type it plus only what the network-less container needs (`--offline` for cargo / gradle, `Cargo.lock` generation, a `node_modules` symlink to the image's), then compare what the tool itself reported (libtest summary, Gradle JUnit XML, jest summary, Catch2 summary) with the grader's graded leaves on the same tree, and run production `Tg2Corpus.snapshot` / `tamper_reasons` / `grade`.
* K1 runs `p426_reconcile.reconcile_item` + `fault_class` (the functions the hook uses); the hook's own disposition path (sidecar write) is not exercised. The fixture assumes fields the shape file does not record: `session_id`, `gate.requests_completed(_at_kill)=40`, `event_types_seen` (40/40), and the item-window `before` snapshot (derived from the kill-time `after` summary).

## Points for the operator / implementer (my reading, not settled by the spec)

* **P1 — spec vs baseline for JS and Java.** The goal says the shipped tests are mostly disabled "in every language … javascript `xtest`, java `@Disabled`". The baseline materializer already rewrites those (1566 skip forms, `TG2_UNIVERSE_REPORT.md`), and the real runs confirm JS/Java run the full suite. Only rust and cpp are short. The JS/Java tests are therefore invariants, not fixes; if the implementer touches the JS/Java preparation they must not regress.
* **P2 — I1 binding test is mechanism-sensitive.** `test_i1_the_identity_binds_the_helper_sentences` requires `(corpus_tg2.SCAFFOLD, Tg2Corpus().identity())` to change when `corpus_tg2.HINTS[lang]` changes at call time. If the implementer binds the prompt by a new label / version constant instead of a content hash, that test fails although the spec would be met. The operator can discount that one test (4 parametrizations); the other I1 tests are mechanism-free (policy hash old ≠ new, `is_compatible` refuses). I did not test binding of the workspace preparation by perturbation (no neutral knob).
* **P3 — "any letter case" for code-search sites.** The spec text says the other lookup denies stay denied "for any letter case"; the baseline has upper-case variants only for `xercism` / `problem-specifications`. `test_t4_code_search_sites_stay_denied_in_upper_case_host` (5 params, host in UPPER case) is my literal reading and fails on the baseline; it is a stretch under "cooperative agent, not adversary". Cheap to drop.
* **P4 — local `problem-specifications` paths.** `LOCAL_WITH_THE_WORD` includes `ls problem-specifications-notes` and `cat ~/problem-specifications/README.md` as allowed local paths (spec: "a local build flag, file or path that merely contains the word"). If the operator thinks reading a local clone of problem-specifications should stay denied, remove those two.
* **P5 — K1 verdict is `accounting` strictly.** The test requires `fault_class == "accounting"` and `report.ok is False` (recorded as an accounting fault), not "reconciled clean". The spec says "recorded (the `accounting_fault` class)", which I read that way.
* **P6 — Rust negative for the grader.** The rust stub of `rust/accumulate` does not compile (`compile_failure`), so the rust known negative is the reference with one `pub fn` body replaced by `todo!()` (the cpp negative: one `return <expr>;` → `return {};`, tried up to 8 occurrences until the grader returns `parsed`). JS / Java negatives are the untouched stubs. Acceptance 1 wants "a solution that compiles but is wrong": satisfied; the test skips (with the grader outcome in the reason) if no such mutation can be built — on the baseline it was always buildable, nothing skipped.
* **Not covered**: acceptance 2's "or a real opencode session" (no real-opencode check); acceptance 5's "every changed module's existing tests pass / nothing that passed on the baseline fails" (the verifier runs the repo suite; I ran only the new directory); acceptance 6 (M85 phase 2 positives) and the carrier hash / generation-identity pipeline beyond the policy hash and `is_compatible`; the hook-level `accounting_fault` disposition for K1. T1 docker covers one item per language (rust/accumulate, javascript/zebra-puzzle, java/zebra-puzzle, cpp/all-your-base), not the whole universe — the whole universe is covered statically only.
