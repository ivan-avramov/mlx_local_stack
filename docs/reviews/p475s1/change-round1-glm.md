## Findings

### F1 — The worker-environment check rests on an unverified platform assumption (D1); the test seam cannot refute it
- **Location:** `benchmark/bench/p475_kv.py:803-805` (`worker_env = ops.proc_env(ident_w["pid"]) or {}; leaked = kv_env_names(worker_env)`); `RealOps.proc_env` → `chain_ops.ChainOps.proc_environ` (`benchmark/bench/chain_ops.py:498`, `psutil.Process(pid).environ()`); tests `test_p475_impl_support.FakeOps.proc_env` (`benchmark/bench/tests/test_p475_impl_support.py:269`).
- **Severity:** major.
- **Evidence:** confirmed (traced in source; the assumption is the operator's own D1, still open). The worker is spawned by `mlx-serve` with no `env=` (`src/mlx-serve/src/mlx_serve/process_manager.py:438-441`), so it inherits the router's stripped environment; the router's env is stripped by `P475Chain.env_base` → `strip_kv(super().env_base())` (`p475_kv.py:1674-1676`). The fork's worker CLI then sets `KV_BITS`/split vars *in-process* from the `--kv-bits` flag (contract Facts). Whether `psutil.Process(pid).environ()` on macOS reports those in-process values or the exec-time envp is the whole question.
- **Problem:** If D1 is false on the live box (psutil reflects the in-process `os.environ["KV_BITS"]="8"` the worker's CLI sets), then every quantized arm — AF8, TQ8, AF4, and the base TQ4 itself — fails the `leaked` check, is marked INVALID before the driver, and the matrix cannot complete. The fake `proc_env` returns a static dict without any `KV_*` name, so this path is green for every arm in every one of the 161 implementer tests; the frozen tests' `FakeOps.proc_env` (`fakes.py:491-493`) is equally static. No test in either suite can disconfirm D1.
- **Failure scenario:** Smoke leg on AF8 (or any quantized arm): load succeeds, the KV line is correct, but `proc_env` returns `{"KV_BITS": "8", ...}`, `leaked == ["KV_BITS", ...]`, the leg is INVALID, the run stops nonzero, and no matrix is produced. The operator reads "worker environment carries stripped name(s)" and has to determine whether the arm actually mis-served or psutil simply reported the CLI-set value.
- **Proposed change:** Resolve D1 on the smoke leg before any full run: spawn the N16 worker and one quantized worker, read `psutil.Process(pid).environ()` for each, and confirm `KV_BITS` is absent from the quantized worker's env. If present, the check must compare against the *router's* env (which was stripped) rather than the worker's in-process env — e.g. capture the worker's env at spawn time from the router side, or drop the env check and rely on argv + KV-line engagement alone (R3 + R2 already prove the format).

### F2 — The frozen tests' `prepare`/`preflight`/`matrix` call shapes do not match the candidate
- **Location:** candidate `benchmark/bench/p475_kv.py:452` (`prepare(ops, cfg, arms=ARMS)`), `:539` (`preflight(arm, ops, cfg, max_retries=None)`), `:1214` (`matrix(cfg, blocks=2)`); frozen tests `.p475-review/frozen-tests/helpers.py:45` (`K().prepare(args(), ops)`), `:49` (`K().preflight(args(arm=a), ops)`), and `test_run_control.py:209` (`K().prepare(H.args(), ops)`).
- **Severity:** major.
- **Evidence:** confirmed (signature mismatch traced in both). The contract's "Ops interface" section pins only `run_leg(leg, arm, ops, cfg)` and `run(args, ops)`; it is silent on `prepare`/`preflight`/`matrix`. The test-writer flagged this as ambiguity P2 and assumed `prepare(args, ops)`, `preflight(args, ops)`. The candidate resolved it the other way. `helpers.ready()` calls `K().prepare(args(), ops)`, so `args()` (an `ArgList`) is bound to the candidate's `ops` parameter and `FakeOps` to `cfg`; `prepare` then calls `cfg.worktree(arm)` on an `ArgList` → `AttributeError`. Every frozen test that goes through `ready()` (all of `test_run_control.py`, `test_matrix.py`, `test_harvest.py` resume cases) errors at collection/run before any behaviour is exercised.
- **Problem:** The independent test-writer's suite — the acceptance deliverable for `prepare`, `preflight`, and the resume/`matrix` paths — cannot run against the candidate without adapting `helpers.py`. The implementer's own tests pass because his `FakeOps.add_all` calls `K._atomic_json` for preflight records directly and never exercises `prepare`/`preflight` through the candidate's real entry points. So the R15 (preflight refusal/retry cap) and R20 (matrix completeness) behaviours are covered only by the implementer's own tests, not by the independent frozen suite.
- **Failure scenario:** The second delivery runs the frozen tests; every `test_run_control` test that calls `ready()` errors with `AttributeError: 'ArgList' object has no attribute 'worktree'`; the operator gets no independent signal on ABBA order, replacements, instability, or resume.
- **Proposed change:** Align the candidate's `prepare`/`preflight`/`matrix` to the shapes the frozen tests (and the contract's CLI) expect, or have the second-delivery adapter rewrite `helpers.py`. The cleanest fix is to make `prepare`/`preflight`/`matrix` accept `(args, ops)` and derive `cfg` inside via `config_from_args`, matching `run` — the contract already routes every subcommand through `config_from_args` in `main`, so the asymmetry is the candidate's own choice, not a contract requirement.

### F3 — `rung_problems` ties validity to two server-telemetry identities that are unverified on the live box
- **Location:** `benchmark/bench/capacity_ladder.py:131-137` (`prompt_per_second` vs `prompt_n/prompt_ms` within 2 %; `prompt_n == prompt_tokens`).
- **Severity:** major.
- **Evidence:** confirmed (the checks are in source; the live server's actual `raw_timings` shape is not exercised by any test — both fakes synthesise the fields to match). The contract explicitly requires both checks (R21), so the candidate is faithful to the contract; the risk is that the fork's `raw_timings` does not satisfy them.
- **Problem:** `prompt_n` (from `raw_timings`) and `prompt_tokens` (the response's top-level token count) are two different counters in the fork; if `prompt_n` excludes a chat-template/special-token prefix that `prompt_tokens` includes (or vice-versa), `prompt_n == prompt_tokens` fails on every rung of every arm, every leg is INVALID, and the matrix is empty. The 2 % prefill-derivation check is the same class of risk: `prompt_per_second` is the fork's reported rate and `prompt_n / (prompt_ms/1000)` is a re-derivation; if the fork rounds `prompt_ms` or reports `prompt_per_second` from a different numerator, the 2 % tolerance is too tight. Neither the implementer's nor the frozen fakes vary these from the server's real values.
- **Failure scenario:** First real leg (N16): the fork reports `prompt_n=8249` and `prompt_tokens=8256` (special-token mismatch); `rung_problems` records both, the leg is INVALID, the run stops at the first arm of block 1.
- **Proposed change:** Before the smoke leg, dump one real strict rung's `raw_timings` and confirm `prompt_n == prompt_tokens` and `prompt_per_second ≈ prompt_n/(prompt_ms/1000)` for the pick. If they differ, the contract's R21 needs a relaxation (or the fork's telemetry needs alignment) before the full run; do not discover it in a 12-leg run.

### F4 — `busy()` in teardown can flag a zombie or an unrelated same-uid process as a survivor
- **Location:** `benchmark/bench/p475_kv.py:958` (`busy = ops.busy(); if busy: survivors.append(...)`); `RealOps.busy` (`p475_kv.py:1544-1549`) scans `ps -axo pid=,command=` for `run_capacity` plus `ChainOps.busy_procs`.
- **Severity:** minor.
- **Evidence:** confirmed (traced). `ChainOps.busy_procs` (`chain_ops.py:366`) matches `BUSY` markers in `ps` output; `RealOps.busy` additionally matches any `run_capacity` in `ps`. The teardown runs after `_reap_driver` and `stop_stack`, so the driver and router are gone. But `busy_procs` does not filter by create_time, and a zombie (exited, unreaped) or an unrelated same-uid `run_capacity`/`mlx_vlm.server` process from another session would appear.
- **Problem:** A lingering zombie worker (the OS has not reaped it yet) or an unrelated process owned by the same uid turns a clean teardown into INVALID. The contract says "an unload refusal or a survivor → INVALID"; a zombie is not a live survivor but `busy()` cannot tell.
- **Failure scenario:** A flaky test run leaves a zombie `mlx_vlm.server` for a few seconds; the next leg's teardown sees it in `busy()`, marks INVALID, and the run stops.
- **Proposed change:** Filter `busy()` by create_time (bind the survivor check to the recorded router/worker identities, as `proc_alive` already does), or exclude zombies (`ps -o stat=` starting with `Z`) from `busy_procs` in the teardown path.

### F5 — The deciding block is re-entered on every resume once blocks 1–2 are flagged, even when it is already complete
- **Location:** `benchmark/bench/p475_kv.py:1497-1505` (`flagged = instability(block_values(records))` uses only blocks 1–2; `started` gates the cap increment but not the re-entry).
- **Severity:** minor.
- **Evidence:** confirmed. `instability` (`p475_kv.py:1173`) is computed from blocks 1 and 2 only. Once those are flagged, `flagged` stays non-empty for every subsequent resume. `started` is True after block 3 has any receipt, so the `or` short-circuits and `_run_block(deciding_block, ...)` is called again. `_run_block` then skips every arm (all "valid") and the replacement queue is empty, so it is a no-op — but it runs `load_dossiers` and `matrix` twice and logs a spurious "instability → deciding block" line each time.
- **Problem:** No correctness impact (the deciding block is bounded by `--max-deciding` via the counter, and a completed block 3 is a no-op), but on a resumed run after the deciding block the operator sees a misleading "instability … -> deciding block b3" log and a redundant matrix regeneration. More importantly, if the deciding block was *interrupted* partway and `--max-deciding` was already spent, the resume path works (because `started=True` bypasses the cap), so this is only cosmetic.
- **Failure scenario:** Resume a completed run; the runlog shows a deciding-block entry that the operator knows already ran.
- **Proposed change:** Record the deciding block as done in `state.json` (e.g. `state["deciding_done"] = True` when block 3 completes with no `unfilled`) and skip the re-entry when that flag is set.

### F6 — The KV-line "since this load" slice relies on append-only behaviour the fork does not guarantee across legs
- **Location:** `benchmark/bench/p475_kv.py:805-808` (`before = _read_optional(ops, log_path) or ""` … `since = after[len(before):] if after.startswith(before) else after`).
- **Severity:** minor.
- **Evidence:** confirmed. `chain_ops.server_log_path` documents the worker log as "append-only across legs". The code reads the whole file before and after load and slices the delta. If `after.startswith(before)` is false (log rotated, truncated, or rewritten between the two reads), it falls back to `since = after` and `parse_kv_line` takes the LAST `KV cache resolved:` line — which is still the current load's line for the same arm worktree. So the fallback is correct. The risk is only a performance one: reading the whole (potentially large) log twice per leg.
- **Problem:** None material; the fallback is sound. The cost is that a long run leaves a large `<WT>/logs/mlx_vlm.log` that is read in full twice per leg.
- **Failure scenario:** A 12-leg run on one arm worktree leaves a 50 MB log; each leg reads it twice, adding seconds of I/O per leg.
- **Proposed change:** Read the log byte offset before load (`Path.stat().st_size`) and read only the tail after that offset, instead of the full file both times.

### F7 — Scope: the candidate does not record the watcher's `--capacity-rows` path in the receipt for provenance
- **Location:** `benchmark/bench/p475_kv.py:695-701` (`watch_argv`), `:858` (`watch_speed_problems` reads `cfg.leg_dir(leg)/"watch.jsonl"`).
- **Severity:** scope request (not a defect).
- **Evidence:** The watcher is launched with `--capacity-rows <rows_path>` where `rows_path` is the arm worktree's `capacity_ladder.<tag>.jsonl`. The receipt records the watcher journal but not the rows path the watcher was pointed at. If the watcher ever polls the wrong file (the `SUSPECT WRONG FILE` shape from `bench_watch`), the journal would still tick and look healthy while reading stale or no rows.
- **Problem:** The contract's R9–R11 checks the journal shape but not that the watcher was reading the *right* file. A misconfigured `--capacity-rows` (e.g. a stale tag from a previous leg) would produce a healthy journal over the wrong file.
- **Proposed change:** Record `watch_argv` (or at least the `--capacity-rows` value) in the receipt and assert it equals `outs["rows"]`.

---

**Beyond the contract:** the candidate is faithful to every R1–R22 behaviour and the ops interface; the harvest/scrub/PII path is sound (F1's `test_a_valid_leg_end_to_end` confirms `$STACK_WORKDIR` substitution and the evidence-stage gets scrubbed logs). The material risks are the live-only assumptions (F1, F3) that no fake can refute, and the frozen-test signature mismatch (F2) that blocks the independent acceptance suite. I would not merge until F1 and F3 are confirmed on a smoke leg and F2 is reconciled with the frozen tests.
