## Cold design review: `spec.md` (TQ4 flash prefill on Neural Accelerators)

Findings below. Locations cite `material/spec.md` line numbers unless noted.

---

**F1 — Blocker — threadgroup-memory budget for BK = 32 is infeasible as stated**
- Location: `spec.md:68-69` ("Per KV tile of BK tokens (free: 16 or 32; threadgroup memory ≤ 32 KB)"); assumption at `spec.md:127`.
- Evidence: confirmed. With BK = 32, D = 256, half codebook values: K tile = 32·256·2 = 16,384 B, V tile = 16,384 B. The spec also requires "the two norm vectors in fp32" (K norms + V norms = 2·32·4 = 256 B) and a codebook (16·2 = 32 B). Subtotal = 32,896 B > 32,768 B (32 KB). This ignores the packed-words staging buffer the same sentence requires ("the threadgroup copies the tile's packed words (coalesced) and unpacks them once into threadgroup memory"): the cooperative coalesced load needs the packed words resident before unpack (32 tokens · 32 words · 4 B = 4 KB for K, 4 KB for V), and unpack cannot be in-place (256 half values = 512 B/token > 128 B/token packed). Statically allocating packed + unpacked + norms blows the budget by ~8 KB at BK = 32.
- Problem: an implementer following "BK free: 16 or 32" literally and choosing BK = 32 hits a threadgroup-memory compile error, or — if they stage packed then overwrite — discovers the static allocation can't be freed mid-kernel. The spec offers an infeasible tile size as if it were free.
- Failure scenario: implementer picks BK = 32 (better arithmetic intensity, fewer tile-boundary masks), kernel fails to compile or spills to device; they fall back to BK = 16 and lose the design's intended tiling headroom, or they drop the norms to fp16 and miss the accuracy bar.
- Proposed change: state the budget explicitly: at 32 KB, BK = 16 is the only viable TQ4 tile with both K and V resident in half plus fp32 norms and codebook (16 KB K + 16 KB V + 256 B norms + 32 B cb = 32,288 B ≤ 32 KB only if one of K/V is staged or norms are fp16); BK = 32 requires staging K and V sequentially (load K → QKᵀ → discard K → load V → PV) or a higher threadgroup-memory limit (verify the actual limit on `applegpu_g17s`; it may be 64 KB). Either drop BK = 32 from "free" or specify the staging discipline that makes it fit.

**F2 — Major — online-softmax masked-value convention is unspecified; literal -∞ → NaN**
- Location: `spec.md:75-77` ("Online softmax per row in fp32 … causal mask only in tiles that straddle a row's position … no NaN for any row"); contrast `context_verify_spec.md:65-67` and the reference `mlx_steel_attention_nax.h:281-320` which uses `Limits<AccumType>::finite_min` and `ExpSubOp = fast::exp2(x - y)`.
- Evidence: confirmed. MLX's `attention_nax` deliberately uses `finite_min` (not `-INFINITY`) and `exp2(x - new_max)` so fully-masked entries contribute 0, never NaN. The prefill spec states the no-NaN outcome but never specifies the sentinel value or the rescale discipline that produces it. With GQA row packing (R = 6 × P rows per threadgroup), a straddling tile has some rows entirely in the future for that tile but not for the threadgroup; those rows see all-masked columns in the mma output. If an implementer masks with `-INFINITY` (the obvious choice) then `exp2(-inf - (-inf)) = NaN` corrupts the row's accumulator the first time the running max is also -inf (early in the sweep, before any visible token).
- Problem: an implementer following the spec literally can produce NaN in early straddling tiles — exactly the A4 edge cases (L = 1, L = 37, q_offset = 0, tile-boundary crossings). The spec asserts no NaN but doesn't give the rule that achieves it.
- Failure scenario: L = 37, q_offset = 0, BK = 16: the first tile (tokens 0-15) is fully visible to rows ≥ 15 but fully future for row 0; mask with -inf → row 0's max stays -inf → first `exp2(score - max)` is NaN → A4 fails on a row that "sees only itself".
- Proposed change: mandate `Limits<float>::finite_min` (or an explicit large-negative sentinel like -1e30) for masked entries, `exp2(x - new_max)` for the rescale, and `max(running, finite_min) = running` so all-masked tiles leave the row's running statistics and accumulator unchanged. Match `attention_nax`'s convention verbatim; add an A4 sub-case that asserts no NaN in a tile that is fully future for at least one row.

**F3 — Major — causal early-exit is per-threadgroup but causal limits vary per row; "skipped per threadgroup" under-skips**
- Location: `spec.md:76` ("tiles entirely in the future are skipped per threadgroup"); rows = R = 6 query heads × P positions (`spec.md:64-66`).
- Evidence: confirmed by reasoning over the row layout. A threadgroup owns rows for P query positions (e.g. P = 16) across all R = 6 heads, at absolute positions [q_offset + tg·P, q_offset + tg·P + P). "Entirely in the future" for the threadgroup means tile start > max query position = q_offset + tg·P + P − 1. But rows within the threadgroup have causal limits ranging over P positions; the straddle region (tile start ≤ max position and tile end > min position) is up to P + BK tokens wide, not BK. The spec's wording reads as if the straddle is one tile, but with P = 16, BK = 16 the straddle is up to 2 tiles, and with P = 16, BK = 32 up to ~1.5 tiles. More importantly, the per-row mask inside the straddle must be computed per (row, column) using each row's own position — `attention_nax` does exactly this at `mlx_steel_attention_nax.h:299-320` (per-fragment `r < c` test). The spec says "causal mask only in tiles that straddle a row's position" which is correct per-row but then says the skip is "per threadgroup", conflating the two granularities.
- Problem: an implementer reading "skipped per threadgroup" may skip tiles based on the threadgroup's max position (correct) but then apply the per-row mask only in the single tile that straddles the threadgroup's *average* or *min* position, missing rows whose causal boundary falls in a tile the threadgroup-level logic deemed "fully visible". Result: leak (future tokens visible to earlier query rows) — and the N2 negative control is designed to catch exactly this, but only on a planted case; a partial leak below the planted threshold passes A3 while being wrong.
- Failure scenario: P = 16, BK = 16, q_offset large. Tile k covers tokens [16k, 16k+16). The threadgroup's rows span positions [tg·16, tg·16+16). Tile tg·16 is fully visible (no mask needed) — correct. Tile tg·16 − 1 straddles rows 0..15 — needs per-row mask. An implementer who masks only the tile equal to the threadgroup's tile index masks tile tg·16 (fully visible, harmless) and leaves tile tg·16 − 1 unmasked → rows 0..15 see 16 future tokens each → silent accuracy degradation not caught by N2 if the planted dominant is at p+1 but the leak is at p−15..p−1.
- Proposed change: specify the causal test per (row, column) inside every tile whose [tile_start, tile_end) intersects (min_row_pos, max_row_pos], and the threadgroup-level skip only for tile_start > max_row_pos. State that the straddle width is P + BK − 1 tokens and that every tile in that window needs the per-row mask. Reference `attention_nax:299-320`.

**F4 — Major — QKᵀ fragment transpose / layout for the NAX mma is unspecified; spike F2's pattern is not the prefill pattern**
- Location: `spec.md:70-72` ("QKᵀ and PV with `BaseNAXFrag::mma` (fp32 accumulators)"); the only mma forms in `mlx_gemm_nax.h:388-528` are (Cn0,Cn1) = A·[Bn0,Bn1] and (Cm0,Cm1) = [Am0,Am1]·B — i.e. the N-column or M-row is split into a pair, never the K dimension.
- Evidence: confirmed. `BaseNAXFrag::mma` is `matmul2d<16,32,16>`: A is 16×16, B is 16×32 (two 16×16 frags Bn0/Bn1), C is 16×32 (two frags). For QKᵀ where Q is (rows × D) and K is (tokens × D), K must be presented as (D × tokens) = Kᵀ. Spike F2 (`spike_f2_nax_matmul.py:78-86`) loads Kᵀ with `F::load(b0, Kp + kk, Int<1>{}, Int<256>{})` — stride_y = 256, i.e. it reads K transposed by treating the token-major K as D-major with stride 256. That works for contiguous bf16 K. For the TQ4 arm, K is unpacked into threadgroup memory; the spec says "Row-simdgroups load their fragments from the tile" but does not specify the threadgroup layout of the unpacked tile (token-major or D-major) or the strides passed to `F::load`. The unpack naturally produces token-major (token, d) half values; `F::load` for the B operand of QKᵀ needs (d, token) = stride_x = 1 (within a token's d-row is NOT stride 1 in token-major) — so the implementer must either unpack into a transposed layout or load with `str_x = D, str_y = 1` reading down a token column. Spike F3 (`spike_f3_tq4_nax_scores.py:64-75`) builds the K fragment in registers per-lane from packed words (no threadgroup tile) and feeds `mma(..., metal::bool_constant<true>{})` (transpose_b = true) — a different approach from the spec's "unpack once into threadgroup memory, shared by all query heads". The spec's chosen approach (threadgroup tile, shared across R = 6 heads) is the right call for amortizing the unpack, but the spec doesn't say how the 6 row-simdgroups each load their QKᵀ B-fragment (Kᵀ) and their PV A-fragment (P) from that tile, given the mma's fixed 16×32×16 shape and the two mma overloads.
- Problem: an implementer must resolve the threadgroup tile layout, the per-simdgroup fragment loads (strides, transpose flags), and the K-narrowing loop (D = 256 = 16 k-steps of 16) on their own. The spec's "as in spike F2" is misleading: spike F2 loads K from device memory with a transposed stride trick that does not apply to a threadgroup-resident unpacked tile, and spike F3 avoids the threadgroup tile entirely. The reference `attention_nax` uses `NAXTile::load` with `K_strides[2]` (device memory, contiguous tokens × D) and `transpose_b = true` (`mlx_steel_attention_nax.h:255-260`) — also a device-memory pattern.
- Failure scenario: implementer unpacks K token-major into threadgroup memory, calls `F::load(kb, Ks + ..., Int<256>{}, Int<1>{})` (the spike F2 device pattern) on threadgroup memory — the strides produce a wrong-layout fragment, QKᵀ is numerically wrong, A1 fails on every sweep case and the cause is not obvious because the kernel "runs".
- Proposed change: specify the threadgroup tile layout (token-major half, D = 256) and the load strides for both QKᵀ (B = Kᵀ: `str_x = D, str_y = 1`, `transpose_b = true`) and PV (A = P: P is computed in registers per-simdgroup, V is B loaded from the V tile with `str_x = D, str_y = 1`, `transpose_b = false`). Note that `NAXTile::load` from threadgroup memory (`mlx_gemm_nax.h:675-687`) takes compile-time strides and is the right primitive, and that the K-reduction loop is 16 steps of 16. Or, if the implementer is meant to choose, say so explicitly and point to `attention_nax:220-265` as the reference for the device case and to the gap (no MLX reference for threadgroup-resident unpacked K) that they must fill.

**F5 — Major — the native16 arm has no NAX-on control and no path to "0.35×" attribution; A5/A6 cannot establish the accelerator is what helps**
- Location: `spec.md:121-123` ("a NAX-off control for the new kernel (its tensor ops have no non-accelerator form; the comparison is against `fused_v1`, which is the shipped NAX path)"); `context_PROBE.md:78-83` (the NAX-off/NAX-on ratio table shows decode/verify ratios ≈ 1.00 — i.e. the existing paths do not use the accelerators except `fused_v1`).
- Evidence: confirmed. The probe's own NAX-off control (`MLX_METAL_GPU_ARCH=applegpu_g16s`) shows decode TQ4 ratio 0.98-1.02 and verify TQ4 0.97-1.04 — the existing TQ4 paths are accelerator-agnostic. The whole premise of the goal is that `fused_v1` (native16) uses the accelerators and TQ4's shipped path does not, so a NAX-backed TQ4 closes the gap. But the spec explicitly declines a NAX-off control for the new kernel (Non-goals, `spec.md:121-123`). Without a NAX-off run of `p2_tq4`, the operator cannot distinguish "the NAX fragment got us to 0.7×" from "a better-tiled non-NAX kernel would have gotten us to 0.7× anyway, the accelerators are irrelevant at this shape." Spike F2 (`spike-f2-nax-matmul.log`) is the only evidence the accelerators matter: stage 3 (in-register MMA, compute-bound) shows NAX at 58.7 TFLOPS vs simdgroup 8x8 at 15.9 TFLOPS (3.7×), but stage 2 (the actual QKᵀ with K from device memory) shows NAX and simdgroup at parity (1.00×) — i.e. at the prefill shape, the kernel is memory-bound and the accelerator's compute advantage does not show up. The spec's headline 0.35× gap is a memory-bandwidth gap (TQ4 reads 4× less but the shipped path doesn't tile), not a compute gap.
- Problem: the spec builds a NAX-backed kernel and measures it against `fused_v1`, but declines the one control that would attribute the gain to the accelerators. Given spike F2 stage 2 shows NAX = simdgroup at this shape, a simdgroup 8×8 flash kernel (no accelerators) would likely score the same — so the prototype may "succeed" (hit some ratio) while the accelerators contribute nothing, and the operator's stated reason for the gap ("TQ4 doesn't use the ANs") is never actually tested. The goal's causal claim is unprovable from the spec's measurements.
- Failure scenario: `p2_tq4` measures 0.7× of `fused_v1`. Operator concludes "the Neural Accelerators closed the gap." A later simdgroup-only port measures 0.68×. The prototype's whole premise was misattributed; the real win was tiling + reading packed indices in place, not the ANs.
- Proposed change: either (a) add a NAX-off control for `p2_tq4` by building the same kernel with `simdgroup_multiply_accumulate` (8×8) instead of `BaseNAXFrag::mma` — the spec's claim that "its tensor ops have no non-accelerator form" is false: the same flash structure runs on simdgroup MMA, as spike F2 stage 2 demonstrates; report the NAX-on/NAX-off ratio for `p2_tq4` as a seventh timing column; or (b) if a second kernel is out of scope, downgrade the goal's causal claim to "a tiled in-place TQ4 flash kernel" (not "a NAX kernel") and add a scope-request note that the accelerator attribution is unmeasured. I lean (a): the control is one extra `mma` template parameter, not a new design.

**F6 — Major — the fp32 reference at 260K is unbounded; the existing probe skipped the analogous path at 131K for memory**
- Location: `spec.md:88-89` (fp32 reference); A1 at `spec.md:108` ("every checkpoint head"); `context_PROBE.md:54-58` (prefill `tq4_decomposed` skipped at T ≥ 131072 with note "memory: fp32 scores … GB"); `context_probe_measure_checkpoint.py:118-120` (the skip branch).
- Evidence: confirmed. The existing probe refuses to materialize fp32 scores for the *production* prefill path at T ≥ 131K (`skipped (memory)`), and `context_PROBE.md:54-58` shows exactly that. The spec's fp32 reference for A1 at the 262,144 checkpoint is the same shape (24 q × 512 L × 262K T × 4 B = 12.6 GB for full scores, or 3 heads × 512 × 262K × 4 = 1.6 GB for the evaluated heads) plus dequantized K/V in fp32 (262K × 256 × 4 kv × 2 (K+V) × 4 B = 2.1 GB). The spec scopes A1 to "three query heads {0, 11, 23} (all rows)" (`spec.md:86`), which brings scores to ~1.6 GB — feasible on a 64 GB M5 Max — but the spec never states the reference is computed per-head-only or streamed; an implementer reading "exact causal softmax per head" may build a full 24-head reference (12.6 GB scores) and OOM at the largest checkpoint, exactly as the production path did. The spec also doesn't say whether the reference dequantizes the *full-cap* buffer or slices to `q_offset + L` first; slicing is required to keep it bounded.
- Problem: an implementer following "fp32 reference: codec.dequantize of K/V; exact causal softmax per head" literally materializes a full-head, full-cap reference and hits the same memory wall the probe already documented, making A1 unmeasurable at the goal's headline context (260K) — the one checkpoint the operator cares about.
- Failure scenario: implementer builds `ref = softmax(Q @ dequantize(K,V)ᵀ) @ V` over all 24 heads and the full cap at T = 262,144; peak ~15 GB; on a 48 GB machine OOMs; on a 64 GB machine it runs but dominates measurement time and the operator can't tell kernel time from reference time in the JSON.
- Proposed change: pin the reference to (a) the three evaluated heads only, (b) K/V sliced to exactly `q_offset + L` tokens before dequant, (c) per-head streaming (compute head h's reference, compare, discard). State the reference's peak memory in `meta.p2_accuracy` and assert it is < the kernel's `peak_GB`. Mirror `context_verify_spec.md:131-134`'s "sliced to `lengths[-1]`" discipline.

**F7 — Major — the projection method double-subtracts and is undefined at the baseline context**
- Location: `spec.md:101-103` ("t(N) = f·N + 16 · Σ_chunks attn(T_j) [+ TQ4 append]; f from the pick's measured time minus 16 · Σ native16 attention").
- Evidence: confirmed by reading the formula. `f` is defined as "the pick's measured time minus 16 · Σ native16 attention" — i.e. `f·N = (pick_prefill_s − 16·Σ attn_native16)`, the non-attention per-token cost inferred from the pick baseline. Then `t(N) = f·N + 16·Σ_chunks attn(T_j)`. For the *native16* arm this is tautological at the pick's context (it reproduces the pick), which is fine. But for `p2_tq4` and `tq4_production`, the formula reuses the *native16-derived* `f` (the non-attention per-token cost) and only swaps the attention term. That assumes the non-attention per-token cost (projections, MLPs, layernorms, the KV append) is identical between a native16 run and a TQ4 run. It is not: the TQ4 append (`context_PROBE.md:54-58`, "KV append 512 tok TQ4 / n16" column) is a measurable extra term the spec itself adds as "[+ TQ4 append]" — so the TQ4 arm adds the append once explicitly and *also* carries it inside the native16-derived `f`, double-counting it. Conversely, native16's append is in `f` and not added back, which is correct for native16 but inconsistent with the TQ4 arm.
- Problem: the projection for `p2_tq4` and `tq4_production` double-counts the TQ4 KV append (once in `f`, once in "[+ TQ4 append]"), overstating TQ4 prefill time and understating the TQ4/native16 ratio — the very number the operator will read to judge "how far TQ4 prefill gets toward parity." The error is small at short context (append is cheap) and grows with N.
- Failure scenario: at 260K, `f` carries ~0.27 ms/chunk of TQ4 append from the pick (per `context_PROBE.md` row T=260096: 0.27 ms), and the explicit "[+ TQ4 append]" adds another 0.27 ms/chunk × 16 chunks ≈ 4.3 ms; the projected TQ4 prefill is ~4 ms too slow; the reported ratio is 0.05 worse than reality; operator misjudges the prototype.
- Proposed change: define `f` per arm — `f_arm = (pick_prefill_s − 16·Σ attn_arm) / N` for the arm whose attention is being projected, or define `f` as the *native16 non-attention, non-append* cost and add the append per arm explicitly. State which. Make the "[+ TQ4 append]" term apply only to TQ4 arms and confirm it is not already in `f`. Add a unit test (the report generator is already tested on synthetic JSON, `spec.md:96`) that asserts the projection reproduces the pick's measured prefill time at the pick's context for the native16 arm (tautology check) and is monotonic in N.

**F8 — Major — `_kv_head_shift` negative control is weak for GQA R = 6; N1 may pass A1 by accident**
- Location: `spec.md:59` ("`_kv_head_shift` (negative control): query heads of KV group g read KV head (g + shift) mod n_kv"); A3 at `spec.md:111` ("N1–N3 fail A1 on both arms"); `spec.md:30` (n_kv = 4, R = 6).
- Evidence: hypothesis. With n_kv = 4 and R = 6, shifting KV head by 1 maps group g to KV head (g+1) mod 4. The four KV heads hold different codebooks/norms (TQ4) and different K/V (native16). Whether the shifted output differs from the reference by more than 2×max(prod_err, 2⁻¹²) with `allclose(atol=rtol=3e-2)` depends on how similar adjacent KV heads' K/V distributions are. The probe uses *synthetic* K/V (`spec.md:39`, "synthetic K / V"). If the synthetic generator fills all KV heads with i.i.d. normal data of the same scale, the shifted attention output is statistically very close to the unshifted one — the softmax over the same-shape random scores produces a similar weighted sum of similar-shape random values, and the relative error may land under 3e-2. The control is designed to *fail* A1; if it passes, A3 is violated and the prototype is rejected, but for a bad reason (the control is too weak for synthetic same-distribution data), masking a real bug or producing a false rejection.
- Problem: N1's discriminating power depends on KV heads being distinguishable, which the spec's "synthetic K/V" does not guarantee. An implementer may build a correct kernel and find N1 passes A1 (false A3 failure) because the synthetic data makes adjacent KV heads interchangeable; or a buggy kernel may pass N1 because the bug is also invariant across KV heads.
- Failure scenario: synthetic K/V drawn i.i.d. normal per head with the same scale; `_kv_head_shift=1` output rel-err vs reference ≈ 2e-2 < 3e-2 allclose → N1 `pass = True` → A3 reports "controls did not fail" → prototype rejected despite being correct; or the implementer "fixes" it by perturbing the kernel until N1 fails, introducing a real bug.
- Proposed change: make the synthetic K/V per-KV-head distinguishable (e.g. distinct scales or a planted dominant key per KV head, as is already done for the planted-token cases), and assert in the sweep setup that the unshifted-vs-shifted reference outputs differ by more than the A1 tolerance *before* running the kernel (a data-level precondition, not a kernel check). Or strengthen N1 to a shift that is guaranteed to differ (e.g. swap two KV heads' contents and assert the outputs differ). The verify spec's N1 has the same issue; flag it there too.

**F9 — Minor — `positions_per_tg` and `block_tokens` interface args are unused by the design and unexplained**
- Location: `spec.md:48-49` (the signatures `*, block_tokens=None, positions_per_tg=None`); the Design section (`spec.md:64-79`) never references either parameter.
- Evidence: confirmed. The design fixes "one threadgroup per (KV head g, block of P query positions)" with P free but chosen at build time, and BK free at build time. `block_tokens` and `positions_per_tg` are not mentioned in the design, not recorded in `meta.p2_kernel` (`spec.md:95` lists only "BK, P, WN, mapping check"), and not in the JSON schema. They appear to be vestigial from the verify spec's `plan_blocks` interface (which the prefill design replaces with "no split over tokens").
- Problem: an implementer must decide whether these are tuning knobs (then they should be in `meta.p2_kernel` and the report) or dead parameters (then they should be removed). Leaving them in the signature invites the implementer to wire them into the kernel without the spec's design accounting for them.
- Failure scenario: implementer treats `positions_per_tg` as the runtime P, builds a dynamic-P kernel (much harder, defeats the NAX fragment's compile-time tile sizes), and the spec's "P free (e.g. 16)" static-tiling design is silently abandoned.
- Proposed change: drop both parameters from the signatures, or specify them (defaults, effect, recorded in `meta.p2_kernel`). I'd drop them — the design is static-tiled.

**F10 — Minor — A5's "peak memory above the live arrays < 0.4× the K/V bytes read" is unmeasured and the threshold is unjustified**
- Location: `spec.md:116` ("No layout copy or materialized K / V (peak memory above the live arrays < 0.4 × the K / V bytes read)").
- Evidence: confirmed. The JSON schema (`spec.md:95-97`) records `peak_GB` per checkpoint but the spec never says how `peak_GB` is measured (MLX's allocator watermark? `mx.get_peak_memory`? a manual accounting?), nor what "the live arrays" are (Q? the output? the fp32 reference for A1?), nor why 0.4. The 0.4 threshold would allow, at T = 262K, a peak of 0.4 × (TQ4 K/V bytes ≈ 34 MB × 2 = 68 MB) = 27 MB of scratch — far more than the threadgroup tiles (32 KB × threadgroups) and far less than any dequantized materialization (2 GB). So 0.4 either passes trivially (if scratch is just threadgroup memory) or fails trivially (if the fp32 reference is counted in peak). The criterion's discriminating power is undefined.
- Problem: an implementer cannot implement A5 without a measurement method, and the 0.4 threshold is arbitrary. A kernel that materializes a 256 MB dequantized tile (a real bug) would pass if `peak_GB` only counts the allocator watermark and the tile is freed before the measurement; a kernel that holds an extra 30 MB of Q in device memory (benign) would fail.
- Failure scenario: implementer uses `mx.get_peak_memory()` which includes the fp32 reference (1.6 GB at 260K for 3 heads), A5 fails (1.6 GB > 0.4 × 68 MB = 27 MB), prototype rejected for a measurement artifact.
- Proposed change: define `peak_GB` as the MLX allocator watermark *during the kernel call only* (exclude the reference, which is computed in a separate scope), define "live arrays" as the inputs + output, and set the threshold to a value tied to the design (e.g. < 2× the threadgroup tile memory × threadgroup count, or an absolute 1 GB). Or drop A5 and rely on the design's "no dequantized K/V outside the kernel" rule enforced by a static check (no `mx.contiguous`/`dequantize` call on the kernel path).

**F11 — Minor — `fragment_mapping_ok` is required but its check semantics are underspecified**
- Location: `spec.md:51` (`fragment_mapping_ok() -> bool`), `spec.md:71` ("Row-simdgroups load their fragments from the tile"); the verify spec at `context_verify_spec.md:73` says "verify it with a unit test before relying on it (MLX steel's mapping is a reference, not a given)" and aborts the probe on failure (`context_verify_spec.md:86`).
- Evidence: confirmed. The prefill spec lists `fragment_mapping_ok()` in the interface but never says what it checks (the element → (row, col) mapping of `BaseNAXFrag`, per the goal's wording), how it checks it (a unit kernel that writes each lane's `get_coord()` to a buffer and compares?), when it runs (before the probe? per the verify spec's "abort exit 6 before any measured work" — the prefill spec doesn't say), or what happens on failure. The prefill spec's `meta.p2_kernel` records "mapping check" but the launcher (`spec.md:99`) and report don't mention an abort. The spike F2/F3 code relies on `F::get_coord(i)` (per-element) and `F::get_coord()` (lane's first element) — both used in the spikes without an explicit check.
- Problem: an implementer may ship a stub `fragment_mapping_ok() -> True` (no test) and a wrong mapping assumption, producing a kernel that transposes rows/cols silently — A1 catches it (wrong numbers) but the cause is obscured because the mapping check passed.
- Failure scenario: implementer assumes `get_coord()` returns (row, col) but it returns (col, row) per `mlx_gemm_nax.h:48-49` (`return short2{fn, fm}` where fn is the column, fm is the row); the stub `fragment_mapping_ok` returns True; QKᵀ writes S transposed; A1 fails everywhere; implementer debugs numerics for hours instead of the mapping.
- Proposed change: specify the check (a kernel that writes `get_coord(i)` for all 8 elems of each lane to a (32, 2) buffer, compared to the reference table from `mlx_gemm_nax.h:46-58`), require it to pass before the probe runs (abort exit 6 like the verify spec), record its result in `meta.p2_kernel.fragment_mapping_ok`, and have the report refuse to combine passes where it was False.

**F12 — Minor — the spec leans on spike F3's "fastest form" (threadgroup codebook lookup) but F3's log shows `tq4_stage` (staged packed) was fastest, not `tq4_tgcb`**

**F13 — Minor — "no split over tokens" claim under-counts threadgroups at small L and large T**
- Location: `spec.md:78` ("No split over tokens: a threadgroup sweeps all tokens for its rows (prefill has 4 · 512 / P threadgroups per chunk — enough parallelism)").
- Evidence: confirmed by arithmetic. Threadgroups per chunk = n_kv (4) × ceil(L / P) × (1 if no head-dim split, or WN if split) = 4 × ceil(512/P) × (1 or 2). With P = 16, WN = 1: 4 × 32 = 128 threadgroups. M5 Max has ~40 SIMD-groups per GPU × many cores; 128 threadgroups is fine for one chunk. But the design says the threadgroup "sweeps all tokens for its rows" — at T = 262,144 and BK = 16, that's 16,384 KV tiles per threadgroup, each tile a QKᵀ + softmax + PV. With P = 16 rows per threadgroup, the threadgroup does 16 × 262K = 4.2M output element-updates — a long-running serial sweep with no cross-threadgroup reduction. That's correct for flash attention, but the "enough parallelism" claim is about threadgroup count, not about the per-threadgroup work being long enough to hide launch overhead. At L = 1 (A4 edge case, q_offset large), threadgroups per chunk = 4 × 1 × 1 = 4 — far too few to fill the GPU; the L = 1 prefill case will be launch-bound and its timing meaningless, yet A4 requires it to "complete with A1-A4 recorded."
- Problem: at L = 1 the kernel launches 4 (or 8) threadgroups, each sweeping 262K tokens — a pathological case that is neither representative of prefill nor fairly comparable to `fused_v1` (which at L = 1 is a decode). The spec includes L = 1 in the accuracy sweep (`spec.md:84`) for A4 (edges, no NaN) — fine for accuracy — but the per-checkpoint timing table (`spec.md:87`) records `p2_tq4` and `p2_native16` times at each checkpoint T, and at L = 512 only; the L = 1 timing is not in the projection but the implementer may be tempted to time it and the operator may read it.
- Failure scenario: operator reads the L = 1 row (if the implementer adds one) and sees `p2_tq4` at 50× `fused_v1` — a launch-overhead artifact, not a kernel defect — and misjudges the design.
- Proposed change: clarify that L = 1 is an accuracy-only edge case (A4), never timed or projected; timing is L = 512 only. State the threadgroup count formula with WN and note it is adequate at L = 512, not at L = 1.

**F14 — Scope request — require a simdgroup-MMA fallback variant for attribution and as a rescue path**
- Location: whole spec; motivated by F5.
- The goal's causal claim is "TQ4 prefill loses because it doesn't use the Neural Accelerators." Spike F2 stage 2 (`spike-f2-nax-matmul.log:7-9`) shows NAX and simdgroup 8×8 at parity (1.00×) for the actual QKᵀ shape (memory-bound), and only stage 3 (compute-bound, in-register) shows the 3.7× NAX advantage. The prefill kernel at D = 256, BK = 16-32 is almost certainly memory-bound on K/V read, not compute-bound — so the accelerators may not be the win. I'd require the implementer to build the kernel with a compile-time switch between `BaseNAXFrag::mma` and `simdgroup_multiply_accumulate` (same flash structure, same loaders), run both as `p2_tq4_nax` and `p2_tq4_sg`, and report the NAX-on/NAX-off ratio. This is the only measurement that tests the goal's premise. It is one template parameter, not a second design. Without it, the prototype cannot answer the question it was commissioned to answer.

**Summary**

Blockers: F1 (BK = 32 threadgroup-memory infeasible).
Majors: F2 (masked-value/NaN convention), F3 (per-threadgroup vs per-row causal skip), F4 (QKᵀ/PV fragment layout & transpose unspecified), F5 (no NAX-off control → goal's causal claim unmeasurable), F6 (fp32 reference unbounded at 260K), F7 (projection double-counts TQ4 append), F8 (N1 control too weak for synthetic same-distribution KV).
Minors: F9 (dead interface args), F10 (A5 peak-memory method & threshold undefined), F11 (`fragment_mapping_ok` semantics underspecified), F12 (F3 "fastest form" mislabeled), F13 (L = 1 parallelism/launch artifact).
Scope request: F14 (simdgroup-MMA fallback for attribution).

The spec's biggest risk is that it builds a correct, measurable NAX kernel that "succeeds" by A1-A7 while leaving the operator's actual question — *is it the Neural Accelerators that close the gap* — unanswerable (F5), and that an implementer following it literally hits a compile wall at BK = 32 (F1) or produces NaN at the A4 edge cases (F2) before reaching the measurement.
