### F1 — Blocker: the bit-identity contract with `rot_fused()` is not achievable as written

- **Location:** `spec.md` lines 47–53 (interface), lines 100–102 (A1).
- **Severity:** blocker.
- **Evidence:** confirmed. The probe's `rot_fused()` (`context_probe_excerpt.py:209–213`) computes `qr = tq.key_codec.prepare_queries(qp).astype(DT)` and then calls `mx.fast.scaled_dot_product_attention(qp, k, v, …)` — it passes `qp`, not `qr`. The spec's `scratch_prefill_tq4` interface (line 49) passes `key_codec.prepare_queries(queries).astype(bf16)` to SDPA. `context_verify_spec.md:50` confirms `prepare_queries` is the query rotation (`q' = cache.key_codec.prepare_queries(queries * scale)`), i.e. non-identity. So the spec and the probe send different `q` tensors into the same SDPA call. With RHT rotation orthogonal but non-trivial, `SDPA(qR, kR, vR) ≠ SDPA(q, kR, vR)`; the two outputs cannot be bit-identical.
- **Failure scenario:** The implementer follows the interface literally (rotates queries via `prepare_queries`), runs A1, and `scratch_prefill_tq4` vs `rot_fused()` is not bit-identical. A1 fails on every checkpoint. The implementer has no way to satisfy the contract without choosing between the spec's formula and the probe's code, and the spec gives no tiebreaker.
- **Proposed change:** Pick one and state it explicitly. Either (a) the probe's `rot_fused()` has a bug (`qr` computed and discarded) and the spec is correct — then A1's "bit-identical to `rot_fused()`" must be relaxed to "bit-identical to the corrected `rot_fused()` using `qr`", and the probe must be fixed first so the reference exists; or (b) the probe is the ground truth and the interface should pass `queries` (not `prepare_queries(queries)`) to SDPA, matching the probe. Given the math comment (`q·k = (qR)·(kR)`) and the verify spec both say the query must be rotated, (a) is the defensible choice — but it makes the probe's existing `rot_fused_vs_production` numbers (PROBE.md, ~5e-3 rel) a measured bug, which the operator should be told. Either way the spec must reconcile the two and stop leaving it to the implementer.

### F2 — Major: A4's memory budget omits the SDPA intermediates that dominate peak at 260K

- **Severity:** major.
- **Evidence:** confirmed. A4 bounds `peak − active_before ≤ 1.25 × one scratch + 0.25 GB`, where "one scratch = 2·4·T·256·2 B" is only the dequantized K/V. But `scratch_prefill_tq4` also runs MLX's fused SDPA, which allocates its own working set. `context_PROBE.md` line 65 reports peak 8.0 GB at T=262144 for the rotated-fused prefill, against a scratch of 1.07 GB and a TQ4 state of ~0.27 GB — i.e. ~6 GB of SDPA-side allocation that A4's formula does not account for. - **Failure scenario:** Implementer builds the kernel correctly, scratch recycles perfectly (one scratch steady-state), but the 16 SDPA intermediates push peak to e.g. 4 GB above `active_before`. A4 fails. The operator is told the prototype leaks memory when in fact it satisfies C314's actual constraint (one dequant scratch, reused).
- **Proposed change:** A4 should bound the *scratch contribution* specifically: measure peak with and without the dequant (or subtract a baseline that runs `rot_fused`'s SDPA alone at the same T), and bound only the incremental peak attributable to the dequant scratch to `1.25 × one scratch + 0.25 GB`. Alternatively, measure the dequant-only peak (`p2s_dequant_only` already exists as an arm) and bound that. State explicitly that SDPA-side allocation is out of scope for A4, matching C314's actual settlement (which is about the dequant scratch, not SDPA).

### F3 — Major: codebook dtype in the kernel is unspecified, threatening the bit-identity contract

- **Location:** `spec.md` lines 59–62 (Design).
- **Severity:** major.
- **Evidence:** confirmed. The probe's `deq_rot()` does `mx.take(codec.codebook, idx, axis=0) * st.norms[..., None]` where `codec.codebook` is fp32 (`_codebook` returns fp32, `context_turboquant_excerpt.py:355–356`) and `st.norms` is fp16, promoting the product to fp32, then `.astype(bf16)` — one rounding. The spec says "fp32 product, one rounding to bf16 (the bit-identity contract fixes this)" but leaves the codebook storage as free ("the codebook in threadgroup memory or registers (free; spike F3: lookup mechanism matters little)"). If the implementer stores the 16-entry codebook as half/bf16 in threadgroup memory (a natural choice to save registers), the `take` result is half, the product is half×fp16→fp16 (or promoted to fp32 from half operands, but with half-rounded codebook values), and the output diverges from the probe's fp32-codebook path. "Lookup mechanism matters little" is about timing, not about bit-identity; conflating the two is the defect.
- **Failure scenario:** Implementer stores the codebook as half in threadgroup memory for coalescing. A1 exactness sweep fails on every row with small but non-zero diffs, and the implementer chases rounding that is actually caused by the codebook dtype.
- **Proposed change:** Add to the Design section: "The codebook values used in the product must be fp32 at the point of multiplication (load from the fp32 `codec.codebook` and do not downcast), to match `deq_rot()`'s `mx.take` on the fp32 codebook. Threadgroup storage of a half-cast copy is allowed only if it is upcast back to fp32 before the multiply — but that changes the value and is NOT allowed under A1." Make F3 a spike about timing only, with the dtype pinned.

### F4 — Major: causal-mask semantics for L queries over T keys (L < T) are unstated and not obviously correct

- **Location:** `spec.md` lines 49–52 (interface), line 121 (Assumptions).
- **Severity:** major.
- **Evidence:** hypothesis (traceable). The chunk is L=512 queries at positions [T−L, T) over T keys at [0, T). MLX's `mask="causal"` with L < T must mean "query i (at global position T−L+i) attends to keys [0, T−L+i]" for this to match the production path's prefill-chunk semantics. The spec only says `mask="causal"` and the Assumptions section only asserts determinism, not the mask's positional interpretation. An implementer who reads "causal" as the standard lower-triangular mask (query i attends to key j iff j ≤ i) would build something that attends to only the first i+1 keys — wrong for every chunk after the first. The probe's `rot_fused()` relies on whatever MLX does here; the spec must state what that is, because the implementer is building from this spec alone and cannot see the probe's behavior.
- **Failure scenario:** Implementer, unsure whether MLX's causal mask offsets by T−L, adds an explicit additive mask "to be safe" that duplicates MLX's offset, double-masking the chunk. A1 fails. Or they trust the lower-triangular reading and the kernel is silently wrong on every chunk past the first (only T=L=512 is correct), which A1's sweep at T∈{1,511,512,…} would partially catch but the spec doesn't flag as the thing to look for.
- **Proposed change:** Add to Assumptions, explicitly: "MLX's `mx.fast.scaled_dot_product_attention(..., mask='causal')` with L query positions and T key positions (L ≤ T) applies the mask 'query i attends to key j iff j ≤ i + (T − L)', i.e. the L queries are taken to be the last L positions over the T keys. The spec relies on this; if MLX changes it, A1 will break and the mask must be supplied explicitly." Add an A3 edge at T=L (the only case where the offset is zero) vs T≫L to make the offset exercised.

### F5 — Major: the projection formula's append term is mis-scoped and the `fixed` term double-counts append

- **Location:** `spec.md` lines 96–98 (Projection).
- **Severity:** major.
- **Evidence:** confirmed. The formula is:
  `fixed = prefill_s(N) − 16 · Σ_j native16_fused_v1(T_j)`
  `t_X(N) = fixed + 16 · Σ_j X(T_j) + [X is TQ4] · 16 · (N/512) · (append_tq4 − append_native16)`
  Two problems. (1) `prefill_s(N)` for the *native16* baseline already includes the native16 append cost per chunk. `native16_fused_v1(T_j)` is the *attention* time only (the probe's prefill chunk arm is SDPA-only, no append). So `fixed` absorbs the native16 append cost (plus everything non-attention). Then for a TQ4 arm, the formula adds `16·(N/512)·(append_tq4 − append_native16)` — the *delta* of append. That is correct for the delta. But `fixed` also contains `16·(N/512)·append_native16` (the absolute native16 append, inside `prefill_s`), and the projection never removes it for the native16 check arm. So `t_native16(N) = fixed + 16·Σ_j native16_fused_v1(T_j) = prefill_s(N)` by construction — the "Check: t_native16 reproduces prefill_s(N)" is tautological and validates nothing. (2) The probe's own report (`context_probe_report_excerpt.py:73–77`, `prefill_attn_total_s`) uses `LAYERS * sum(interp(...))` with no append term at all and validates against P475 with 6–8% error; the spec's formula adds an append delta that the probe's validation never tested, so the projection's accuracy at 260K is unvalidated.
- **Failure scenario:** The implementer codes the formula as written. The native16 check passes trivially (it's `prefill_s(N)` by definition), giving false confidence. The TQ4 projection at 260K includes an append delta extrapolated from `kv_append_chunk_ms` "means at long context" — but the probe's append measurement is per-chunk at fixed checkpoints, and the spec doesn't say which checkpoint's append number to use or how it scales with T. The reported `t_p2s(N)/native16` ratio at 260K is sensitive to this un-specified choice.
- **Proposed change:** (a) Make the native16 check non-tautological: define `fixed` from a *non-append* baseline (e.g. `prefill_s(N) − 16·(N/512)·append_native16 − 16·Σ_j native16_fused_v1(T_j)`) and then reconstruct `t_native16(N) = fixed + 16·(N/512)·append_native16 + 16·Σ_j native16_fused_v1(T_j)`, checked against `prefill_s(N)`. (b) Specify exactly which `kv_append_chunk_ms` field (the spec references `context_probe_report_excerpt.py`'s `ap('tq4_mean_last64')` / `ap('native16_mean_last64')` but the projection text says "the probe's measured `kv_append_chunk_ms` means at long context" without naming the field or the T). Pin it to a named checkpoint or interpolation.

## Summary

- **Blocker (F1):** the bit-identity contract is internally inconsistent — the spec's interface rotates queries via `prepare_queries` before SDPA, the probe's `rot_fused()` does not. One of them is wrong; the spec must pick and the probe may need fixing.
- **Majors (F2–F6):** A4's memory budget ignores the SDPA intermediates that dominate peak at 260K; the codebook dtype in the kernel is unspecified and can break bit-identity; the causal-mask offset semantics for L<T are unstated; the projection's `fixed` term makes the native16 check tautological and the append term is under-specified; the fp32 reference at T=262144 is unbudgeted and may collide with A5.
- **Minors (F7–F9, F11–F12):** negative-control shift semantics, A3 edge, A5 identity check, report provenance, dequant-share labeling.
- **Scope request (F10):** pin that the rotation is RHT for D=256.

The kernel itself (one fused Metal dequant, fp32 codebook product, one bf16 rounding, rotation outside) is sound and buildable; the failures are in the contract, the measurement criteria, and the projection — exactly the surfaces an implementer working from this spec alone cannot recover.
