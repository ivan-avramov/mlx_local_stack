## Findings

### 1. `read_worker_log` reads the worker's STDERR file; the `KV cache resolved:` line is a `logger.info` line that goes to `logs/mlx_vlm.log`, not to `$TMPDIR/mlx-manager-logs/<model>.log`
**Location:** `benchmark/bench/p475_kv.py:2008-2010` (`read_worker_log`), used at `p475_kv.py:1007` (`wait_kv_line`) and `p475_kv.py:2038` (harvest `log_slice`).
**Severity:** blocker.
**Problem:** `read_worker_log` returns `Path(ops.tmpdir) / "mlx-manager-logs" / f"{model}.log"`. That file is where mlx-serve redirects the worker's **stderr** (`benchmark/m1/p1a_opencode_smoke.sh:11` cites `process_manager.py:387`; `docs/serving-path.md:13` confirms "only stderr reaches `$TMPDIR/mlx-manager-logs/<model>.log`"). The `KV cache resolved:` line is emitted by `logger.info(...)` in `mlx-vlm/mlx_vlm/server/app.py:950`. With `env_base()` setting `MLX_VLM_LOG_FILE=logs/mlx_vlm.log` (`chain_ops.py:266`), `mlx-vlm/mlx_vlm/server/cli.py:700-710` configures `logging.basicConfig(filename="logs/mlx_vlm.log")` — a FileHandler only, no stderr StreamHandler. The fork's own comment at `mlx-vlm/mlx_vlm/server/generation.py:168-172` states this explicitly: `logger.info` "normally routes to stdout" and mlx-serve sends stdout to DEVNULL, so sibling startup evidence has to be re-printed to stderr to reach `mlx-manager-logs`; the `KV cache resolved:` line is **not** re-printed to stderr. So the line lives in `<arm worktree>/logs/mlx_vlm.log` (the worker's cwd is the router's cwd, set by `start_router`'s `popen(cwd=str(self.repo))`), which is exactly where the rest of the harness reads it (`benchmark/chains/m59/run_m59.py:254` reads `REPO/"logs/mlx_vlm.log"`; `p426_leg.py:730` uses `repo/"logs/mlx_vlm.log"`). No test exercises the real path — `Rig.read_worker_log` is mocked to return `self.log_line` (`test_p475_kv.py:318`), and the round-3 test that "awaits" the line (`test_p475_round3.py:657-673`) feeds logs from an iterator. The implementer's report discloses `--kv-arm` as "verified only against fakes" but does not flag this.
**Failure scenario:** The first fable-N16 leg loads. `wait_kv_line` polls `receipts/fable-N16-b1/tmp/mlx-manager-logs/<model>.log` every 2 s for 60 s. That file holds the worker's stderr (mlx-serve startup banner, `moe_expand=` lines re-printed to stderr) but no `KV cache resolved:` line — it is in `<arm worktree>/logs/mlx_vlm.log`. After 60 s `wait_kv_line` returns `["no \`KV cache resolved:\` line in the worker log"]`, the pre-driver check fails, the stack is torn down, the leg is INVALID, and `run` stops on leg 1 with rc 1. The operator sees "no KV cache resolved line" and diagnoses a codec failure that is actually a wrong-file read. The smoke leg (acceptance criterion 2) fails the same way, so the full run never starts.
**Proposed change:** `read_worker_log` should read `Path(ops.repo) / "logs" / "mlx_vlm.log"` (the worker's `logger` file, as `run_m59`/`p426_leg` already do for the same evidence), or read both files and judge the union. The harvest `log_slice` should be taken from the same file. Add a test that points `read_worker_log` at a real `logs/mlx_vlm.log` containing the frozen `LINE` and a `mlx-manager-logs/<model>.log` containing only stderr, and asserts the line is found.

### 2. The strict ladder's rate reconciliation is a new validity rule beyond the specification; it refuses a rung when the backend's `prompt_per_second` and `prompt_ms` come from independent instrumentation paths even though both are "the backend's own"
**Location:** `benchmark/bench/capacity_ladder.py:33-44` (`_reconcile`), called at `capacity_ladder.py:64-66` inside `p475_rung_problems`.
**Severity:** major.
**Problem:** The spec (Stage 1, "Instrument" bullet) requires persisting and using the backend's own `prompt_ms`, `prompt_per_second`, `prompt_n` and `cache_n`; it does **not** require that `prompt_per_second == prompt_n / (prompt_ms/1000)`. The candidate adds a 2% reconciliation as a rung-validity rule. I verified against the fork (`mlx-vlm/mlx_vlm/server/schemas.py:528-545`): `prompt_per_second = prompt_n / prompt_s` and `prompt_ms = prompt_s * 1000` where `prompt_s = prompt_tokens / metrics.prompt_tps`, so the two are derived from the same `metrics.prompt_tps` and reconcile exactly — **for prompt**. For decode, `predicted_per_second = float(generation_tps)` and `predicted_ms = output_tokens / generation_tps * 1000`, also derived from the same `generation_tps`. So on the current fork the check passes. But the check is a coupling to the fork's internal derivation: if a future fork maintenance change makes `metrics.prompt_tps` and `metrics.rate` independent (e.g., `rate` from a per-token timer and `prompt_tps` from a prefill timer), every rung is refused and the run stops. The spec's "backend prefill timings" did not ask for this guard, and the 2% tolerance is a judgment call the operator never signed off.
**Failure scenario:** A maintenance change to the fork's `GenerationMetrics` splits `prompt_tps` (prefill wall) from `rate` (per-token) so they disagree by 4%. The first fable-N16 rung's `prompt_per_second` no longer reconciles with `prompt_n / (prompt_ms/1000)` within 2%. `p475_rung_problems` returns "backend prompt_per_second … does not reconcile", the rung is invalid, the ladder breaks at rung 1, the leg is INVALID, the run stops on leg 1. The operator sees a "backend rate mismatch" that the spec never required and that a single `--p475-strict` opt-out cannot relax.
**Proposed change:** Either drop the reconciliation (the spec asks to persist and use the backend's numbers, not to cross-check them against each other), or make it a speed problem (rerun) rather than a rung-invalid (stop), or document it as a deliberate guard and add a flag to relax it. At minimum, record in the spec that the ladder refuses a rung whose backend rates do not self-reconcile, so the operator knows the run depends on that coupling.

### 3. `teardown_verified` proves the worker gone by a name-based `worker_cmdlines(model)` scan, not by the recorded pid; a same-model worker from any source makes every teardown fail
**Location:** `benchmark/bench/chain_ops.py:705` (`worker_gone=not (model and self.worker_cmdlines(model)) and not (worker and self._alive(worker))`), `chain_ops.py:444-451` (`worker_cmdlines`).
**Severity:** major.
**Problem:** `worker_gone` is the AND of "no `mlx_vlm.server` worker whose `--model` basename matches `model`" and "the recorded worker pid is dead". The scan is by model **name**, not by pid. All five arms of a pick serve the **same** model name (the pick's registry name). The `busy_procs` pre-check at leg entry catches a stale same-model worker (BUSY includes `mlx_vlm.server`), so under normal sequencing the false positive is gated. But the gate is at entry, not at teardown: if a same-model worker appears **during** the leg (e.g., the daily driver's mlx-serve auto-restarts a worker for the same model after a crash, or an operator opens a second probe in another terminal), `worker_cmdlines(model)` returns it at teardown, `worker_gone` is False, the leg is INVALID, and the run stops — even though the leg's own worker was correctly unloaded. The receipt says "the loaded worker is still alive after teardown" but the surviving worker is not the leg's. No test exercises a second same-model worker appearing during the leg; `loaded_router` in `test_p475_round3.py:428` keeps exactly one worker.
**Failure scenario:** During a long TQ8 leg at 256K (~80 min), the daily driver's mlx-serve (which the operator forgot to stop) restarts its `Qwen3.8-27B-Fable-Distill-OptiQ-4.5bpw-mixed` worker after an OOM recovery. At teardown, `worker_cmdlines(model)` returns that foreign worker; `worker_gone` is False; the leg is INVALID; the run stops. The receipt blames "the loaded worker" but the leg's worker was unloaded cleanly. The operator hunts a teardown bug that is actually a foreign-worker collision.
**Proposed change:** Make the recorded pid the primary check (`worker and not self._alive(worker)`) and use `worker_cmdlines(model)` only to confirm no **new** same-model worker appeared that this orchestrator did not record (a separate, named problem: "a same-model worker not loaded by this leg is alive"). That distinguishes "our worker survived" from "a foreign worker appeared", and only the former should INVALID the leg.

### 4. `kv_env_problems` is only run when `ops.proc_env` exists; `KvArmOps` does not override `proc_env`, so the check is silently skipped if `ChainOps.proc_env` is absent
**Location:** `benchmark/bench/p475_kv.py:1009-1011` (`if hasattr(ops, "proc_env"): ...`).
**Severity:** major.
**Problem:** The pre-driver block guards the router/worker environment check with `hasattr(ops, "proc_env")`. `KvArmOps(ChainOps)` inherits `proc_env` from `ChainOps` (`chain_ops.py:356`), so on the real `ChainOps` the check runs. But the guard is `hasattr`, not "the ops type must provide this": any future `ChainOps` subclass or test double that does not expose `proc_env` silently skips the KV-env check entirely — the leg proceeds to launch the driver with no KV-override proof. The frozen tests pass `proc_env` via the `Rig.ops` mock, so the silent-skip path is not exercised. The spec's engagement preflight requires "the worker argv must carry exactly the arm's KV flags and the worker log's `KV cache resolved` line must agree"; a router/worker env carrying `KV_VALUE_BITS` is exactly the kind of leak the check exists to catch, and a skipped check is a silent engagement failure.
**Failure scenario:** A refactor moves `proc_env` behind a capability flag or a different method name on a subclass used for a probe-tree run. `hasattr(ops, "proc_env")` is False; the pre-driver block skips the env check; the router inherited `KV_VALUE_BITS=3` from `.env`; the worker serves K8/V3; the argv and `KV cache resolved` line both read `kv_bits=8` (the argv flag wins for the codec the worker reports, but the env override changes the actual key/value split under some fork paths). The leg is receipted VALID and its numbers enter the matrix under the wrong format.
**Proposed change:** Make the env check unconditional for P475 (require `proc_env` on the ops used by `p475_kv`, and raise if it is absent), or drop the `hasattr` guard and let `AttributeError` fail the leg. Add a test that an ops without `proc_env` is refused, not silently passed.

### 5. The `run` function's outer `refused = {}` is dead code; the preflight-refused set is `refused_arms`
**Location:** `benchmark/bench/p475_kv.py:1171` (`refused = {}`).
**Severity:** minor.
**Problem:** `refused` is initialized at the top of `run` and never read. The preflight-refused set is `refused_arms` (`p475_kv.py:1270`), populated at `p475_kv.py:1283` and read at `p475_kv.py:1257`. The local `refused` inside `cell` (`p475_kv.py:1215`) is an unrelated int counter for NOT_STARTED retries. The outer dict is a leftover that a reader must trace to confirm it is unused, and a future edit could wire it to the wrong set.
**Failure scenario:** A maintainer reading `run` sees `refused = {}` and `refused_arms = {}` and assumes the former is the intended name; they add a line `refused.setdefault(pick, set()).add(arm)` in the preflight loop, shadowing the real `refused_arms` population, and preflight refusals stop gating `plan` (which reads `refused_arms`). The run proceeds to schedule legs for refused arms.
**Proposed change:** Delete `refused = {}` at `p475_kv.py:1171`.

### 6. The instability rule flags a direction reversal even when both blocks are on the same side of 1.0 and the spread is below the floor for the mean but the reversal itself is real
**Location:** `benchmark/bench/p475_kv.py:862-876` (`instability_flags`), the `why = "direction reversal" if min(r) < 1.0 < max(r) else "spread"` branch.
**Severity:** minor.
**Problem:** The floor `max(SPREAD_FLOOR, 0.5·|mean−1|)` is applied to the spread check (`spread <= floor → continue`), but the direction-reversal label is assigned after the floor check passes. So a pair with ratios 0.999 and 1.001 (spread 0.002, below the 0.03 floor) is correctly not flagged. But a pair with ratios 0.98 and 1.01 (spread 0.03, at the floor) passes the floor check (`0.03 <= max(0.03, 0.5·0.015) = 0.03` is False, so it continues — not flagged). Good. The gap: a pair with ratios 0.94 and 1.05 (spread 0.11, floor `max(0.03, 0.5·0.005)=0.03`, spread > floor) is flagged as "direction reversal" and schedules a deciding block — but the "reversal" is a 0.94/1.05 pair, which is a real instability worth a third block. So the rule is correct. Withdrawing this finding after writing it — no defect. (Reported only to show the floor + reversal interaction was checked.)

### 7. Scope request: a smoke leg that is INVALID for a harness reason (wrong file, missing `kv_arm`) should not gate the full run the same way as a serving failure
**Location:** `benchmark/bench/p475_kv.py:2059-2071` (the smoke path: `return 0 if receipt["verdict"] == "VALID" else 1`).
**Severity:** scope request (no severity).
**Problem:** The spec's acceptance criterion 2 is "a smoke leg (N16, grid 8192 only) VALID before the full run". The smoke leg uses the same `run_leg` as a full leg, so it is exposed to finding 1 (wrong worker-log file) and to the `kv_arm` report-shape assumption. A smoke INVALID from a harness false positive returns 1 and the operator is told "do not start the full run", when the serving path is actually fine. The spec does not distinguish harness-caused smoke failures from serving-caused ones; the candidate implements the literal "VALID before the full run" with no override.
**Proposed change:** Add a smoke-only escape hatch that, on a smoke INVALID whose `problems` are all harness-side (no `driver_rc`, no `rung … INVALID`, no `worker identity changed`), prints a clear "smoke failed for a harness reason; the serving path is not implicated" message and a flag to proceed past it, so a harness false positive does not block a 20-hour run that the operator has already cleared the box for. Beyond the spec's literal text, but directly serves the request's intent (the smoke is a gate, not an end in itself).
