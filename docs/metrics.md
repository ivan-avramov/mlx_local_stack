## The resolved thinking budget (the silent 0.8 clamp)

🚨 **THE THINKING BUDGET YOU DECLARE IS NOT ALWAYS THE ONE IN FORCE — JUDGE CONVERGENCE AGAINST THE *RESOLVED* BUDGET** (measured 2026-08-14; it turned 33 IFEval rows into false passes). `mlx-vlm`'s `_apply_generation_budget` (`server/generation.py:585-601`) resolves the budget in two steps and **the second is SILENT**: `effective = min(max_tokens, max_kv_cache_size - prompt_tokens)` (logs a WARNING), then `thinking_budget = min(thinking_budget, int(effective * 0.8))` — `THINKING_BUDGET_CLAMP_RATIO` at `generation.py:535` — **logging NOTHING**. The IFEval runs declared `max_tokens 102400` / `thinking_budget 81920` against `max_kv_cache_size 65536`, so the budget actually in force was `int((65536 - prompt) * 0.8)` ≈ **52,390**. `ThinkingBudgetCriteria` force-injected `\n</think>` there, the model wrote its answer, `finish_reason` came back `"stop"`, and `is_converged` compared against the REQUESTED 81,920 — returning True. **That is exactly the FALSE PASS the convergence rule exists to prevent**; it slipped through because the clamp is invisible to the harness. Reproduced to the token: every loop stop matches `int((cap - prompt) * 0.8)` for its own prompt length, and every `finish_reason=="length"` row lands on `prompt + completion == cap + 1` exactly. **Fixed (`aca967b`):** `convergence.resolved_thinking_budget` mirrors the fork constant and `grade._rows` annotates from the run manifest, so `conv%` / `nonconv_kinds` / `acc_strict` are corrected at one seam; unclamped runs keep their verdicts by construction. **Standing obligations: (1) a run whose `max_tokens` exceeds `max_kv_cache_size - prompt` is measuring a budget you did not choose — check this BEFORE spending worker time; (2) never quote a "% of budget" figure without saying which budget; (3) the harness mirror of the 0.8 ratio must be kept in step with the fork.** Corrected IFEval: Ornith-1.0-35B-mlx-uniform-4bit conv 99.3%→**94.6%**, `acc_strict` 89.8%→**86.7%**; Qwen3.6-27B-Opus-Distill-OptiQ-4bit 98.6%→**93.2%**, 88.5%→**85.1%**. `acc` is unaffected (the answers still verify) and the "two winners are EQUIVALENT" headline survives.

## Thinking budget is external truncation, not a model knob

THINKING-BUDGET IS EXTERNAL TRUNCATION, NOT A MODEL KNOB. mlx_vlm's `ThinkingBudgetCriteria` force-injects `</think>` at the cap; the model never sees the budget and CANNOT "expand to fill" it. So a budget-hit means exactly one thing — the model did not self-terminate = NON-CONVERGENCE. Bumping the budget does NOT fix non-convergence (it only moves the clip point); set it as GENEROUS FIXED HEADROOM (high enough that a converging trace is never clipped — e.g. Qwen 81920), never as a tuning knob. PROVEN: gemma-4-26B-A4B-it-OptiQ-4bit LCB 16384→32768 left convergence equal/worse (11/15→8/15) and pass@1 flat (~80%), just revealing longer-but-still-truncated traces. Corollary: NEVER compare runs that differ ONLY in budget — the model ignores it, so any convergence/pass@1 delta is single-sample temp-0.7 noise, not a budget effect.

## The temperature-ladder recipe (standing per-model process)

THE KNOB FOR NON-CONVERGENCE IS TEMPERATURE, not budget (established: gemma-4-26B-A4B-it-OptiQ-4bit degenerate-loops at temp 1.0, converges at 0.7). When a model persistently hits a GENEROUS budget, run the **TEMPERATURE-LADDER RECIPE**. It is the STANDING, REPEATABLE per-model process — apply it identically to every new candidate that won't converge, so results are comparable.

- GOAL: find the HIGHEST temperature that reliably converges WITHOUT a pass@1 regression. Quality (pass@1) is the HARD CONSTRAINT (goal #1); convergence / reasoning-efficiency is the secondary objective (goal #2), optimized STRICTLY within it — NEVER trade pass@1 for convergence. We hunt a KNEE (a dramatic drop in median reasoning tokens / jump in convergence, e.g. ~8k→4k), NOT subtle differences.
- PROCEDURE: OFAT — hold everything (same items, fixed GENEROUS budget headroom via the `coding` profile) and vary ONLY temperature via the provenance-tracked `--temp` override (`bench/model_params.py`, `run.py`; each rung auto-clean-stales + is archived per-temp). Coarse grid 0.7→0.5→0.3; add ONE intermediate rung only if a big jump appears between two rungs. Per rung record {median reasoning tokens, convergence rate, pass@1} on the SAME items. N=15 single-sample resolves a DRAMATIC knee but NOT subtle (~±13pp) differences — do not over-read small deltas (0.5 vs 0.6 is noise).
- DECISION: pick the HIGHEST temp that clears the convergence bar AND holds pass@1 vs the baseline temp. No knee → record the highest reliable temp as-is.
- WATCH-POINTS: (1) reliability is often NON-MONOTONIC — too-low temp re-introduces GREEDY repetition loops (`finish=length` near `max_tokens`), so it's a sweet spot, not "lower is always better"; check BOTH ends. (2) The result is MODEL/QUANT-SPECIFIC — re-run the ladder per candidate; never globalize one model's temp.
- CAPPED FINE SCAN (validated 2026-08-17): when an item runs away at a grid temp (>1h, no self-termination), do not spend 1h/rung. Scan temp in 0.1 steps ON THE FAILING ITEM under a hard `max_tokens` 8192 cap (~7 min/probe worst case). Verdict is clamp-aware: converged iff `finish=="stop"` AND `completion_tokens < int(0.8 × min(max_tokens, cap − prompt))` — never `finish=="stop"` alone. One draw per temp (seeds are inert, O30; k>1 = byte copies). Cap in TOKENS, never wall-clock. The scan is a PROBE that selects which official n=15 rung to run; it is never a scored result and never replaces the rung — a single draw per temp finds a candidate knee, not a certified one. First use: `Qwen3.8-27B-mlx-uniform-4bit` ran away >3600s at 1.0 and 0.7 on HumanEval/146; the scan found t0.6 in ~25 min; the n=15 rung at t0.6 then scored conv 100%, pass@1 1.0, median 528 reasoning tokens.

## Convergence is a vector; how runs are ranked (the full ruling history)

**CONVERGENCE IS A VECTOR, SCORED PER ITEM — the run-level INVALID flag is RETIRED** (2026-08-11). Report `(pass@1|converged, conv%, nonconv_kinds)`. ⚠️ **THE `conv% ≥ 0.90` GATE IS WITHDRAWN — UNRATIFIED AND UNSOUND** (2026-08-11). It was not derived and never agreed: it came from the adversarial review's suggested scheme and was adopted verbatim. Three problems, all measured: (1) conv% is QUANTIZED, so the gate's strictness depends on n — at n=5 it demands perfection, at n=15 it tolerates 1 miss, at n=100 it tolerates 10; (2) comparing a POINT ESTIMATE to a hard threshold ignores sampling error — a model whose TRUE rate is exactly 0.90 fails the gate 35–45% of the time by chance (n=15→55% pass, n=30→65%, n=100→58%), and it is inconsistent with the campaign's one established threshold (eff-ctx 0.85), which is applied to the interval; (3) it is also ~10× too LENIENT on cost grounds — a runaway turn generates 102,401 tokens vs a 3,294-token median, i.e. **31×**, so even conv 0.99 spends 24% of session wall-clock on turns that never self-terminated, and Ornith-1.0-35B-mlx-uniform-4bit's measured agentic 0.94 spends ~62%. ⚠️ **BUT THE COST ARGUMENT IN (3) MEASURES AN EMPTY SET AT THE CURRENT CONFIG** (measured 2026-08-12 on m1f, 64K KV + `deployed` sampling): across **284 agentic turns** — 213 Ornith-1.0-35B-mlx-uniform-4bit, 71 Qwen3.6-27B-Opus-Distill-OptiQ-4bit — there were **ZERO** budget-hits and zero `max_tokens` truncations. Max completion 62,083 / 59,974 against an 81,920 budget; p95 38,839 / 12,016; **wasted wall-clock share 0.0%**. Agentic `conv% = 100%` for BOTH winners. The 102,401 figure is `max_tokens + 1`, i.e. a `max_tokens` truncation observed under the OLD 256K-KV config that also produced the Metal OOM — so it is a config artifact, not a standing model property. Re-measure the runaway tax per config before invoking it; do not carry the 31× number forward as if it were current.

**DO NOT rank on `successes_per_hour` — RANK ON CAPABILITY, report throughput beside it** (revised 2026-08-12; supersedes the earlier "rank on `successes_per_hour`" line, which was proposed before there was matched data to test it against). `successes_per_hour` (`stats.time_to_success`) is a THROUGHPUT metric: `E[T]=mean(t_succ)+((1−p)/p)·mean(t_fail)` is the expected wall-clock to a first success **under independent retries of a resampleable failure**. That retry model is empirically false on this stack and mis-specified for coding: (1) unseeded requests are BYTE-IDENTICAL (harness-v2 finding #1), so a literal retry reproduces the same failure forever; (2) item difficulty dominates variance (σ²_btw≈0.16), so per-item p is near 0 or 1, not a poolable coin — retrying an item the model cannot do yields zero, not `1/p` attempts; (3) it REWARDS FAST FAILURE, because a smaller `mean(t_fail)` raises the rate; (4) when p is high it degenerates into `1/latency`, since `E[T]→mean(t_succ)`. MEASURED on m1f's matched python (n=22): Ornith-1.0-35B-mlx-uniform-4bit **25.2 successes/hour** vs Qwen3.6-27B-Opus-Distill-OptiQ-4bit **7.8** (3.2×) — while the EXCLUSIVE-SOLVE sets say Qwen3.6-27B-Opus-Distill-OptiQ-4bit solves 4 exercises Ornith-1.0-35B-mlx-uniform-4bit never does (`connect`,`poker`,`pov`,`react`) and Ornith-1.0-35B-mlx-uniform-4bit solves 1 Qwen3.6-27B-Opus-Distill-OptiQ-4bit misses (`forth`); adding javascript makes it **7 vs 1**, McNemar exact two-sided **p=0.070**. No amount of Ornith-1.0-35B-mlx-uniform-4bit throughput produces those 7 solutions. And its one legitimate job — charging runaway turns — currently has NOTHING TO CHARGE (0/284 turns, 0.0% wasted wall-clock, above), which leaves only `latency ÷ pass-rate` joined by a retry model nobody performs. **WHAT THE RETRY TERM ASSUMES, AND WHY IT IS A FICTION HERE:** aider polyglot already runs 2 attempts INSIDE each case, the second one INFORMED by the test failure, both inside the case duration — that is what `final` scores. `time_to_success` instead models UNBOUNDED, INDEPENDENT, UNINFORMED retries of the whole case, which nothing in this campaign or in daily use does. The only real retry modes are best-of-k with FRESH SEEDS (`--samples k`, legitimate — there you genuinely pay wall-clock per draw) and an informed agent loop to green (where p RISES per turn, so the geometric model is wrong in the other direction).

**REPORT FOUR SEPARATELY-INTERPRETABLE NUMBERS, NO COMPOSITES:**

1. **capability ceiling** `final`/`pass@1` + CI, plus the **exclusive-solve sets** (nested ⇒ one model strictly dominates and throughput is only a tiebreaker within the shared set; crossed ⇒ neither dominates);
2. **edit competence** — well-formed rate / malformed / context-exhaustion. ⚠️ **CORRECTED 2026-08-16: "m1f: 100% / 0 / 0 for both, a genuine tie" was WRONG — it was never read off the rows.** Counted from `aider.jsonl`: Ornith-1.0-35B-mlx-uniform-4bit **4 malformed responses across 3 of 110 cases, 2 context-exhaustions**; Qwen3.6-27B-Opus-Distill-OptiQ-4bit **1 malformed in 1 case, 1 context-exhaustion**. Still effectively a tie (0.036 vs 0.009 malformed per case) and the conclusion is unchanged, but the numbers were fabricated-by-rounding and a "0" invites treating any nonzero count as anomalous. **This metric is load-bearing precisely because it separates capability from scaffold fluency:** measured on the same item set, `NVIDIA-Nemotron-3.5-Lightning-30B-A3B-4bit` produced **3.75 malformed responses PER CASE** (15 across 4 cases) — a ~100× rate — so edit competence is a real axis on which candidates differ, not a formality;
3. **latency per task** — mean/median/p95 seconds, no retry model needed;
4. **runaway tax** — non-self-terminating turn RATE and its measured **share of wall-clock**, which replaces `successes_per_hour` for the cost question because it needs no assumption at all.

Also report `conv%` + `nonconv_kinds` as DIAGNOSTICS, not as a pass/fail. **`acc` measures ONE thing** — the provided tests pass within the harness's attempt budget. It says nothing about maintainability, readability, idiom, diff surgicality or review-acceptability; per the instrumentation rule those belong to the blind mixed-family JUDGE PANEL over execution-PASSING outputs, which is built and still NEVER RUN. Do not let an execution-gated number stand in for code quality. `acc` keeps its historical meaning (correctness over generated items) so published rows stay comparable.

**`acc_strict@<budget>` (truncated draw = FAILED) IS THE RANKING KEY at a MATCHED budget** (operator ruling 2026-08-13, superseding the earlier "never the ranking key"). **A DNF counts as a failure IN THE DENOMINATOR, never as an exclusion from it:** a model that DNFs 99 of 100 tasks scores **1%, not 100%**. The old prohibition was correctly MOTIVATED — `acc_strict` rises monotonically with `thinking_budget`, and the campaign holds rows at 16384/32768/81920, so a 5× budget spread could masquerade as capability — but it was OVER-SCOPED: the hazard is a CROSS-BUDGET comparison, not the metric. Two facts make the narrow rule safe, both verified 2026-08-13: (1) `compare.py` ALREADY REFUSES any comparison where `thinking_budget` or `max_tokens` differ (`_MUST_MATCH_SAMPLING`), so the guard the prohibition wanted is mechanical and already shipped; (2) **0 of the (model, bench) pairs in the corpus mix budgets** — the mixing is ACROSS pairs, and a scoreboard row IS a pair, so `acc_strict` is sound within every row we publish (both winners sit at 81920 on every shared bench). The budget stays IN THE METRIC NAME so a cross-budget read is obvious.

⚠️ **`pass@1|converged` is DEMOTED to a DIAGNOSTIC and must NEVER rank** — it CONDITIONS on convergence, so it shrinks the denominator and carries exactly the pathology the ruling forbids: the 99-DNF model scores 100% on its one converged item. (This is the same objection already raised as "conditioning on convergence conditions on a model-dependent, easier subset"; it is now decisive rather than a caveat.)

Why the vector rather than one scalar: a wrong answer is CAPABILITY, external truncation is CONFIG × VERBOSITY, and they have different fixes — collapsing them also destroys the temperature-ladder's lexicographic rule (pass@1 is the hard constraint, convergence the secondary objective). `nonconv_kind` per item (`degenerate_repetition` / `meander` / `budget_hit` / `max_tokens`) comes from the persisted trace statistics. The FAIL-signal-to-investigate obligation is UNCHANGED; it is carried by `conv%` + the mechanism, not by voiding the run. Cross-model `pass@1|converged` MUST be paired on the intersection of items both models converged on (conditioning on convergence conditions on a model-dependent, easier subset).

## Items buy power; samples buy reliability

`Var(pass@1) = σ²_btw/N + E[p(1−p)]/(N·k)`. With σ²_btw≈0.16, E[pq]≈0.08: at N=15, k=1→5 shrinks the SD only 12.7→10.8pp (−14% for 5× the model time), while N=15→75 at k=1 gives −55%. So spend on ITEMS; use `--samples 2–3` only where run-to-run reliability is the endpoint. Minimum detectable effect (paired binary, α=.05, power .80, p_d≈0.20, `stats.mde`): **N=15 → ±32pp, N=40 → ±20pp, N=100 → ±12.5pp, N=164 → ±9.8pp, N=378 → ±6.4pp**; resolving 10pp needs 157 matched items, 5pp needs 628. NEVER print a delta without its interval and the axis MDE. **"Inconclusive" is a valid and expected answer** — failing to resolve a difference is not evidence of a tie (`stats.paired_delta` reports `equivalent` only when the CI fits inside the ±5pp TOST margin). Apply `stats.holm` across the metric family: 3 models × ~6 axes at α=.05 is a 79% chance of at least one false "better".

## Intervals: two-stage cluster bootstrap

**INTERVALS COME FROM A TWO-STAGE CLUSTER BOOTSTRAP** (`stats.cluster_bootstrap`: resample items, then resample that item's draws), NOT a pooled Wilson over N·k trials. Pooling ignores item clustering — at k=5 with ρ≈0.7 the design effect is ~3.8, making the true SE ~1.95× larger, i.e. a pooled interval is about twice too tight.

## Seeds

**EVERY DRAW CARRIES AN EXPLICIT SEED** (`rowschema.sample_seed(item_id, sample)`, recorded per row). MEASURED 2026-08-11: with no `seed` in the request the server returns **byte-identical** text for repeated identical requests (its sampler is keyed deterministically per request, `DEFAULT_SEED=0`, and the shipped suffix-decoding path keys off `(seed, row_id, position)`). So k unseeded samples are k COPIES — pass^k would collapse to pass@1 and reliability would report perfect stability for every model. Seeds derive from (item, sample) only, so they are identical across models (paired / common-random-numbers) and independent of queue order.

## Time-to-outcome (when throughput IS the question)

Expected wall-clock to a success is `E[T_success] + ((1−p)/p)·E[T_fail]` (`stats.time_to_success`), reported as successes/hour. NOT `median/pass_rate` — the Wald expectation needs the MEAN, and these runs are heavily right-tailed (a ~14.5-min median case beside 2-hour loop cases), so a median-based figure systematically flatters the loop-prone models the metric exists to punish. (Ranking on this metric is refuted above; it survives only as a descriptive throughput figure.)
