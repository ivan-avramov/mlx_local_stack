## FU-2: registry-side default sampling (RESOLVED 2026-07-09)

Per-model `generation_defaults` in `main_models.yaml` → mlx-serve forwards it opaquely as `--generation-defaults <json>` (it enumerates no param names) → mlx-vlm applies each entry only when the request omits it (precedence request > yaml > checkpoint > hardcoded; an unknown key fails loud at startup). `enable_thinking` lives in `generation_defaults` (no top-level key; a stale one raises). vscode/zed therefore get the tuned op-temps + `presence_penalty 0.0`. Runtime-verified (a no-sampling `Qwen3.6-27B-Opus-Distill-OptiQ-4bit` request resolves to temp 0.3, NOT the checkpoint's 1.0). Spec: `docs/superpowers/specs/2026-07-09-registry-default-sampling-design.md` (deleted 2026-09-03, in git history).

⚠️ The FU-2 claim that "resolved sampling is logged at INFO" is FALSE — the fork has no such line, and mlx-serve sends worker **stdout to DEVNULL** (only stderr reaches `$TMPDIR/mlx-manager-logs/<model>.log`, truncated per load). The durable rule that survives it: **a resolved-sampling readback must use a value that DIFFERS from the registry default**, because the registry fills every omitted field with the same values a client would send.

## kv_prealloc_tokens (structural; THE RULE STANDS)

`kv_prealloc_tokens` (per-model, `main_models.yaml`) is **structural**, not a sampling/client-facing carrier: mlx-serve-only, forwarded to vision workers as `--kv-prealloc-tokens`; configgen's emitters don't read it, so it never touches opencode/aider/OWUI/vscode/zed configs. Set equal to that model's `max_kv_cache_size` so the KV cache is pre-allocated at the full cap and the stack never reallocs. ⚠️ **THE RULE STANDS — IT IS WHAT MAKES 256K POSSIBLE AT ALL** (operator, 2026-08-14). Growing a cache from 128K to 256K requires holding **384K worth of KV simultaneously** during the realloc double-buffer, and that MEASURABLY OOMed. So once a model's usable context is identified, it is pre-allocated so the config works in practice. **Do NOT remove or lower prealloc on the strength of the throughput observation below.**

✅ **A THROUGHPUT CONCERN RAISED AGAINST THIS RULE IS RETRACTED — IT DID NOT REPRODUCE** (2026-08-14). A >47× slowdown was reported at `262144/262144`. A 3-arm OFAT on the SAME item (`HumanEval/146`, Ornith-1.0-35B-mlx-uniform-4bit, `deployed`, router restarted per arm) says otherwise: cap/prealloc `131072/131072` **24.7 s @ 98.5 tok/s**, `262144/131072` **25.0 s @ 103.1**, `262144/262144` (shipped) **27.8 s @ 104.5**. All fast; peak memory 25.35 / 25.50 / **28.18 GB**, far under the 46GB gate. **The original 19.5-minute non-completion was a TRANSIENT and is unattributed** — most likely environmental (that run started with ~21GB already in use by other processes and swap already active). **The rule is unchallenged.** Lesson: one dramatic observation, on one item, with two variables moved at once, is a hypothesis — it needed the OFAT before it was written down as a finding.

⚠️ **DO NOT cite peak-memory numbers from SHORT-GENERATION probes for anything memory-related.** It was inferred from the OFAT above that prealloc "may not be committing" its reservation, because doubling it moved peak memory only ~2.8GB. **That inference is INVALID:** the probe generated ~2,868 tokens, so the cache never grew past ~3K of a 131072/262144 capacity, and an untouched virtual allocation costs no resident pages. An actual OOM HAS been hit in testing, so the growth spike is real. The 46GB gate is defined on the PREFILL SPIKE precisely because a short probe cannot see it. Open question + the depth test that would settle it: `docs/open-questions.md` O15.

## max_kv_cache_size is output-determining (fingerprint member)

**`max_kv_cache_size` IS OUTPUT-DETERMINING AND IS PART OF THE PROVENANCE FINGERPRINT** (added 2026-08-14). It changes the TEXT (it sets the resolved thinking budget — see `docs/metrics.md`, the silent 0.8 clamp) and it changed THROUGHPUT, so runs at different caps must never be pooled. Consequence: `--clean-stale` can now delete rows it previously kept. **Before resuming any arm, check the cap the existing rows were generated at** — e.g. the 148 IFEval Qwen3.6-27B-Opus-Distill-OptiQ-4bit rows are at 65536, so resuming them against a 131072 registry reports STALE, and `--clean-stale` would destroy them.

## APC is OFF everywhere (benchmarks AND the daily driver)

**APC IS OFF EVERYWHERE** (operator decision; benchmark rule restated 2026-08-11, extended to `runserver.sh` on 2026-08-13 after measurement). Start any router with `APC_ENABLED` **absent from the environment**, and VERIFY it (`ps -Eww` on the router pid, and the *worker* pid too — it inherits) rather than assuming, because a stale exported value silently persists. **`runserver.sh` no longer sets it**, guarded by `test_provenance_fingerprint.py::test_runserver_does_NOT_enable_apc`.

- **WHY, mechanically: SESSION CACHING SHADOWS APC BY CONSTRUCTION.** `mlx_vlm/server/generation.py:2455-2464` dispatches any request carrying a `prompt_cache_state` to `_process_cached_request` and `continue`s past the BatchGenerator — the ONLY site that is ever passed `apc_manager`. Anonymous requests resolve to a session by chained per-message hashes, so effectively ALL traffic takes the session path and APC is never consulted. Measured 2026-08-13 with `APC_ENABLED=1 APC_NUM_BLOCKS=2048` in both router and worker env: worker `/metrics` reports `enabled: true` but `pool_used 0, lookups_hit 0, lookups_miss 0, stores 0, resident_bytes 0`; one 9K prefix served 3× gave prefill 3.10/3.00/3.00 s (no reuse); peak memory bit-identical to APC-absent (22.957264336 GB both ways). ⚠️ **The Phase-2 claim "agentic multi-turn TTFT 34–147×" does NOT reproduce and is UNRELIABLE until re-measured.**
- **What actually makes multi-turn cheap is the SESSION CACHE** (`PromptCacheState`, `server/session_manager.py`), which prefills only tokens after the common prefix and needs no `chat_id` from the client. Measured: cost per NEW token flat (0.82→0.91 ms) while cost per TOTAL token fell **17×** (2.55→0.15 ms). Independent of APC. Do not confuse the two: APC is a generic content-hashed block cache for reuse ACROSS conversations; the session cache holds one conversation's live KV. They are mutually exclusive per request.
- **WHY IT IS NOT MERELY UNUSED BUT REMOVED:** (1) zero benefit now, ~6 s per NEW conversation even if repaired (its one reachable case is a fresh conversation reusing a previous one's ~18K-token system prompt); (2) a demonstrated OOM class — `APC_NUM_BLOCKS=16384` MEASURED **~33GB**, with Ornith-1.0-35B-mlx-uniform-4bit resident the footprint was **54.2GB (4.1GB free)** and generation died on `[METAL] Insufficient Memory`, aider then retried the 500s against its 24h RETRY_TIMEOUT while the failures were scored as MODEL failures (same model, APC absent: **20.8GB, 39.9GB free**); (3) it collapses a real measurement hazard — `runserver.sh` enabling APC while the benchmark recipe omitted it is exactly why past benchmark runs silently differed from what we serve. **Served config == measured config.**
- The code, its `/metrics` counters and the **≤4096 pool-size guard** all STAY: the counters are what made the inertness provable, and a future multi-tenant deployment could want it. APC state is still RECORDED in provenance (fingerprint **v3** as of 2026-08-16 — v3 also POPULATES `draft_kind`, which v2 merely named), and `compare` REFUSES a speed/memory comparison across differing APC state. Declare it with `MLX_BENCH_APC=0|1` when the router's env can't be read.

## The suffix-decoding saga (2026-08-16)

Suffix/MTP/draft speculative decoding is INHERENTLY non-lossless on bf16 (kernel numerics flip greedy argmaxes) — proven not a logic bug; MTP is a net slowdown. Don't re-chase the numerics as "bugs."

🚨 **"Campaign runs suffix-OFF" WAS FALSE AND IS CORRECTED (2026-08-16). Suffix decoding is configured PER MODEL in `main_models.yaml` (`draft_kind: suffix`), and it was ON for EXACTLY THE TWO WINNERS and OFF for every other model** — `Ornith-1.0-35B-mlx-uniform-4bit` and `Qwen3.6-27B-Opus-Distill-OptiQ-4bit` ON (`draft_block_size 16`, `suffix_min_match 2`); `NVIDIA-Nemotron-3.5-Lightning-30B-A3B-4bit`, `gemma-4-31B-it-qat-6bit`, `gemma-4-26B-A4B-it-OptiQ-4bit` OFF. Committed, not local dirt.

**CONSEQUENCE: suffix state is OUTPUT-DETERMINING yet was ABSENT from the provenance fingerprint, so `compare` never refused across it** (it did refuse across APC state and `thinking_budget`). Every corpus comparison between a winner and any other model is therefore a **(model × serving-path) composite** — all four humanevalplus/mbppplus paired verdicts vs `NVIDIA-Nemotron-3.5-Lightning-30B-A3B-4bit`, both ifeval `--intersect` verdicts, and the aider edit-protocol contrast. All are INCONCLUSIVE so no verdict flips, but none is admissible as stated.

⚠️ **The candidate's "3.75 malformed per case" is SERVING-PATH-UNMATCHED — but the MECHANISM once offered for it is REFUTED, so do not repeat that explanation.** The claim was: aider's `diff` needs a BYTE-EXACT copy of existing code in the SEARCH block, suffix drafts from a suffix tree of prior text and is 2.41× on verbatim, so suffix-ON should help produce well-formed SEARCH blocks. **It does not follow.** Read the acceptance rule (`speculative/suffix_decoding.py`): sample the target, accept iff it equals the draft, else emit the target's token. With a deterministic proposer q is degenerate, so P(emit draft) = p_target(draft) — exactly the speculative-sampling acceptance probability — and on rejection the emitted token is p_target conditioned on ≠ draft, i.e. the residual `norm(max(0, p−q))`. **There is no bias toward continuing a copy**; the only residual mechanism is finite-precision noise, whose direction is undetermined and which is arguably LARGEST during verbatim stretches (draft length ramps up on high acceptance → bigger batch → bigger numeric deviation), i.e. pointing the other way. The confound is real (different serving path); the directional story was not. **MEASURED 2026-08-16:** the winners' aider go arms show **0 malformed across all 22 items each** with suffix ON — so a suffix-OFF winner arm is what tests it, and the candidate's figure is auditable (its raw `.aider.results.json` artifacts are on the worker under `$AIDER_REPO/benchmark/tmp.benchmarks/2026-08-16-*` (see `config.sh`), uncommitted; 3.75/case, `whole`-format 0, and the temp-0.4 "21 vs 15" all reproduce exactly).

**What IS established:** draft-then-verify is distribution-preserving in EXACT arithmetic only — lossless in distribution, never token-identical. Measured 2×2 (`bench/probe_determinism.py`): suffix ON + tail truncation OFF is **DIVERGENT across identical requests** (1.6× length spread); with the deployed `top_p 0.95 / top_k 20` it is byte-reproducible. **But ON and OFF are DIFFERENT FIXED POINTS** — different text at the same truncated config. The "quality-neutral" claim is an AGGREGATE one at MDEs of ±12.5pp/±32pp, while the campaign's lossy-lever gate is **≤5%** (needing 628 matched items at the default p_d): **the gate has never been demonstrated for suffix.** Latency benefit is real (1.27×, 23.8 s vs 30.3 s).

✅ **DONE 2026-08-16 — SUFFIX IS NOW OFF FOR ALL FIVE MODELS, and the guard exists.** `draft_kind` is commented out on both winners in `main_models.yaml` (committed) and on the worker registry. **Verified AT THE WORKER CMDLINE for both states** — a suffix-OFF worker carries no `--draft-*` argument; the winner previously carried `--draft-kind suffix --draft-block-size 16 --suffix-min-match 2`. Always verify there, never from the yaml alone. `draft_kind` is registry-only, NOT a sampling carrier, so this needs no configgen fan-out.

🔒 **FINGERPRINT v3 + `compare` REFUSAL (the mechanism that would have caught all of the above).** `draft_kind` had been NAMED in `_FINGERPRINT_RUNTIME` since v2 and was INERT: nothing populated it, so it read as absent → None, and an unobserved value is a wildcard. Of the 50 manifests on disk, 37 carry no runtime block, 13 carry exactly `{apc_enabled, apc_source}`, and **ZERO** carried `draft_kind`. **A declared-but-never-written fingerprint key is worse than an absent one, because it reads as covered.** v3 populates it via `provenance.registry_draft()`, which normalises a missing registry entry to **"off" — an OBSERVATION** — and reserves `"unknown"` for genuine ignorance. `compare` now REFUSES across differing draft state for QUALITY metrics as well as speed (stronger than the APC rule, because APC is a cache that moves only latency while suffix changes the TEXT); an UNOBSERVED value warns instead, so the pre-v3 corpus stays readable.

📐 **THE ≤5% GATE IS REACHABLE — the "628 items" figure was sized on the WRONG p_d.** 628 comes from `stats.mde`'s DEFAULT `p_d=0.20`, a BETWEEN-MODELS discordance guess. Suffix ON vs OFF is the same weights, prompt and seeds, so its discordant-pair rate is far lower: at p_d 0.05 the gate needs 157 items, at 0.02 it needs **63**. `stats.mde`'s own docstring says to measure p_d from a pilot. **Consequence: pass@1 IS an admissible OFAT endpoint** (an earlier framing excluded it — that holds only at p_d=0.20), and `benchmark/m1/suffix_ofat.py` measures p_d FIRST and reports the design n at the MEASURED value beside the default.

⚠️ **DO NOT score the suffix OFAT on any WALL-CLOCK share.** Suffix's documented purpose is a 2.41× speedup on VERBATIM text — exactly what a degenerate loop emits — so `degenerate_wall_share` moves mechanically when the lever moves, with zero quality change. An earlier plan listed it as a "sensitive endpoint"; it is a contaminated one. Use degeneracy COUNTS and TOKEN shares, the completion-token distribution, per-item text divergence, and paired accuracy. (See also O26: "degenerate wall-share" names two quantities differing by up to ~10×.)

**Return condition (O25, needs a ruling): re-enable for SERVING ONLY** — never for measurement, where per-model uniformity outranks 1.27× — **if the paired OFAT puts the accuracy delta inside ±5pp.** Measured cost of the withdrawal on `Ornith-1.0-35B-mlx-uniform-4bit`: decode ~100 → 77 tok/s, wall 23.8 → 30.3 s.

## Penalties and suffix decoding are mutually exclusive per request

**THE PENALTIES AND SUFFIX DECODING ARE MUTUALLY EXCLUSIVE PER REQUEST, and the gate is real** — cited so it stops being folklore: `_suffix_structured_fallback`, `../mlx-vlm/mlx_vlm/generate/ar.py:163`, called at `:648`. Any nonzero repetition/presence/frequency penalty (or `logit_bias`, or structured output) makes `logits_processors` non-empty, and suffix then falls back to plain decode — because its block verify samples raw target logits and can apply NO processor. So `presence_penalty: 0.0` in all four carriers is load-bearing WHILE SUFFIX IS ON; with suffix off it is a free knob. `compare` REFUSES across a penalty mismatch for this reason: it changes the distribution AND the serving path.

## presence_penalty is not the fix for the runaway tax (measured NO-GO, 2026-08-16)

`make_presence_penalty`'s `context_size` is **20**, so it can only reach verbatim cycles of period ≤ ~20 tokens; beyond that the penalty is exactly zero, not merely weaker. Of 54 classifiable nonconverged rows, 17 are reachable and **ALL 17 are ifeval — zero on humanevalplus or mbppplus**, where measured cycles run 40–262 tokens. Crossing reachability with pass/fail leaves **6 items on one model, 0 on the other**: a perfect fix is **1.1pp** of `acc_strict` against a **±5.4pp** MDE, while re-sampling 11 currently-passing rows. **Degenerate loops cost TIME, not accuracy — 6 of 10 degenerate coding rows still PASSED.** The natural experiment is already negative: the two arms shipping `repetition_penalty 1.08` have the corpus's WORST convergence (0.727 / 0.833). And the vendor pins 0.0 for THINKING mode because chain-of-thought is re-entrant by construction. **The proven lever for this failure mode is TEMPERATURE.**
